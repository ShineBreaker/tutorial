十五、移动端与特殊场景

这一章不讲按键，讲的是「换地方」。你要把已经练熟的肌肉记忆搬到三类地方：一是没有桌面 Linux 的设备（手机、平板）、二是 Windows、三是「不用鼠标」和「文件特别大」这种会打断你工作流的场合。读完你会得到三样东西：一份能照着敲的 Android 与 Windows 装机步骤、一份诚实的 iPad 可行性评估（结论多半是「别在 iPad 上做主力」）、以及一本随身排障手册——Emacs 起不来、启动即报错、卡死的时候照着做就能救回来。

要点

这一章的每一条技术结论都有出处，分三类标注：本机实测指我在写稿时用 `emacs --batch -Q --eval '...'` 在 Emacs 32.0.50 上直接查过函数与变量的存在性、默认值的；官方文档指随 Emacs 安装的 Info 手册（`emacs.info`，对应 32.0.50）或 `etc/NEWS.*` 里的原文；联网查证指我抓取了项目的官方仓库/文档站当时的原文。凡是我核实不到版本的（比如某个变量到底是哪一版被删的），我在正文里会直接说「我没能核实是哪一版删的」，而不是猜一个版本号。

易错

这一章反复出现同一条纪律，读者请务必先接受它再往下读：不要把老博客里的变量名和按键直接抄进 init.el。移动端和 Windows 这两个领域的资料尤其陈旧，因为它们的工具链更新慢、写文章的人又少，网上能搜到的多半是七八年前写的。本章里所有「这个名字其实已经不存在了」的判断，都是我在本机 Emacs 32.0.50 上用 (boundp '名字) 与 (fboundp '名字) 查出来返回 nil、并且在整棵 lisp/ 源码树里 grep 不到定义之后才写的。抄错了 Emacs 会报 Symbol's value as variable is void: 那个名字，而这种错误在 init.el 里会让 Emacs 带着一堆配置半死不活地启动，比没有配置更难查。

15.1 Android：先决定你要哪条路，再动手

2026 年在 Android 上得到一个能用的 Emacs，路只有三条，代价完全不同。选错路比选慢路更贵——很多人装了两小时 proot 才发现自己要的其实只是「在手机上改一行配置」。所以先把三条路摆清楚。

路线你得到什么代价适合谁
A. Termux 官方包一个终端版 Emacs，跑在 Termux 里，pkg install emacs 就能装只有终端界面（没有图形窗口），Android 后台会杀它在手机上改配置、跑脚本、SSH 上去写点东西
B. Termux + proot-distro一个完整的 Debian/Ubuntu/Alpine 用户空间，装在手机本地，能用发行版的包管理器proot 用 ptrace 拦截每一次系统调用，文件系统密集的活明显变慢；没有真正的 root，不能起 systemd需要发行版工具链（gcc、python、git 全套）的人
C. GNU 官方 Android 移植一个真正带图形窗口的 Android 应用，有桌面图标、有「用其他应用打开」注册必须自己在电脑上交叉编译，没有现成 APK 分发愿意折腾、要 GUI 的高级用户

路线 A：Termux 官方包，最省事的一条

这是最应该先试的一条。Termux 是一个 Android 终端应用和 Linux 环境，官方维护，源码在 github.com/termux/termux-app。它的包仓库（termux/termux-packages）里有一个官方 Emacs 包，我写稿时读到的 packages/emacs/build.sh 节选（原文件的 configure 参数有十几项，这里只摘出跟「能干什么」直接相关的几行）：

TERMUX_PKG_VERSION="31.1"
TERMUX_PKG_REVISION=3
TERMUX_PKG_DEPENDS="libacl, libgmp, libgnutls, libsqlite, libxml2, ncurses, tree-sitter, zlib"
TERMUX_PKG_SERVICE_SCRIPT=("emacsd" 'exec emacs --fg-daemon 2>&1')
TERMUX_PKG_EXTRA_CONFIGURE_ARGS="
…（另有 --without-dbus、--without-png、--without-lcms2、--with-modules、--with-gnutls 等十余项，此处从略）
--without-x
--with-dumping=none
--with-pdumper=yes
--with-tree-sitter
"

版本、服务脚本、依赖列表和这几个参数你要看懂，它们决定了这东西能干什么：

  • 版本是 31.1（revision 3）。也就是说你今天（2026 年 10 月）在 Termux 里 pkg install emacs 拿到的是 Emacs 31.1，不是最新的 32。这不是 Termux 偷懒，是 Android NDK 的编译条件比桌面苛刻。写配置时按 31 的行为来。
  • --without-x：没有 X11 支持，所以 Termux 里的 Emacs 只能跑在终端里，不能开图形窗口。注意这一条只针对 Termux 官方包；路线 C 的官方移植是带图形的。
  • --with-dumping=none 加 --with-pdumper=yes：Emacs 有两种「预编译自己的 Lisp 内核」的方式（unexec 和 portable-dump）。Termux 这份禁用了 unexec，只用 pdumper。后果是第一次启动会慢一点，而且它靠 postinst 脚本在安装时先生成 .pdmp 文件。你要是升级 Emacs 包之后启动时看见奇怪的报错，多半是这个文件没生成对，重装一次包通常就好。
  • --with-tree-sitter：带 tree-sitter 支持。这是 2025 年以后 Emacs 的新方向，意味着 Python、Rust、Markdown 等语言的解析器可以按语言加载，语法高亮和缩进不再靠正则。

装法很短：

# 1. 装 Termux 本体（Android 7 及以上）
#    从 F-Droid 装 https://f-droid.org/en/packages/com.termux/
# 2. 装 Emacs
pkg update
pkg install emacs

# 3. 确认版本
emacs --version        # 应输出 GNU Emacs 31.1 ...
易错

不要混着装 Termux 的多个渠道。Termux 的 F-Droid 版、GitHub 版、Google Play 版签名密钥各不相同，而 Termux 本体和它的所有插件（termux:api、termux:boot、termux:widget、termux:x11）共用同一个 sharedUserId（com.termux），Android 要求同一组 APK 的签名一致。你从 F-Droid 装了 Termux，又从 GitHub 装 Termux:API，安装时会直接失败并报 INSTALL_FAILED_SHARED_USER_INCOMPATIBLE 或 signatures do not match previously installed version 这类错误。这是 Termux 官方 README 里明确写出来的一条（「Do not attempt to mix them together」），我写稿时读的原文就是这么说的。

另一个已经过时的事实：Google Play 版是实验分支，只为 Android 11+ 提供，官方描述是「under development and has missing functionality and bugs compared to the stable F-Droid build」。Termux README 给的建议是「如果你能装 F-Droid 或 GitHub 版，就应该装那两个」。2026 年了，Google Play 版仍然不要用。

另外注意 Termux 的最低要求是 Android 7；Android 5/6 只在 GitHub 渠道有应用本体，没有包仓库更新，装不了 Emacs。

路线 B：Termux + proot-distro，要完整 Linux 时才值得

proot 是一个用户态工具，利用 ptrace 把系统调用逐个拦截并做路径重定向，从而在没有 root、没有内核模块、没有 Docker 守护进程的前提下「假装」出一个 Linux 根文件系统。proot-distro 是 Termux 官方维护的包装器（源码 github.com/termux/proot-distro），现在可以从 Docker Hub 直接拉发行版镜像装进手机。

我写稿时读它的 README，它对自身限制的描述非常坦率。这一段几乎可以原样当作选型依据（下面四条我略去了每条末尾的解释句，只保留关键事实）：

Performance: proot intercepts every system call via ptrace. Filesystem-heavy workloads (compilation, package managers) are noticeably slower than native execution.

Kernel features: features that depend on Linux kernel modules (FUSE, specific iptables targets, custom cgroup hierarchies, etc.) do not work.

No background services: starting service supervisors (systemd, OpenRC, socket-activated daemons) is generally not possible.

No cgroups / namespaces: proot is path translation, not kernel isolation.

翻译成人话：编译和装包会明显慢；你不能指望在里面跑 systemd 或任何服务管理器；sudo、mount、iptables 这类需要真 root 的操作会失败。如果你只是想「在手机上有个能跑 python 和 git 的环境」，这条路的性价比很高；如果你想在手机上编译一个大型 C 项目，先想清楚那要多花的时间。

pkg install proot-distro     # 会自动带上 proot 这个依赖

proot-distro install debian:bookworm
proot-distro login debian

# 进到容器里之后：
apt update && apt install -y emacs-nox git

# 把手机的 home 目录挂进容器（root 挂在 /root，普通用户挂在 $HOME）
proot-distro login debian --shared-home

几点必须提醒的：README 写明 proot-distro 拒绝在另一个 proot 里运行（proot 本身不支持嵌套，因为它没法 trace 一个已经被 trace 的进程），并且运行时会警告如果你以 root 身份启动。另外 proot-distro 自己也列了一条限制：「No zstd-compressed layers: Python's tarfile module does not support zstd」——用 zstd 压缩层的镜像装不上，得换镜像或换旧版本号。

路线 C：GNU 官方 Android 移植（要图形界面就选这条）

这条路我知道得最晚，但它才是「正路」。Emacs 30.1 起官方就支持 Android 平台——etc/NEWS.30 里原文写着：

Emacs has been ported to the Android operating system. This requires Emacs to be compiled on another computer. The Android NDK, SDK, and a suitable Java compiler must also be installed.

See the file java/INSTALL for more details.

Emacs 32 的手册里有专门的附录 H 讲这件事（ChR 然后 emacs RET 就能翻到，或者直接 Chi emacs 搜「Android」）。附录里交代了几件只有读了才知道的事：

  • Emacs 的 lisp/ 数据目录在 Android 上挂载点是 /assets，里面是 etc、lisp、info 三个目录。
  • /assets 和 /content 目录下没有 . 和 ..，且这两个目录里不能起子进程——你把 default-directory 设成 /assets 再 M- x ls，命令会悄悄改在 home 目录里执行。这是 Android 的 asset manager 不是真文件系统造成的。
  • Android 应用能访问的目录就四类：应用私有数据目录（Emacs 的 home 就在这里）、应用库目录（会自动加进 exec-path）、外部存储（需要用户授权「文件和媒体」权限）、以及 Android 5.0 起的文档提供者目录。
  • Emacs 自己注册了一个 emacsclient 包装器，让别的应用可以把文件「用 Emacs 打开」；它还注册了 org-protocol: 链接和 mailto: URI。但这些都要求 Emacs server 已经在跑，否则会失败。
  • 调试很麻烦：启动时的消息在系统日志里，要看日志得用 adb 连上电脑跑 adb logcat | grep -E "(android_run_debug_thread|[Ee]macs)"。

代价我也写清楚：这条路线没有现成 APK 分发，你得在电脑上装好 Android NDK/SDK/JDK，按 java/INSTALL 的说明交叉编译，再把 APK 装到手机上。整个过程对第一次做交叉编译的人来说以「天」为单位。我自己没跑过这个流程，所以这里只写文档怎么说的，不写我的成功经验。

要点

如果你的需求里包含「想要一个带菜单栏和图标的 Emacs」，那 Term:X11 值得看一眼。Termux 官方有一个 X 服务器（源码 github.com/termux/termux-x11，要求 Android 8+），装好之后可以在 Termux 里跑 termux-x11 :1 起一个 X server，再在里面跑任何 X 程序。但要清楚两件事：一，Termux 的主 Emacs 包（pkg install emacs，即 packages/emacs）是 --without-x 编译的，在 Term:X11 里跑不起来——不过你不必自己编译：Termux 另有官方的 X11 版包 emacs-x（源码在同一个仓库的 x11-packages/emacs-x/build.sh，我写稿时它同样是 31.1，依赖里有 libx11、libxaw、libxft 等一串 X 库，并且没有 --without-x）。装法是先开图形仓库再装它：pkg install x11-repo 然后 pkg install emacs-x；注意它用 TERMUX_PKG_CONFLICTS="emacs" 与主包互斥，两个不能同时装。二，Term:X11 的 README 明确提醒 Android 会给「不在屏幕上的应用」更少的 CPU，Term:X11 一开，Termux 本身就被系统认为不在前台了，于是里面的东西会变慢——官方给的解法是装 termux-x11-universal-sharedUid-debug.apk 变体，让两个应用算作同一个（注意这个变体只兼容从 GitHub 装的 Termux，因为要签名匹配）。

练习 1　你在 Termux 里执行 pkg install emacs 之后运行 emacs --version，看到 GNU Emacs 31.1。你想要确认这个 Emacs 是不是带图形界面支持的，应该看安装脚本里的哪个 configure 参数？

看 --without-x。Termux 官方包的 packages/emacs/build.sh 里带着 --without-x，意思是编译时禁用了 X11 支持，所以这个 Emacs 只能跑在终端里，开不了图形窗口。想在 Android 上要图形，得走 15.1 的路线 C（官方移植）或自己用 Term:X11 重新编译。

练习 2　有人告诉你「装个 proot-distro 就能在手机上跑完整 Linux，跟真机没区别」。根据它的官方 README，下面哪一条是真的？

真的那条是：proot 通过 ptrace 拦截每一个系统调用，所以「文件系统密集的负载（编译、包管理器）明显比原生执行慢」，而且依赖内核模块的特性（FUSE、部分 iptables 目标、自定义 cgroup 层级）不能用，systemd 这类服务管理器基本起不来，sudo / mount / iptables 这些需要真 root 的操作会失败。另外它不能嵌套——不能在另一个 proot 里再跑。所以「跟真机没区别」是错的；准确说法是「能拿到发行版的包管理器和工具链，但慢且没有真 root」。

练习 3　你用官方移植版 Emacs 跑在 Android 上，启动时崩了，什么也没显示。要看到崩溃信息，Emacs 手册让你怎么做？

手册附录「Android Startup」说：启动期间的消息写在系统日志里，要用 adb（Android Debug Bridge）从另一台电脑上看。步骤是设备里开「开发者选项」→ 开「USB 调试」→ 用 USB 连电脑 → 在电脑上跑 adb logcat | grep -E "(android_run_debug_thread|[Ee]macs)"。手册还提到 Emacs 起来之后可以直接在 Emacs 里异步跑一条 logcat 命令来看日志。

15.2 Termux 实操：后台限制是与桌面共享配置

装好了不等于能用。Android 和 Linux 的根本差别在于：你的应用随时可能被别人杀掉。这一小节把 Termux 官方 README 里关于这件事的原话摆出来，再给对策。

Android 会怎么杀你，以及怎么让它别杀

Termux 官方 README 顶部有一条加粗的警告，我原样引用（写稿时读到的版本标注为 v0.118.3）：

NOTICE: Termux may be unstable on Android 12+. Android OS will kill any (phantom) processes greater than 32 (limit is for all apps combined) and also kill any processes using excessive CPU. You may get [Process completed (signal 9) - press Enter] message in the terminal without actually exiting the shell process yourself.

翻译成你能据此行动的三条：

  • Android 12 及以上可能杀进程。你在终端里会看到 [Process completed (signal 9) - press Enter]，意思是进程被 SIGKILL 掉了。按回车重来即可，你的数据没丢。
  • 整个系统所有应用加起来只有 32 个进程的上限（不是每个应用 32 个）。所以在手机上开一堆 Emacs daemon + 一个 proot 容器 + 几个后台服务，很可能就是把这 32 个名额占满了，然后某个无辜的进程被随机牺牲。
  • 电量优化会杀后台。这是厂商 ROM 最常见的杀手。Termux README 明确让你去 dontkillmyapp.com 查你的手机该怎么关掉这个优化，并把它写在 F-Droid 那段的注意事项里（「Make sure battery optimizations are disabled for the app」）。小米/红米、华为、OPPO、vivo、OnePlus 这几家的 ROM 都需要单独处理。
# 在 Termux 里打开系统设置页（不同 ROM 的 intent 可能不一样，最通用的写法）
termux-open-settings

# 用 termux-api 插件查询当前的电池优化状态，需要先装 Termux:API
termux-battery-status | grep -i optimization
技巧

如果你想让 Emacs 在你切走之后还活着并且能连回来（这是 termux-services 的用途），Termux 官方那个 Emacs 包自带一个服务脚本：TERMUX_PKG_SERVICE_SCRIPT=("emacsd" 'exec emacs --fg-daemon 2>&1)。用法是：

pkg install termux-services
sv-enable emacsd        # 开机自启（termux-services 依赖 Termux:Boot）
sv up emacsd             # 立刻启动
# 看日志，出问题第一件事就是看这里
cat $PREFIX/var/log/sv/emacsd/current

sv-enable / sv up / sv down / sv-disable 这套命令来自 termux-services 自己的 README，日志固定在 $PREFIX/var/log/sv/<服务名>/current。README 原文是：「A service is disabled if $PREFIX/var/service/<服务名>/down exists, so the sv-enable and sv-disable scripts touches, or removes, this file.」所以 sv-enable 的效果就是「下次开机自启」，而 sv-disable 会创建那个 down 文件把它关掉——如果你 sv-enable 之后 sv status emacsd 还是显示没跑，多半是你之前 disable 过，文件还在。还有一个前提要提醒：termux-services 的开机自启依赖 Termux:Boot 这个插件（包名 com.termux.boot），而且它必须和 Termux 本体来自同一个渠道，否则装不上。说明一下：渠道一致这一条我是从 Termux README 核到的；而「依赖 Termux:Boot」这一条我没能从 termux-services 当前那份很简短的 README 里找到原文，所以它属于通行做法而非我核实到的文档结论——如果你 sv-enable 之后重启手机发现服务没起来，第一件事就是去 F-Droid 装上 Termux:Boot。

与桌面共享同一份配置：能共享什么，不能共享什么

Android 与桌面之间共享配置是可行且常见的，但「共享」两字要拆开看：你可以共享纯 Elisp 源码，不该共享编译产物和机器相关的数据。下面是踩过就懂的清单。

能共享的：early-init.el、init.el、各种 modules/*.el、Org 文件、dash 这类函数式配置的函数库。

绝对不要同步的：

  • *.elc（字节编译产物）。不同平台的编译产物互不兼容，同步过去只会得到一堆莫名其妙的加载错误。用 .gitignore 排掉。
  • 原生编译产物（*.eln）和相关缓存目录（eln-cache/、native-comp/ 之类）。同理，Emacs 会自己在每台机器上重新生成。
  • .dir-locals.el（除非你真的想共享）、recentf、transient/、url/、projects/ 这类自动保存的会话状态。
  • 任何机器相关的路径。这是最关键的一条，见下面的配置片段。

路径差异是共享配置时最容易翻车的地方。Android 上的 home 目录和 Linux 桌面的 home 目录结构不同（比如你在桌面用 ~/projects，Termux 里可能根本没有这个目录，或者挂在 /sdcard/ 下面）。Emacs 提供了正规的查询方式，不要硬编码：

;;; init.el 片段：跟着平台走，不要硬编码路径。
;;; 依赖：无第三方包，只有内置的 cl-lib。
;;; cl-remove-if-not 来自 cl-lib，所以 require 必须写在它被用到之前。

(require 'cl-lib)

;;; user-init-file 是变量，值就是「Emacs 正在加载的那个 init 文件」的绝对路径。
;;; Emacs 启动时在读 init.el 之前就把它设好了，所以在这个文件里直接可用。

(defconst my-emacs-d (file-name-directory (or user-init-file (expand-file-name "init.el"))))

(defun my-config-dir ()
  "配置所在目录；桌面和 Android 上都指向 init.el 旁边那一份。"
  my-emacs-d)

(defun my-sync-dir ()
  "同步目录：存在就用它，不存在就退回 home，不报错。"
  (or (car (cl-remove-if-not #'file-directory-p
                             (list (expand-file-name "~/projects/emacs-config")
                                   (expand-file-name "~/sync/emacs-config")
                                   (expand-file-name "/sdcard/Sync/emacs-config"))))
      (expand-file-name "~/")))

(setq my-projects (expand-file-name "projects/" (my-sync-dir)))
易错

别再写 (locate-user-emacs-file) 了，这个用法是错的，而且流传很广。本机实测：(commandp 'locate-user-emacs-file) 与 (interactive-form ...) 都是 nil——它既不是命令也没有交互式声明，所以 M- x 调不了；而且它的签名是 (locate-user-emacs-file NEW-NAME &optional OLD-NAME)，必须传一个文件名参数。你要是照老文章写 (file-name-directory (locate-user-emacs-file))，Emacs 会直接报 wrong-number-of-arguments (locate-user-emacs-file 0)。它真正的用途是「在 Emacs 的用户数据目录里算出一个文件名」，比如 (locate-user-emacs-file "abbrev_defs" ".abbrev_defs") 这种内置用法，跟「我的 init 文件在哪」无关。

想知道 init 文件在哪，问 user-init-file 这个变量；想知道 early-init.el 在哪，问 early-init-file。这也顺带说明为什么不该硬编码 ~/.emacs.d：作者本机实测 user-emacs-directory 的值是 /home/you/.config/emacs/（用户名已替换）——同样是因为那台机器上 ~/.config/emacs/ 已存在。而在一台 HOME 下什么都没有的全新机器上实测，得到的是 ~/.emacs.d/，可见这个值根本不是固定的。

上面这段代码我已经原样在 Emacs 32.0.50 上跑过一遍，三个函数都正常求值、不报错。剩下的两条经验性提醒：(require 'cl-lib) 必须在用到 cl-remove-if-not 之前执行（Emacs 读配置是自上而下的，写在后面就会报 void-function）；or 那一层兜底是为了在「Emacs 没找到任何 init 文件」时也能给出合理默认值。

要点

再补一个移动端特有的实用配置：用 system-type 做平台分支。system-type 是 Emacs 内置变量，取值是符号（不是字符串）：gnu/linux、darwin、windows-nt；Termux 里它的值也是 gnu/linux，因为 Termux 跑的是 Linux 内核。所以如果你要区分「桌面 Linux」和「Termux」，不能只看 system-type，得再判一个环境变量：

(when (getenv "TERMUX_VERSION")
  ;; 只有在 Termux 里才生效的配置
  (setq gc-cons-threshold 200)
  (setq inhibit-startup-screen t))

TERMUX_VERSION 是 Termux 官方脚本里用来检测 Termux 环境的那个变量（Termux 的 shell 启动脚本会设置它）。这一点我是按 Termux 的通行做法写的，不是我在本机 Emacs 上验证出来的——本机没有 Termux 环境。如果你不想依赖环境变量，另一个更稳的办法是判路径：(string-prefix-p "/data/data/com.termux" (getenv "HOME"))，Android 上每个应用的私有目录都在 /data/data/<包名>/ 下面。

这是 Android 系统的「电量优化 / 后台限制」层面，跟 Emacs 本身无关。终端里那句 [Process completed (signal 9)] 就是 Termux 官方 README 里点名说的现象。查法：Termux README 让你去 dontkillmyapp.com 按你的手机品牌和型号查该怎么把电池优化关掉，然后用 termux-open-settings 打开系统设置处理。顺带提醒：Android 12+ 的 proot-distro 那套 README 里也提到系统会在 12L/13 提供关闭这种杀进程行为的开关，但作者仍然写明「upgrade at your own risk if you are on Android 11」，也就是不建议为了这个去升级旧系统。

15.3 iPad / iOS：先接受一个结论，再谈方案

这一小节的结论要放在最前面，因为它能替你省下几个周末：

要点

2026 年，iPad 上没有一条「装完就能像桌面一样用 Emacs」的路。App Store 里没有 GNU Emacs；能跑真 Emacs 的项目都是要你自己编译、自己签名、自己侧载的实验性项目，其中最活跃的一个在写稿时才存在了三个月。反过来说，iPad 上真正实用的 Emacs 方案只有一个：把 Emacs 放在别处，用 iPad 当键盘和屏幕。下面把三条路都讲清楚，附上我实际核实到的项目状态，你按自己的场景选。

为什么 App Store 上不可能有 GNU Emacs

这个问题我不是靠记忆回答的。Codeberg 上那个 iPad 移植项目 mclearc/emacs-ipad 的 README 里有一段专门的说明，我原样引用：

This is not an App Store app and cannot be one. GNU Emacs is GPLv3, and the App Store terms are incompatible with the GPL, so the only distribution path is sideloading onto your own iPad.

这是该项目作者的判断，我读的是他的原文，不是我对 Apple 条款的法律解读。你可以把它当作「至少在 2026 年，GPLv3 项目的分发路径被 App Store 条款挡住了」这一事实的来源。

那 App Store 上有没有「长得像 Emacs」的替代品？有，但我建议你先看完这段再决定要不要装：

  • 「Emacs starts in about half a second」——冷启动约半秒。
  • 「No subprocesses of any kind: the Out of Scope list below is a hard consequence of the iOS sandbox, not a roadmap」——任何子进程都跑不了。这意味着 M- x compile、M- x shell、grep/git 这些全都没有。这条限制来自 iOS 沙箱，不是「以后会做」。
  • 它的解决方案很有想象力：把 libgit2 直接编进应用，配一个叫 vc-libgit 的后端，于是 vc-dir、vc-diff、提交日志、暂存、提交、丢弃、建分支、切换分支都在设备上可用，而 git 二进制本身跑不了。如果你用 Magit，这里要泼一盆冷水：Magit 依赖调用外部 git，在这个项目里用不了。

它的 README 里有一段关于「原生 GUI 后端」的话，我认为这是判断这条路能走多远的关键，引用如下：

The ultimate goal is a native GUI: a real iOS/Metal redisplay backend for Emacs, the iOS analog of the macOS nsterm.m or the Android port's androidterm.c, drawing Emacs frames directly rather than through a terminal grid. No such backend exists yet, in this project or anywhere else.

这段话里有个顺带的印证：它提到 Android 移植版的 androidterm.c 是「Emacs 源码里已经有的」东西——这和 15.1 路线 C 里 GNU 手册附录 H 讲的那个官方 Android 移植对得上。两个独立来源指向同一件事。

第三个项目：macOS 优先，iPadOS 还在路线图上

GitHub 上 hiroakit/emacs-on-apple 的定位是「Emacs for Apple devices」，我读它 README 时看到两点：一是它当前目标是 Emacs 30.2，README 自己标为「Experimental」；二是它的目标清单分三层，macOS 启动、App Store 分发这类属于「Immediate」和「Finally」，而 「Support iPadOS」被明确列在最后那一档。所以这是一个 macOS 项目，iPadOS 是将来的事，不是现在的事。

那么 iPad 上真正该怎么用 Emacs

把上面三个方案和代价放在一起，务实结论有三条：

  1. 主力方案：远端 Emacs，客户端只当键盘。在你的服务器、家里的机器或云主机上跑 Emacs，iPad 上用一个支持 SSH 的终端客户端连进去。App Store 里有若干款这类客户端（例如 Blink Shell、Termius）——我写稿时没有逐一核实它们在 2026 年的功能与订阅政策，这一点你需要自己确认。这条路的好处是：Emacs 跑在真正的 Linux 上，Magit、Eglot、LSP、编译全都正常；坏处是它依赖网络，而且手机端的终端键盘对 CM- 这种组合键支持普遍一般，你可能要把 C- 单独映射到一个可点的修饰键上。
  2. 进阶方案：远端 Emacs + emacsclient。如果你的 SSH 客户端支持端口转发，可以在电脑上跑 M- x server-start（这一节前面那张表里有），然后让客户端把本地端口转到远端的 Emacs server 端口上，之后用 emacsclient 打开文件会直接跳到已经开着的那个 Emacs 会话里，不会每次新开一个窗口。但这依然是「Emacs 在远处」，没有解决网络依赖。
  3. 本地方案：emacs-ipad，如果你愿意当早期用户。适合这样的场景：你要的是「在没有网络、没有服务器的飞机上写点东西」，而且你手上确实有 Mac + Xcode，愿意花时间编译和维护。它的存在本身就是有价值的——它证明了 iOS 沙箱下的 Emacs 不是不可能，只是代价极高。
易错

不要为了「在 iPad 上装 Emacs」而把 iPad 越狱或做不透明的重签名分发。理由不是安全洁癖，而是收益为零：你折腾一整天换来的还是 emacs-ipad 那个终端网格界面，外加一个每 7 天就要重签一次、随时可能失效的安装包。iPadOS 沙箱禁止任何子进程（上面引用过原文），这条不会因为你越狱就自动消失——真要真正自由，得回到 15.1 的路线 C 那类「自己编译一份带完整后端的 Emacs」的思路，而那在 Linux 和 Windows 上是顺手的事，在 iPad 上不是。

如果你只是想「在 iPad 上读自己写的 Org 笔记」，那根本不需要 Emacs：用一个支持 Markdown/Org 的笔记 App 就够了。为了一个编辑器的图标去改变一台设备的安全模型，是本末倒置。

练习 6　你决定走「远端 Emacs + iPad 当键盘」这条路。SSH 上去之后，第一件该敲的命令是什么？

M- x server-start。它会启动 Emacs 的 server 端，这样以后你每次从客户端进来不必新开一个 Emacs 会话，用 emacsclient 就能把文件送进已经开着的那个 Emacs 里。想知道 socket 到底在哪，用 M- (list server-socket-dir server-name)——这两个内置变量拼起来就是 socket 的完整路径，server-socket-dir 一般是 $XDG_RUNTIME_DIR/emacs 或 /tmp/emacs<uid>。别指望 *Messages* 会告诉你：server-start 里那句 Started server 走的是 server-log，而 server-log 默认是 nil，什么都不打印；把它设成 t 才会记到 *server* 缓冲区里。关掉用 M- x server-force-delete。再顺带纠正两条老教程：M-x server-edit 不是用来查 socket 的——它的作用是「切到下一个由 emacsclient 打开的编辑缓冲区」，与 socket 路径无关；M-x edit-server-socket 这个命令在 Emacs 29 到 32 的 server.el 里都不存在，按了只会得到 Invalid command；而 server-stop 虽然是真函数，却没有 interactive 声明，M- x 也调不了，能交互式停掉 server 的是 server-force-delete。

练习 7　为什么 App Store 里没有一个真正能用的 GNU Emacs？下面哪条是 mclearc/emacs-ipad 项目 README 里给出的理由？

原文的理由是：GNU Emacs 是 GPLv3，而 App Store 的条款与 GPL 冲突，所以唯一的分发途径是在你自己的 iPad 上侧载。这句话是该项目作者的表述，不是我对 Apple 条款的解读，但方向是可靠的：App Store 上唯一叫 Emacs 的东西是 Marc Feeley 的 Not Emacs，那是个 2015 年发布、2015 年之后再没更新过的 ymacs 派编辑器，只支持「部分常用 Emacs 键位」，不是 Emacs 本身。

练习 8　假设你在 iPad 上真的跑起来了 emacs-ipad，能不能用 Magit？为什么？

不能直接用。Magit 的工作方式是调用外部 git 可执行文件去跑子命令，而 iOS 沙箱禁止任何子进程，该项目的 README 把这条列为「hard consequence of the iOS sandbox, not a roadmap」。这个项目给出的替代方案是自己解决：把 libgit2 编进应用，写了一个叫 vc-libgit 的后端，于是内置的版本控制接口（vc-dir、vc-diff、暂存、提交、建分支、切换分支）都能用——但那是内置 vc 的能力，不是 Magit 的界面。

15.4 Windows：推荐 WSL，原生构建是第二选择

Emacs 在 Windows 上有三条路可以跑：WSL 里的 Linux 版、官方的原生 Windows 构建、以及Cygwin / MSYS2 里的第三方构建。我把三者的代价讲清楚，然后给出推荐。

要点

推荐 WSL，没有悬念。理由很直接：WSL 里跑的是真正的 Linux 版 Emacs，system-type 就是符号 gnu/linux，你在本书其他章节里学到的所有 Linux 技巧——Tramp、Eglot、Magit、编译、Org——原样有效，不需要为 Windows 写任何分支。你在 Windows 上遇到 Emacs 的问题时，绝大多数是「Windows 的问题」而不是「Emacs 的问题」；WSL 把绝大部分 Windows 问题挡在了外面。

    wsl --list --online

wsl --install -d Ubuntu-24.04
    --install 名字里的 -d 就是 distribution 的意思。文档还提醒：如果 wsl --install 之后停在 0.0% 不动，改用 wsl --install --web-download -d <发行版名>，它会先把发行版下载下来再安装。
  4. 装 Emacs：第一次进发行版会让你建用户名和密码（这个密码是 Linux 用户的，不是 Windows 账户的），然后 
    sudo apt update
sudo apt install emacs-nox     # -nox 是纯终端版，不装 X11 相关依赖
emacs --version
  5. 确认你在 WSL 2 上： 
    wsl -l -v
    这条命令会列出所有发行版、运行状态，以及每个发行版跑的是 WSL 1 还是 WSL 2。官方文档明确说 WSL 2 需要 Windows 11 或 Windows 10 版本 1903（Build 18362）及以上。要转换已有的发行版：wsl --set-version <发行版名> 2；要改新装发行版的默认版本：wsl --set-default-version 2。官方文档同时提醒：版本转换可能很耗时、也可能因为架构差异而失败，大项目的发行版转换前请先备份。
  6. 保持 WSL 是最新的：wsl --update。这一步不是可选的——下面讲 systemd 时会用到版本下限。

最容易踩的两个坑：文件放哪、systemd 开不开

坑一：文件位置。微软的 filesystems.md 文档里有明确建议，我原样引用：

We recommend against working across operating systems with your files, unless you have a specific reason for doing so. For the fastest performance speed, store your files in the WSL file system if you are working in a Linux command line.

When storing your WSL project files:

  • Use the Linux file system root directory: /home/<user name>/Project
  • Not the Windows file system root directory: /mnt/c/Users/<user name>/Project

翻译过来就是：项目代码放 WSL 自己的文件系统里（~/project），不要放 /mnt/c/...。后者要穿过一层 Windows↔Linux 的文件桥（DrvFs），每次系统调用都有额外开销——在 Emacs 里这意味着打开文件慢、revert-buffer 慢、Magit 的 git status 慢、文件变更发现有延迟。这是本章最值得记住的一条 Windows 实践。

需要从 Windows 里访问这些文件时，官方给的路子是 \\wsl$：在资源管理器的地址栏输入 \\wsl$ 就能看到所有发行版的根文件系统。从 WSL 里反向打开 Windows 资源管理器也很方便：

explorer.exe .              # 打开当前目录
powershell.exe /c start .  # 同上，官方给的另一种写法

坑二：大小写。WSL 文件系统默认是大小写敏感的（因为你跑的是 Linux），而 Windows 文件系统大小写不敏感。微软的 case-sensitivity.md 还给了一个反向的坑：在 Windows 侧，如果你把某个目录标成了大小写敏感，那些假定「文件系统不区分大小写」的 Windows 应用可能就打不开里面的文件了；而且 Windows 应用在这个目录树里新建的子目录不会自动继承大小写敏感属性。这个坑的实践含义是：大小写敏感的目录混着给 Windows 应用用，是一个已知的、会咬人的组合。

systemd：以前 WSL 用的是仿 SystemV 的自定义 init，所以 systemctl 那套不管用。现在 WSL 支持 systemd 了，官方文档给的启用方法是改 /etc/wsl.conf，然后必须从 PowerShell 跑 wsl.exe --shutdown 重启 WSL 实例，改动才生效。

# 编辑 /etc/wsl.conf，加上：
[boot]
systemd=true

# 然后在 PowerShell 里（不是 Linux shell 里）：
wsl.exe --shutdown

# 重进发行版后确认：
systemctl list-unit-files --type=service

官方文档（systemd.md）还写明一个版本下限：WSL 必须是 0.67.6 或更新才能用 systemd。检查方法是 wsl --version；文档明确说，如果这条命令抛出 Invalid command line option: --version 错误，说明你用的是老的 inbox 版 WSL，必须先 wsl --update。而 systemd.md 同时说明：wsl --install 默认装的那个「当前版 Ubuntu」已经默认用 systemd 了，其他发行版可能还在用仿 SystemV 的 init，才需要手动加这几行。

进阶：为什么 metadata 默认是关的，以及你什么时候该打开它

微软 wsl-config.md 文档的 [automount] 小节里，metadata 这个选项的默认值是 disabled，含义是「不给 Windows 侧的文件添加 Linux 权限元数据」。它的作用是让 chmod、chown 这类 Linux 权限语义在 NTFS 上也能工作——代价是要在 Windows 文件系统上额外维护一份权限记录。

什么时候该开：你在 /mnt/d/ 之类的地方跑需要权限位的程序（某些语言的包管理器、某些测试工具），而且确实撞到了权限报错。什么时候别开：你只是把代码放在那儿编辑——那么它只会多一层转换开销，不会带来任何好处。

文档里还有一个容易踩的细节：权限相关的挂载选项（umask、fmask 之类）只有在盘是带 metadata 挂载时才生效，而 metadata 默认是关的。也就是说你在 wsl.conf 里写了一堆 umask= 却发现没效果，多半是这个原因——不是你写错了，是前提没满足。

高危一：在 /mnt/c/... 上跑 Emacs daemon 或 Magit。不会损坏数据，但会遇到两类很难查的问题：一是性能塌掉（DrvFs 桥接的开销，Git 尤其怕这个）；二是权限与换行符会被搞混——你可能同时在 WSL 和 Windows 原生 Emacs 里打开同一个仓库，一个按 Linux 语义处理、一个按 Windows 语义处理，两边互相覆盖。正确做法是把仓库整个放在 WSL 的文件系统里，只在需要时用 \\wsl$ 或 explorer.exe . 去看它。

高危二：把 WSL 的 ~/.emacs.d 目录直接挂给 Windows 原生 Emacs 用（比如让 Windows 侧指到 \\wsl$\Ubuntu\home\me\.emacs.d）。共享源码没问题，但同一个目录里会同时出现 Linux 版和 Windows 版 Emacs 生成的 .elc、原生编译产物 .eln 和相关缓存，两边互相覆盖：轻则每次启动都重新编译，重则加载到不兼容的字节码而报难懂的错。要共享就共享 .el 源码（用 Git 同步），编译产物一律各人生成。

高危三：卸载发行版。wsl --unregister <发行版名> 会永久删除该发行版的整个文件系统，且不可恢复。微软文档在 basic-commands.md 里把它单列一节，标题就叫「Unregister or uninstall a Linux distribution」。执行之前务必确认你的代码已经提交或备份——你写在 ~/project 里的东西（按上面的建议）不会跟 Windows 盘联动，删发行版就真的没了。

官方原生 Windows 构建：什么时候该选它

WSL 不是唯一选项，也不是永远最好。以下两种情况选原生构建更合适：

  • 你需要在 Windows 桌面（资源管理器、VS Code、Word）里用「打开方式 → Emacs」，并且不想跳出一个应用。
  • 你在意的文件本来就在 Windows 盘上，而且文件量不大。

原生构建有若干与其他平台不同的地方。下面每一条都来自 Emacs 32.0.50 手册的附录 I「Microsoft Windows」，我在本机的 emacs.info 里逐条读过。

四个可执行文件的区别，这是最容易搞混的地方：

程序性质什么时候用
emacs.exe控制台程序（按 Windows 的定义）在「命令提示符」里敲 emacs。代价是：那个命令提示符窗口在 Emacs 退出前不能用来敲别的命令。
runemacs.exe同上，但隐藏控制台窗口桌面快捷方式应该指向这个而不是 emacs.exe，否则会多弹一个黑窗口。任务栏固定图标也一样。
emacsclient.exe控制台程序调用方本身是控制台程序时用它，这样 Emacs 的消息会出现在同一个命令行窗口里。
emacsclientw.exeWindows GUI 程序调用方是图形界面程序时用它。用 emacsclient.exe 的话，从 GUI 里调它会凭空弹出一个命令行窗口。典型场景：在资源管理器里右键文件 →「打开方式」→ 选 emacsclientw.exe。

如果调用 emacsclient 时 Emacs 还没跑起来，加 --alternate-editor=（简写 -a）参数可以保证「无论如何都给返回一个编辑器」。

一条 Windows 特有的硬限制，手册写得很清楚：由于 Windows 的限制，Emacs 不能在同一会话里同时拥有图形窗口和文本窗口；也不能在多于一个「命令提示符」窗口里打开文本窗口，因为每个 Windows 程序同时只能有一个控制台。实际后果是：你用 emacsclient -c 时，如果 server 跑在文本模式下，新窗口只会出现在它当初启动的那个命令提示符里，不会新开；反过来 emacsclient -t 在 server 是图形会话时开图形窗口，server 是文本会话时开文本窗口。

换行符：Windows 原生构建最实际的一个坑。Emacs 用单个换行符分隔行，而 Windows 文件通常用「回车 + 换行」两个字符。所以 Emacs 读文件时会把 CRLF 转成 LF，写回时再转成 CRLF。有一个后果值得记住：Emacs 里报告的字符位置和操作系统看到的文件大小对不上，因为转换在中间发生了。Emacs 会在模式行（mode line，就是显示文件名和模式的那一行）上用两种方式提示你：如果当前缓冲区在做 CRLF 转换，会在编码系统缩写后面加一个反斜杠 \；如果没做转换，会显示 (Unix)。

想手动指定，就用编码系统命令（两处都要看）：

C-x RET c unix RET      # 然后 C-x C-f 打开文件：不转换换行符
C-x RET f unix RET      # 然后 C-x C-s 保存：按 Unix 换行格式写出

「我打开一个 DOS 文件，按 unix 格式保存」这个组合就等价于 dos2unix；反过来（打开 unix 文件、按 dos 格式保存）等价于 unix2dos。

如果你通过网络访问的是 Linux 文件系统（NFS、Samba 之类），Emacs 应该完全不做换行符转换——哪怕你新建文件也不转。手册给的正式办法是调用函数 w32-add-untranslated-filesystem：

;; init.el：把网络盘标记成「不转换换行符」
(w32-add-untranslated-filesystem "Z:")
;; 也可以只标某个子目录：
(w32-add-untranslated-filesystem "Z:\\foo")
;; 反向操作：
(w32-remove-untranslated-filesystem "Z:")

手册建议这段代码放在 init.el 里，或者放在 site-start.el 里让全站用户都受益。

Cygwin：手册里一个字都没提

这一条我做了穷尽检查，可以给出确定答案：在 Emacs 32 的完整参考手册 emacs.info 里，搜索 cygwin、msys、mingw 三个词，命中数是 0。手册的平台附录只有四个：macOS/GNUstep、Haiku、Android、Microsoft Windows/MS-DOS（Windows 与 MS-DOS 合在一个附录里），外加一个讲 X 资源的附录。但要说公道话：Cygwin 并非完全没人管——它有自己的一节，写在另一本手册《GNU Emacs 常见问题》（emacs-faq）里，另外文档 FAQ 也有涉及。只是这些内容不在你手边那本 emacs.info 中，键位、默认行为、平台差异这些日常要查的东西它一概不讲。

这不代表 Cygwin 上跑不了 Emacs（社区里肯定有人在维护打包），但它意味着：你走上的是没有官方文档的路。遇到问题时你不能指望手册；而且 Windows 平台特有的那些坑（上面的 CRLF 转换、四个可执行文件的区别、控制台限制）在 Cygwin 上要么不存在、要么表现完全不同——因为 Cygwin 提供的是 POSIX 层，它有自己的路径语义和换行符处理方式。

技巧

一个能省你半天时间的习惯：在写任何平台相关的配置之前，先问 Emacs 它自己是什么。这里有一个非常多人踩的坑，先说清楚：system-type、emacs-version、version-number 这些名字里，只有 emacs-version 同时也是命令，其余都是变量——用 M- x 调它们只会得到 Invalid command。本机实测：(commandp 'system-type) 与 (commandp 'version-number) 都是 nil；而 version-number 这个名字在 Emacs 32 里连变量都不存在（(boundp 'version-number) 返回 nil），老文章里教人用它做版本判断的代码今天会直接报 void-variable。显示变量的正确姿势是按 M-（eval-expression，回显区会提示 Eval: 的那个键）：

M-: (message system-type)     ; 回显 gnu/linux / darwin / windows-nt / android
M-: (message emacs-version)   ; 回显 "32.0.50"（字符串，不是列表）
M-: (message emacs-major-version)  ; 回显 32（要数字时用这个）

M-x emacs-version RET        ; 这个是真命令，回显 GNU Emacs 32.0.50 (build 1, …, GTK+ …)

然后用它们写判断，而不是靠「我记得我是 Windows」。注意 system-type 的值是符号（gnu/linux），不是字符串，所以下面的判断要用 memq 而不是 string=：

;; 只在原生 Windows 上生效
(when (memq system-type '(windows-nt ms-dos cygwin))
  (w32-add-untranslated-filesystem "Z:"))

;; 只在 Emacs 30 及以后生效
(when (>= emacs-major-version 30)
  (setq-default tab-width 4))

这段代码在 Termux、WSL、原生 Windows 上都跑得对，而且不需要你手动维护任何「我是哪个平台」的变量。

练习 9　你装了 WSL，Emacs 也跑起来了。现在要决定项目代码放哪。微软官方文档明确建议放哪儿？

练习 10　你在 Windows 上要给 Emacs 做一个桌面快捷方式。按 Emacs 手册，「目标」应该填哪个程序？为什么不是另一个？

应该填 runemacs.exe 的完整绝对路径，而不是 emacs.exe。手册的理由是：emacs.exe 在 Windows 看来是控制台程序，用它做目标会额外弹出一个控制台窗口；runemacs.exe 会把这个窗口隐藏起来。手册对任务栏固定图标也给了同样的建议。另外快捷方式属性里的「起始位置」（Start in）决定 Emacs 在哪个目录启动，你可以在那里指定工作目录。

练习 11　你用 Windows 原生版 Emacs 打开了一个从 Linux 上拷过来的 foobar.txt，里面有 Windows 的 CRLF 换行，想让 Emacs 不做换行符转换地打开它。按哪一组键？

Cx RET c RET，然后输入 unix 再回车，接着才按 Cx Cf 打开文件。手册给的例子就是 C-x <RET> c unix <RET> C-x C-f foobar.txt。这样做 Emacs 不转换 EOL，如果文件里真的有 CRLF，屏幕上会显示成 ^M。反向操作（打开时转换、保存时写 unix 格式）用 Cx RET f RET unix RET 然后 Cx Cs，这等价于 dos2unix。

练习 12　有人推荐你在 Cygwin 里装 Emacs，说「这样路径和 Linux 一样，最省心」。这个说法有什么问题？

问题在于：Cygwin 不是 Emacs 参考手册覆盖的平台。我在 Emacs 32 的完整参考手册 emacs.info 里搜 cygwin、msys、mingw，命中数是 0；它的平台附录只有 macOS/GNUstep、Haiku、Android、Microsoft Windows/MS-DOS 四个。所以「省心」的前提不成立——遇到问题你查不到官方参考文档，而且 Windows 原生构建那些特有的坑（CRLF 转换、四个可执行文件的区别、同会话不能混用图形与文本窗口）在 Cygwin 上要么不存在要么表现不同，因为 Cygwin 自己提供 POSIX 层。公平地说，Cygwin 在《GNU Emacs 常见问题》（emacs-faq）里是有专门一节的，但那是另一本手册、只覆盖安装与常见故障，键位与默认行为这些日常要查的东西仍然无从查证。真正省心的做法是 WSL。

15.5 无鼠标与可访问性

Emacs 在设计上就是键盘优先的编辑器。这一节回答三个问题：不用鼠标会不会少很多东西、手不听话（运动障碍）该怎么配、以及用屏幕阅读器（screen reader，把屏幕内容朗读出来的软件）行不行。第三个问题的答案可能出乎你意料，我放在最后。

鼠标能做的每一件事，都有一个按键

Emacs 手册第 23.1 节「Mouse Commands for Editing」把鼠标操作列得很全：mouse-1（mouse-set-point，把光标移到点的地方）、拖动 mouse-1（mouse-set-region，选区并把文本放进 primary selection）、Shift mouse-1（调整已有选区）、mouse-2（mouse-yank-primary，把 primary selection 粘到点的地方）、mouse-3（mouse-save-then-kill，把选区存进 kill ring，再点一次就删掉）。这五个命令每一个都有等价的纯键盘做法。

鼠标操作命令纯键盘等价

拖动选一段 mouse-set-region 先 CSPACE（set-mark-command）放好标记，再移动光标；要整个缓冲区就 Cx h（mark-whole-buffer）。

选中一段并删掉 mouse-3 点两次 Cw（kill-region）。
点另一处同时扩选并复制 mouse-3 点一下 CMw（append-next-kill）。
中键粘贴 mouse-yank-primary Cy（yank）粘 kill ring；My（yank-pop）轮换 kill ring 里的多条。至于 primary selection（X11 那种「选中即复制」），Emacs 核心里没有对应的粘贴命令：本机实测 (fboundp 'yunk-primary-selection) 返回 nil，我也查过上游 Emacs 32 开发版的 lisp/simple.el，整个文件里没有这个函数定义。既然它既不存在也不是命令，用 M- x 前缀去调它同样只会得到 Invalid command。想用 primary selection 的实际办法是在 X11 终端里按住中键点一下；纯键盘路线就用 kill ring（Mw 复制、Cy 粘贴）。
滚轮 mouse-wheel-mode Cv / Mv（本机实测分别绑在 scroll-up-command / scroll-down-command 上；scroll-up / scroll-down 是同名的变量，别写混）。

还有两个纯键盘姿势在只有键盘的设备上极其重要：用 Cu（universal-argument）当「数字前缀」——Cu Cu f 就是「往前移两行」；用 Mx（execute-extended-command）按名字调任何命令，包括那些默认没有键位的、以及你临时才想起来的。

Cg：一个键就是全部的保险

Cg 值得单独一节，因为它的工作方式决定了你敢不敢放手去试。下面是 Emacs 32.0.50 手册「Quitting」一节的原文要点。

Cg works by setting the variable quit-flag to t the instant Cg is typed; Emacs Lisp checks this variable frequently, and quits if it is non-nil.

There are some situations where you cannot quit. When Emacs is waiting for the operating system to do something, quitting is impossible unless special pains are taken for the particular system call within Emacs where the waiting occurs. […] In one very common case—waiting for file input or output using NFS—Emacs itself knows how to quit, but many NFS implementations simply do not allow user programs to stop waiting for NFS when the NFS server is hung.

这三个机制要分清楚，它们回答三个不同的问题：

  • Cg（keyboard-quit，我实测绑定成立）：按下的瞬间就把 quit-flag 置 t，Elisp 在各个检查点发现它就中止。它只能掐断「Emacs 自己在跑的东西」，掐不断「Emacs 在等操作系统」的东西。NFS 挂死就是手册点名的那一类。
  • Cg 连按两下：这是紧急逃生（emergency escape），只在文本终端上有效。它不是 Emacs 的命令，而是终端层面的逃生阀：Emacs 卡得来不及处理第一个 Cg 时，第二个直接把你从 Emacs 里拽出来。手册说：恢复之后 Emacs 会问两个问题——「Auto-save?（y or n）」和「Abort (and dump core)?（y or n）」。答 y 就立刻把开了自动保存的缓冲区存盘；答 n 就能带着原状态继续；两个都答 n 的话，若 Emacs 其实只是慢而非卡死，会回到原来的状态。手册还提醒：这个功能只在文本终端上存在，图形界面下你可以直接用鼠标切走或者杀进程。MS-DOS 上要用两次 C<Break> 代替 Cg。
  • C]（abort-recursive-edit，实测存在）和 M- x top-level（实测存在）：用来逃出「多层嵌套的提问」——比如你在搜索里又打开了另一个搜索。C] 一次退一层，top-level 一次退所有层。它们的区别在手册里说得很清楚：C] 是普通按键，只在 Emacs 准备好接受命令时才生效，所以它停不了一个正在运行的命令；而 Cg 是那种「一按就置标志」的东西，能打断运行中的命令。

还有第四个：ESC ESC ESC（keyboard-escape-quit，实测存在）。它的定位是「像 PC 程序里 ESC 那样退出」：能取消前缀参数、清除选区、退出查询替换、退出 minibuffer（Emacs 底部那个等你输入的提示行）、退出 Cx 1 这种切窗口的瞬态状态。但它同样停不了一个正在运行的命令。

技巧

如果你手指够不到某个键、或者某些按键在移动端键盘上很难同时按，Emacs 允许你把「功能键」重新绑到「好按的键」上。最有用的三条：

;; 把函数键改成 Caps Lock / 无修饰键，笔记本小键盘上很好按
;; （本机实测 <f5>/<f6>/<f7> 默认都没有绑定，所以覆盖它们是安全的）
(global-set-key (kbd "<f5>") 'isearch-forward)
(global-set-key (kbd "<f6>") 'isearch-backward)
(global-set-key (kbd "<f7>") 'goto-line)

;; 把不常用的功能挪到 Meta 上：
;; Meta = Alt，或 Esc 键（按一次 Meta 前缀）。Emacs 允许 ESC ESC 当 Meta 用，
;; 这在只有一层修饰键的移动端键盘上很关键。
;; 代价要知道：M-s 默认是一个前缀键（. 跟 h 是 highlight-symbol-at-point，
;; f / u / n 属于 hi-lock 一族），M-/ 默认是 dabbrev-expand。
;; 覆盖之后这两族功能就没了；如果你在用它们，就把下面的键换成 C-c 之类。
(global-set-key (kbd "M-s") 'query-replace)
(global-set-key (kbd "M-/") 'undo)

;; 查询当前某个键到底绑了什么（永不过时，问的是当前状态）
(global-set-key (kbd "C-h k") 'describe-key)

最后那句 Ch k 是这一整节的钥匙：你改完键位之后，Emacs 能告诉你「现在的」绑定表是什么，而不需要你回头去翻文档。

屏幕阅读器：Emacs 核心目前不提供

这一节我必须给一个明确的、可能让人失望但诚实的答案。我做了三项检查，结论成立，但其中一项的原始数字和我第一版写的不一样，这里如实修正：

  1. 在随 Emacs 32.0.50 安装的全部 etc/NEWS、etc/NEWS.31、etc/NEWS.30 里搜索 screen reader 与 screen-reader，命中数是 0。
  2. 在整棵 lisp/ 源码树里不区分大小写地搜索 screen reader，只有一个文件命中——lisp/net/shr.el，那是把网页转成 Emacs 能读的文本的工具，跟可访问性无关。
  3. （修正）在完整的 32.0.50 手册 emacs.info 里搜索 screen reader，不是 0，而是 3 处命中——全部集中在 Windows 附录讲 w32-use-visible-system-caret 的那一段。原文说的是：没有屏幕阅读器软件在用时该变量默认为 nil，Emacs 画自己的光标；设成非 nil 就改用系统光标显示位置，「这方便屏幕阅读器软件使用」，而且 Emacs 检测到这类软件时会自动设成非 nil。这仍然是「让屏幕阅读器能读懂光标位置」，不是 Emacs 提供了屏幕阅读器接口——但我原来写「手册里命中 0」是错的，这里更正。另外手册里 “Accessibility” 有十来处命中，全都与残障无关：那是 Emacs 手册 “Information about Files” 下面的 “Testing Accessibility” 节点（测试一个文件是否可读/可写，Elisp 手册里也有同一个节点）；而 “accessible portion” 指的是窄化（narrowing）之后缓冲区里可见的那一段，也是完全不同的概念，不要被搜索结果误导。
要点

结论不变：截至 Emacs 32.0.50，GNU Emacs 核心没有内置的屏幕阅读器接口。唯一的内置相关物是上面那个 w32-use-visible-system-caret（Windows 专用，且是自动检测开启的，你一般不用管）。这不意味着盲人用户用不了 Emacs——有一条非常成熟的第三方路径，只是它不在核心里。Emacspeak（作者 T. V. Raman；由公司 Emacspeak Inc 运营，该公司在其官网上自我标注的股票代码是 NASDOG: ESPK——注意这是公司名与代号，不是 Emacspeak 的「版本代号」，它自己的版本代号是 DreamDog 那一串。官方网站 emacspeak.sourceforge.net，源码在 github.com/tvraman/emacspeak，这个仓库地址我在它官网上核对过）是一个「完整的音频桌面」——我写稿时它的首页公告是 Emacspeak 60.0（代号 DreamDog），仓库里有一个标准的 Makefile。这是第三方项目，不是 Emacs 的一部分，它的安装步骤、语音合成器配置、覆盖范围都需要你自己去它的官方手册里查；我没有在本机安装它，也没有验证过它在 Emacs 32 上的兼容性，所以本章不给它的安装命令——给了你也无法信任。

所以，如果你依赖屏幕阅读器，务实的选择有三个，按我的推荐顺序：

  1. 把 Emacs 放进一个屏幕阅读器已经读得懂的终端里。Emacs 内置了三个终端模拟器，它们启动的都是一个真的终端程序：M- x term（内部 term，我实测 (fboundp 'term) 为 t）、M- x shell（调用系统 shell）、M- x eshell（Emacs 自带的、用 Elisp 实现的 shell）。在 term 里敲 emacs，你就得到「终端里的 Emacs」——GNOME 的 Orca、Android 的 TalkBack、macOS 的 VoiceOver 读这个终端的输出通常比读 Emacs 的图形界面可靠得多，因为终端的输出就是纯文本。代价是：图形功能全没了（没有窗口分割的鼠标操作、没有图片、没有鼠标滚轮），而且多了一层终端的按键转义。
  2. 试 Emacspeak。如果你的工作真的离不开 Emacs 的功能又需要语音，这是唯一成熟的组合。先在你能接受的环境里试，不要一上来就把它配进日常配置文件。
  3. 接受现实，换一个工具。如果 Emacs 对你的可访问性需求来说边际收益不足，用一个本身就支持屏幕阅读器的编辑器（VS Code 有成熟的屏幕阅读器支持、Neovim 可以配朗读插件）可能更省你的生命。这不是失败，这是把时间花在你真正要编辑的东西上。
技巧

无论你用不用屏幕阅读器，把 Emacs 变成一个「会说话」的编辑器都值得做，成本只有几行配置。这几行全部是我在本机 Emacs 32.0.50 上验证过命令存在的：

;;; init.el：让 Emacs 在你停下不动时自动报出上下文
;;; 依赖：无，纯内置。

;;; 1. 光标停住 1.2 秒后，在回显区显示「这里是什么模式、这一行有多长」
;;;    对应命令是 which-function-mode（把 which-function-mode 设为 t 即可）
(global-set-key (kbd "<f5>") 'which-function-mode)

;;; 2. 说话：Emacs 有内置的 speak-region / read-from-minibuffer，
;;;    但它们依赖系统语音。Windows 上 Emacs 能直接调 SAPI（见系统自带语音），
;;;    Linux 上通常需要 espeak 之类的引擎。这条是经验性说法，各平台差异很大，
;;;    建议先 M-x 试 speak-region 看你的 Emacs 能不能出声。

更实用的是把「我现在在哪个缓冲区、什么模式、有没有未保存改动」这条信息打出来看而不是猜：Cx Cb 列出所有缓冲区并显示每个缓冲区的保存状态；Ch m（describe-mode）告诉你当前模式的一切——本机实测 Ch m 确实绑在 describe-mode 上。这两条在任何情况下都该记住，它们比屏幕阅读器更靠得住。

练习 13　你在终端里跑 Emacs，它彻底卡住了：光标不动，回显区不刷新。第一下 Cg 按下去没反应。该怎么办？这个功能在图形界面的 Emacs 里存在吗？

连按第二下 Cg，触发「紧急逃生」（emergency escape）。手册的解释是：Cg 一按就把变量 quit-flag 置 t，Elisp 在检查点发现它才中止；正常情况下 Emacs 处理得很快、第二个不会触发紧急逃生，但真卡住时第二个会把你直接拽回 shell。恢复后 Emacs 会问「Auto-save? (y or n)」和「Abort (and dump core)? (y or n)」，答 n n 能带着原状态回去。但这个功能只在文本终端上存在，手册明确说图形界面上你可以直接用鼠标切走或杀进程。（MS-DOS 上是连按两次 C<Break>。）

练习 14　你在「查询替换」里又打开了一层提示（递归编辑），想一次退出去。按 C] 和 M- x top-level 各会退几层？它们和 Cg 的关键差别是什么？

C]（abort-recursive-edit）一次退一层，M- x top-level 一次把所有层都退掉（并且会关掉 minibuffer）。关键差别是：C] 和 top-level 都是「普通命令」，只在 Emacs 准备好接受下一个命令时才生效，所以它们停不了一个正在运行的命令；Cg 是一按就置 quit-flag，能打断运行中的命令。手册还把两者和 ESC ESC ESC（keyboard-escape-quit）放在一起对比，结论一致。

练习 15　一个视障用户问：Emacs 32 自带屏幕阅读器支持吗？依据是什么？如果没有，可行的替代路径是什么？

不带。我在 Emacs 32.0.50 上查了三处：全部 NEWS 文件里 screen reader 命中 0 次；整棵 lisp/ 树里只有 lisp/net/shr.el 提到它（那是网页转文本工具，无关）；手册里则有 3 处 screen reader，但全部出现在 Windows 附录讲 w32-use-visible-system-caret 的段落里，说的是「让 Emacs 用系统光标显示位置，这方便屏幕阅读器软件使用，检测到这类软件时会自动开启」——这是「让屏幕阅读器读得懂光标」，不是 Emacs 提供了屏幕阅读器接口。（另外手册里 “Accessibility” 的十来处命中全是文件权限意义上的 “Testing Accessibility”，与残障无关；“accessible portion” 指窄化后可见的缓冲区部分。都与本题无关。）可行路径有三条：①用 M- x term 开一个真终端再敲 emacs，让终端的屏幕阅读器（Orca / TalkBack / VoiceOver）去读；②装第三方项目 Emacspeak（官网 emacspeak.sourceforge.net，源码 github.com/tvraman/emacspeak，写稿时最新公告是 60.0 DreamDog），但我没有验证它在 Emacs 32 上的兼容性；③如果边际收益不足，换一个原生支持屏幕阅读器的编辑器。

15.6 性能与大文件

这一节讲三类不同的「慢」：打开一个大文件慢、打开一个有很多超长行的文件慢、远程编辑一切操作都慢。它们的成因和对策完全不同，混在一起讲就会得出「Emacs 处理大文件就是慢」这种没用的结论。

打开大文件：Emacs 会先问你一句

Emacs 32.0.50 手册「Visiting」一节里有这么一段，我原样引用关键部分：

If you try to visit a file larger than large-file-warning-threshold (the default is 10000000, which is about 10 megabytes), Emacs asks you for confirmation first. You can answer y to proceed with visiting the file or l to visit the file literally (see below). Visiting large files literally speeds up navigation and editing of such files, because various potentially-expensive features are turned off.

本机实测：(boundp 'large-file-warning-threshold) 为 t，large-file-warning-threshold 的值是 10000000。Emacs 源码里它定义在 lisp/files.el，标记 :version "22.1"——也就是说这个阈值从 Emacs 22.1 用到今天，中间没改过语义。

那个提问的三个选项，源码（files.el 里的 files--ask-user-about-large-file-help-text）给的说法是：y 照常打开；n 放弃；l（小写字母 l，不是数字 1）「literally 地打开」——不做任何格式或字符编码转换，用 Fundamental 模式，不加载任何可能昂贵的功能。

技巧

遇到提示时，拿不准就按 l。l 是完全无损的保险：它只是关掉高亮和主模式，你的文本一个字都不会少。你在 Fundamental 模式里照样能编辑、能保存。确认内容没问题之后，随时按 M- 再输入 (set-auto-mode) 换成正确的主模式——这里必须用 M- 求值而不是 M- x：本机实测 set-auto-mode 没有 interactive 声明，M- x 调它只会得到 Invalid command。反过来，按 y 打开一个几百 MB 的日志文件然后发现 Emacs 动不了，才是真正浪费时间。

还有一个硬上限要记住：手册说「Emacs cannot visit files that are larger than the maximum Emacs buffer size, which is limited by the amount of memory Emacs can allocate and by the integers that Emacs can represent」。真超了会看到「maximum buffer size has been exceeded」的错误。这条限制是物理性的，配置改不动它。缓冲区理论最大值由几个整数宽度的因子相乘决定，在 64 位机器上是几百 MB 到 GB 量级；具体数值依平台而异，我在这里不做确切承诺，你要知道自己机器的数可以运行 (message "%s" (number-to-string most-positive-fixnum)) 再自己算，或者直接实测打开一个大文件看结果。

一条必须纠正的流传很广的错误：large-file-mode 不存在

中文互联网上关于「Emacs 打开大文件」的文章，十篇里有九篇会叫你设置 large-file-mode。这个变量在今天的 Emacs 里查不到。我在本机 Emacs 32.0.50 上做了四项检查，每一项都返回「不存在」：

检查方式结果
(boundp 'large-file-mode)nil
在整棵 lisp/ 源码树里 grep large-file（只看 .el 源文件）只命中 large-file-warning-threshold 和几个 files--ask-user-about-large-file* 函数，没有 large-file-mode 的定义
在 emacs 可执行文件的字符串表里搜 debug-init 那种精确符号名同样方法验证 large-file-mode：不存在
在完整手册 emacs.info 里搜 large-file（不区分大小写）只有 2 处，都是 large-file-warning-threshold

同样的结论适用于另外两个你可能见过的名字：large-file-data-warning-threshold（(boundp ...) 返回 nil，源码树里没有）、so-long-lines 和 so-long-line-threshold（同样 nil，源码树里没有）。

要点

我没能核实它们是哪一版被删的，这里如实说明。我确实去查了：拉取 Emacs 官方 Git 镜像 github.com/emacs-mirror/emacs 的 emacs-29、emacs-30、emacs-31 三个分支的 lisp/files.el 与 lisp/so-long.el，发现 large-file-mode 在这三个分支里也已经不存在，而 so-long-lines / so-long-line-threshold 在 so-long.el 里也不存在；同镜像上 emacs-27、emacs-28 分支的对应文件返回 404，git.savannah.gnu.org 从我这里连接超时，所以更早的版本我查不到。结论可靠（「今天的 Emacs 里没有这几个变量」），但「哪个版本删的」我不编。你在 2026 年要做的只有一件事：写进 init.el 之前先问 Emacs。

顺带说明 Emacs 的行号也有一个大文件相关的开关，手册的说法是：如果缓冲区非常大（超过 line-number-display-limit 的值），Emacs 不会计算行号，因为太慢，模式行上就不显示行号；另外如果点附近的行太长，Emacs 也不显示行号，阈值是 line-number-display-limit-width。本机实测：line-number-display-limit 的值是 nil（即默认不设上限），line-number-display-limit-width 的值是 200（字符）。所以在现代 Emacs 里，行号消失更可能是「你的行太宽」而不是「文件太大」，而把 line-number-display-limit 设成 nil 是解除限制的正规做法。

真正的性能杀手是超长行，不是大文件

这一节的判断和很多人的直觉相反，我把它说清楚：一个 50 MB、每行 80 字符的日志文件，Emacs 处理得挺好；一个 2 MB、但有几行长 50000 字符的压缩过的代码文件，Emacs 会卡住。原因是各种高亮和缩进算法都是按行工作的，一行越长代价越大。

Emacs 为此准备了一个专门的机制，叫 so-long（短就是「太长了」）——它是 Emacs 内置的，不是第三方包，源码就在 lisp/so-long.el，作者与维护者是 Phil Sainty，项目主页 savannah.nongnu.org/projects/so-long。我核对过本机这份文件的版本是 1.1.2、版权年份到 2026，并且和上游 master 分支的同一文件内容一致——也就是说它是跟着 Emacs 核心一起维护的。

本机实测的默认值（(require 'so-long) 之后读取）：

变量默认值意思
so-long-threshold10000一行的字符数超过这个值就算「太长」。
so-long-max-lines500整个文件里超过 so-long-threshold 的行数超过这个数就触发。光有一两行长行不会触发。
so-long-actionso-long-mode触发时默认做一件事：把主模式换成 so-long-mode（一种专门为「行很长」优化的基础模式）。
so-long-skip-leading-commentst跳过开头的注释再判断，避免把「注释块里有长行」的文件误伤。

它的工作方式是：检测到触发条件后，把那些昂贵的主模式和次模式暂时换掉，并在模式行上标一个 So Long 标签提醒你。恢复很简单：M- x so-long-revert。本机实测有个前提要说清楚：直接起一个干净的 Emacs（emacs --batch -Q）时，(fboundp 'so-long-revert) 返回 nil，M- x 也找不到它——因为 so-long 这个库还没被加载。执行 (require 'so-long) 之后，它就变成一个正经的交互命令了（(commandp 'so-long-revert) 变成 t，interactive 形式是 "@"，即接受文本作为参数）。所以下面那份配置里的 (require 'so-long) 不是可有可无的，你按了 global-so-long-mode 就等于加载了这个库，之后 M- x so-long-revert 随时可用。

真正推荐的用法是全局打开自动检测，这样你永远不用手动管：

;;; init.el：全局启用超长行保护
;;; 依赖：无。so-long 是 Emacs 内置库。
(require 'so-long)

;; 自动生效：打开文件时检测，触发就自动切换
(global-so-long-mode 1)

;; 想更激进一点：把「一行多长算长」的门槛调低
(setq so-long-threshold 2000)

;; 想更保守一点（只在极端情况才切模式）：
;; (setq so-long-threshold 50000)

;; 触发时不要换主模式，只关掉次模式（这样语法高亮还在，
;; 只是慢的那些东西被关掉了）：
;; (setq so-long-action 'so-long-minor-mode)

;; 被切走之后怎么恢复：
;;   M-x so-long-revert        （撤销这次 so-long）
;;   M-x so-long               （手动强制触发一次检查）

代价必须说清楚：so-long-mode 不是「更快的原模式」，它是一个故意牺牲功能的模式——语法高亮没了、语言相关的缩进没了、自动配对括号没了。所以正确的定位是：压缩过的代码、巨大的 JSON、自动生成的 API 客户端、数据导出——这些你本来也不该在里面正经编辑的文件，用 so-long；正常代码不该触发。如果你发现它在自己写的代码上频繁触发，说明 so-long-threshold 对你太小了，或者你的项目里有真正的超长行需要处理。

tree-sitter 模式的大文件陷阱

这一条是 2025 年以后 Emacs 特有的新坑，和上面的历史包袱无关。手册「Visiting」一节写着：如果你打开的文件其主模式使用了 tree-sitter 解析库，而文件大小超过 treesit-max-buffer-size，Emacs 会给出警告；默认 64 位 Emacs 是 40 MB、32 位 Emacs 是 15 MB。手册给出的原因是：一个典型的 tree-sitter 解析器需要的内存大约是它所解析文本的 10 倍。

本机实测：执行 (require 'treesit) 之后 treesit-max-buffer-size 的值是 41943040（正好 40 MiB），和手册里说的 64 位默认值吻合。

这对你意味着什么？如果你在 Emacs 32 里编辑 JSON、Markdown、Python、TypeScript 之类的文件，打开一个几十 MB 的数据文件会直接触发警告而不是被硬塞进内存。这里要说清楚「默认走 tree-sitter」到底是怎么发生的，因为机制不是「auto-mode-alist 里直接写着 tree-sitter 模式」，而是两层：第一层，auto-mode-alist 里仍然是老模式的名字（本机实测 \\.json\\' 对应 js-json-mode）；第二层，Emacs 32 有一张重映射表 treesit-major-mode-remap-alist，我读了它，里面有 25 条，js-json-mode → json-ts-mode、python-mode → python-ts-mode、typescript-mode → typescript-ts-mode、markdown-mode → markdown-ts-mode 都在里面——只要对应的 tree-sitter 解析器装了，老模式就被换成对应的 *-ts-mode。例外是 Markdown：它比较特殊，\\.md\\' 在 auto-mode-alist 里直接就是 markdown-ts-mode-maybe（本机实测），不需要走重映射。另一个我实测到的事实：\\.el\\' 现在对应的是 emacs-lisp-mode（不是老文章里常写的 lisp-mode）。这也是为什么你在手机上（Termux 的 Emacs 是 --with-tree-sitter 编译的）打开大 Markdown 文件会特别卡：解析器的内存开销被 10 倍放大了。

高亮为什么有时候不卡、有时候卡

手册对这件事有完整解释，叫 JIT 锁（JIT Lock）：

Fontifying very large buffers can take a long time. To avoid large delays when a file is visited, Emacs initially fontifies only the visible portion of a buffer. As you scroll through the buffer, each portion that becomes visible is fontified as soon as it is displayed; this type of Font Lock is called "Just-In-Time" (or "JIT") Lock. You can control how JIT Lock behaves, including telling it to perform fontification while idle, by customizing variables in the customization group jit-lock.

翻译过来：Emacs 本来就不会给整个文件上色，只给屏幕上看得见的那部分上色，滚到哪儿才给哪儿上。所以「大文件卡顿」往往不是「打开时卡」，而是「你按住 Cn/Cp 快速滚动时卡」——因为新进入屏幕的那部分要现上色。如果你让它在空闲时预先上色，滚动就顺了，代价是空闲时它在后台干活。相关选项在 jit-lock 这个定制组里，可以用 M- x customize-group RET jit-lock RET 打开。本机实测：jit-lock-mode 默认值是 nil。

远程编辑为什么每一下都慢

Tramp（本书第十章讲的远程编辑）的延迟模型很简单：Emacs 的一个「本地」动作在远程会变成一次子进程往返。你按一下 Cn，Emacs 可能需要向远端发一次请求去读那一行的内容；你按 CM f 跳定义，Emacs 要去远端搜文件；revert-buffer 要从远端重读整个文件。在低延迟网络上感觉还行，跨越手机热点或高延迟链路就会变成每一下都「顿」一下。

本机实测的三个默认值：tramp-default-method 是 "scp"，tramp-verbose 是 3，tramp-connection-timeout 是 60（秒）。

能立刻改善体感的两个改动：

;;; init.el：Tramp 调优
;;; 依赖：无，tramp 是 Emacs 内置库。

;; 1. 默认用 ssh 而不是 scp。
;;    scp 是「拷贝文件」的协议，编辑一个文件时你并不需要拷贝，
;;    ssh 是交互式会话，连接建立后所有操作都走同一条通道。
;;    延迟敏感的场景（手机热点、公司 VPN）差别最明显。
(setq tramp-default-method "ssh")

;; 2. 把连接超时从 60 秒压到 20 秒：
;;    移动网络切换（4G ↔ Wi-Fi）时你会立刻知道断了，
;;    而不是干等一分钟。
(setq tramp-connection-timeout 20)

;; 3. 卡住时打开详细日志：把 tramp-verbose 调到 6 以上，
;;    再连一次，Emacs 会把每一次 SSH 调用和它的耗时打进 *Messages*。
;;    这就是排查「到底哪一步慢」的正路。查完记得调回 3。
;; (setq tramp-verbose 6)

关于「在远端编译」，Emacs 有一个内置开关 async-byte-compilation，让它在后台编译而不是卡住界面。但这里有一个必须说明的事实：这个功能已经不在 Emacs 核心里了。我在本机 Emacs 32.0.50 的 lisp/ 目录里找不到 async.el，(require 'async) 直接报 Cannot open load file。它现在是一个独立的包：我查过 GNU ELPA 的包索引（elpa.gnu.org/packages/），async 在上面，描述是「Asynchronous processing in Emacs」，写稿时的版本是 1.9.9，发布于 2024-08-21，排名 90%。GNU ELPA 是 Emacs 的两个默认包仓库之一（另一个是 NonGNU ELPA），所以装它不需要额外配置仓库地址：

M-x package-install RET async RET

我没有在本机验证 async-byte-compilation 的具体默认值，因为这台机器上装不了 async。装好之后用 Ch v RET async-byte-compilation RET 自己看一眼当前值。

原生编译（native-comp）：到底启用了没有

这一段有一处特别容易被说错，我按 NEWS 的原文和本机实测分别讲清楚。

Emacs 30.1 的 NEWS 原文（我读的是随 Emacs 32.0.50 安装的 etc/NEWS.30）：

Native compilation is now enabled by default. configure will enable the Emacs Lisp native compiler, so long as libgccjit is present and functional on the system. To disable native compilation, configure Emacs with the option: ./configure --with-native-compilation=no

请注意这句话说的是 configure 阶段：「configure 会启用原生编译器」。本机实测证实了这一点：(native-comp-available-p) 返回 t，也就是说这台 Emacs 32.0.50 确实带了这个编译器。但「带了这个编译器」和「你的 Elisp 已经被编译过」是两件事——package-native-compile 这个选项的文档字符串（我读的是 lisp/emacs-lisp/package.el 里 :version "28.1" 的那个定义）说得很清楚：

Non-nil means to natively compile packages as part of their installation. […] If this option is nil, packages will be natively compiled when they are loaded for the first time. This option does not have any effect if Emacs was not built with native compilation support.

也就是说：package-native-compile 默认是 nil（实测确认），此时包是在第一次被加载时异步做原生编译，而不是在安装时。你可以选择不改（第一次慢一点，之后就走编译好的代码），也可以设成 t 让安装完就编好（安装变慢，但第一次加载不卡）。注意它带 :risky t 标记，Customize 里会警告你。

本机实测的另一个值：native-comp-jit-compilation 的默认值是 nil。这个选项控制的是「即时编译」（JIT，用 libgccjit 把函数在运行时编译并缓存），关着就是用传统的预编译产物。老文章里「打开 JIT 能提速」的说法在今天的默认配置下不成立。

技巧

移动端和笔记本用户请注意 Emacs 31 新增的一个选项，它就是为这件事设计的。etc/NEWS.31 里的原文：

New user option native-comp-async-on-battery-power. Customize this to nil to disable starting new asynchronous native compilations while AC power is not connected.

翻译：不在插着电源时，别启动新的异步原生编译。在手机上这几乎是必配的一条——否则你在等电的时候，后台编译会把电量吃掉。配法：

;; init.el 或 early-init.el：只在插电时才让原生编译跑起来
(setq native-comp-async-on-battery-power nil)

另外 etc/NEWS.31 还提到 Emacs 31 新增了函数 native-compile-directory，也就是「把一个目录整批原生编译」的入口。

进阶：原生编译的日志在哪、产物在哪、怎么让它说话

三条都来自随 Emacs 32.0.50 安装的 Elisp 手册（elisp.info）的「Native Compilation」一章，我逐条读过了：

  • 日志缓冲区叫 *Native-compile-Log*。手册说：原生编译产生的警告与错误「are normally recorded in the buffer called *Native-compile-Log*」，在交互式会话里它用一种特殊的 LIMPLE 模式（native-comp-limple-mode），这与 Fundamental 模式相同，只是把 font-lock 配好了。如果你的 init.el 或某个包在原生编译时报了警告但你什么都没看到，就是没去翻这个缓冲区。
  • 控制日志的是 native-comp-verbose，默认值是 0，也就是不记任何日志。手册逐级说明：设为 1 到 3 之间的值，会允许记录级别高于该值的消息。所以「编译报错了但我什么也没看到」不是 bug，是默认如此。调试时把它调到 3。
  • 非交互模式下，手册说消息「are usually displayed on the standard error stream of the terminal from which Emacs was invoked」——也就是打到标准错误流上。这意味着你在终端里跑 emacs --batch 编译出错时，错误出现在终端，不在 *Messages* 里。
  • 还有一个诊断细节：生成的伪 C 代码（pseudo-C code）会放在对应 .eln 文件的同一个目录里。这句话在手册里的直接用途是排错——你能顺着它找到编译产物。

一句话总结这一段的实践含义：原生编译的问题不会在启动时以「变量未定义」的形态炸给你，它只会让 Emacs 变慢或者悄悄地走回解释执行。所以遇到「我明明开了原生编译但感觉没区别」，第一件事是设 native-comp-verbose 到 3，然后去看 *Native-compile-Log*。

易错

高危：把「字节编译」当成性能开关乱开。常见的两种翻车方式：

一、每次启动都跑 byte-compile-dired 或 byte-recompile-directory 整个目录。第一次确实能变快（因为字节编译后的 .elc 加载比解释 .el 快），但代价是每次启动都要花几秒到几十秒重新编译，而且手机与机械硬盘上尤其明显。现代 Emacs 有原生编译，这条老优化的收益已经小得多。如果你真的需要，把它做成一个手动命令而不是放进启动流程。

二、把 load-prefer-newer 或 load-no-warn 之类跟字节编译相关的开关乱设。这类选项的含义往往和直觉相反（load-prefer-newer 是「源文件更新时优先用源文件」，load-no-warn 是「加载时不警告」），乱设的典型症状是「改了配置不生效」或者「每次启动刷一堆警告」。遇到这种症状，先把这些开关清掉，看问题是否消失，再一个一个加回来。

还有一个更朴素的提醒：性能问题九成不是 Emacs 的慢，是你在一个慢的介质上打开一个不该用 Emacs 打开的文件。与其折腾 Emacs 的选项，不如先问一句「我为什么需要在手机上编辑这个 200 MB 的日志」。

练习 16　你打开一个 300 MB 的日志文件，Emacs 弹出提示问你要不要打开。按 y 之后 Emacs 几乎不动。正确做法是什么？

按下 l（小写字母 l），即「literally 地打开」。Emacs 源码 lisp/files.el 里那个提示的说明是：l 会「visit the file literally, which means that Emacs will visit the file without doing any format or character code conversion and in Fundamental mode, without loading any potentially expensive features」。手册也补充说，这样能加快大文件的导航与编辑，因为各种可能昂贵的功能被关掉了。这一步不丢任何数据，之后还能按 M- 再输入 (set-auto-mode) 换回正确的主模式（注意不是 M- x——这个函数没有交互式声明）。另外注意缓冲区有硬上限，手册说超过 maximum buffer size 会直接报「maximum buffer size has been exceeded」，这是物理限制，调配置没用。

练习 17　你照着一篇 2019 年的博客在 init.el 里写了 (setq large-file-mode t)，启动时 Emacs 报 Symbol's value as variable is void: large-file-mode。这个变量到底是什么情况？

它在今天的 Emacs 里不存在。实测：Emacs 32.0.50 上 (boundp 'large-file-mode) 返回 nil；在整棵 lisp/ 源码树里 grep large-file 只命中 large-file-warning-threshold 和 files--ask-user-about-large-file* 这几个函数；完整手册 emacs.info 里 large-file 只出现 2 次，都是 large-file-warning-threshold。我另外查了 large-file-data-warning-threshold、so-long-lines、so-long-line-threshold，同样都不存在。我没能核实这几个变量具体是哪一版被删的（镜像的 27/28 分支取不到，savannah 连接超时），所以我不给版本号。你要做的只有一件事：写进 init.el 之前先问 Emacs 有没有这个东西——按 M- 然后输入 (boundp 'large-file-mode)，看到 nil 就说明它不存在。（注意 boundp 本身是个纯函数、不是命令，M- x 调不了；老文章里教你的「M- x checkdoc」之类也不对——checkdoc 检查的是文档格式，跟「这个符号存不存在」是两回事。）

练习 18　你的项目里有几个自动生成的巨型文件，每行几十万字符，打开后 Emacs 几乎不能动，但那些文件你从来不手写。Emacs 内置的对应机制是什么？它的两个关键默认值是多少？

是 so-long（Emacs 内置库，源码 lisp/so-long.el，作者 Phil Sainty，本机版本 1.1.2）。本机实测它的两个关键默认值：so-long-threshold = 10000（一行超过一万字符算长），so-long-max-lines = 500（这种长行超过五百行才触发，所以一两行长行不会误伤）。触发后的动作默认是 so-long-action = so-long-mode，也就是把主模式换成专为长行优化的基础模式，模式行会标上 So Long。推荐 M- x global-so-long-mode 全局打开；误伤了用 M- x so-long-revert 恢复。代价要说清楚：so-long-mode 是故意牺牲语法高亮和语言相关功能的模式，只适合那些你本来也不该手改的文件。

练习 19　你在 Emacs 32 里打开一个 50 MB 的 JSON 文件，主模式用的是 tree-sitter。会发生什么？为什么这么设计？

Emacs 会给出警告而不是直接打开。手册「Visiting」一节写明：如果文件的主模式使用 tree-sitter 解析库，而文件大小超过 treesit-max-buffer-size，Emacs 就警告；默认 64 位是 40 MB、32 位是 15 MB。本机实测 (require 'treesit) 之后 treesit-max-buffer-size = 41943040（正好 40 MiB）。设计原因手册也写了：「a typical tree-sitter parser needs about 10 times as much memory as the text it parses」——解析器的内存开销约为文本的 10 倍，所以宁可提前拦住，也不要让 Emacs 在这种文件上耗尽内存。这一条对你在手机上的体验尤其重要，因为 Termux 的 Emacs 正是 --with-tree-sitter 编译的。

练习 20　有人说「Emacs 30 起原生编译默认开了，什么都不用做」。这句话哪里对、哪里容易让人误解？

容易误解的地方在于「默认开了」说的是 configure 阶段。Emacs 30.1 NEWS 原文：「Native compilation is now enabled by default. configure will enable the Emacs Lisp native compiler, so long as libgccjit is present and functional on the system. To disable native compilation, configure Emacs with ./configure --with-native-compilation=no.」也就是说你的 Emacs 里带了编译器（本机实测 (native-comp-available-p) 返回 t），而不是「你的每个 Elisp 都已经被编译过」。运行时这一层由 package-native-compile 控制，它的文档字符串说得很清楚：默认 nil 时，包是在「第一次被加载时」做异步原生编译，而不是安装时；设成 t 则安装完就编好（安装慢、首次加载不卡）。另外本机实测 native-comp-jit-compilation 默认是 nil，所以「打开 JIT 提速」这类老说法在今天的默认配置下不成立。移动端用户还该关注 Emacs 31 新增的 native-comp-async-on-battery-power：设成 nil 就是「不插电时不启动新的异步原生编译」。

A. 分清「Emacs 坏了」和「我的配置坏了」

这是排障的第一原则，也是唯一能让你少走弯路的原则。Emacs 手册「Understanding Bug Reporting」里说得很直接：

If possible, try quickly to reproduce the bug by invoking Emacs with emacs -Q (so that Emacs starts with no initial customizations) […] If you can reproduce the bug this way, that rules out bugs in your personal customizations and makes the bug much easier to reproduce.

-Q 的意思是「不加载任何初始化文件」，它比 --no-init-file（-q）还干净：-q 只跳过用户自己的 init.el，而 -Q 连 early-init.el、site-start.el、default.el 一起跳过。

# 1. 最小环境：什么配置都不加载
emacs -Q

# 2. 加载你的配置但打开调试器（Emacs 27+ 有 early-init.el，所以两者都要带上 -q）
emacs --debug-init

# 3. 把完整输出存成文件，出错时贴给社区或自己慢慢读
emacs --debug-init 2>emacs-error.log

# 4. 不用图形界面（排查 GUI 本身的问题时用）
emacs -Q -nw
要点

--debug-init 在 Emacs 32 里到底做了什么，我查到了确切实现。它把变量 init-file-debug 置成 t，Emacs 随后在加载启动文件时改用 handler-bind 把错误接进调试器，而不是像平常那样只弹一个警告。我读了本机的 lisp/startup.el：第 422 行是 (defvar init-file-debug nil)，第 1419 行是 (setq init-file-debug t)，第 1097 行的判断决定走调试器还是走 condition-case-unless-debug。

顺带纠正一条老文章里的说法：debug-init 和 debug-init-form 这两个变量在今天的 Emacs 里已经不存在了。我的核对方式：(boundp 'debug-init) 和 (boundp 'debug-init-form) 都返回 nil；在整个 share/emacs/32.0.50/ 目录里搜索字符串 debug-init，命中的全部是 --debug-init 这个命令行选项的字符串、一个 etc/DOC 里的说明段，以及 edebug.el 里的 edebug-initial-mode（另一个功能，跟启动调试无关）；我另外拉了上游 emacs-29、emacs-30、emacs-31 三个分支的 lisp/startup.el 与 lisp/emacs-lisp/debug.el 对照，同样没有这两个变量的定义。所以网上那些「在 init.el 里设 debug-init 让 Emacs 启动时报错直接进调试器」的做法，在今天的 Emacs 里只会得到 Symbol's value as variable is void: debug-init。正确做法是用命令行选项 --debug-init。

易错

高危操作：把 init.el 改名来做「救援模式」。这个做法本身是对的，而且是官方推荐的标准手段（-Q 帮不了你时就得靠它），但必须知道它的正确姿势和高危之处：

  • 用改名，不要用删除。命令是 mv ~/.emacs.d/init.el ~/.emacs.d/init.el.bak。千万不要用 rm——Emacs 启动文件里往往有你写了两年的配置，而删除是不可逆的。改名的逆操作就是改回来，零风险。
  • early-init.el 也要一起改名。Emacs 27 以后启动分两个阶段：early-init.el 先跑，然后才加载 init.el。如果你只改 init.el 而 early-init.el 里有错，故障照旧。
  • 改名要在 Emacs 外面做。如果你是在 Emacs 里按 Cx Cx RET 改的文件，Emacs 还在运行，改名不会生效于当前会话（而且这个文件正被当前 Emacs 打开着）。正确的做法是：先完全退出 Emacs（Cx Cx 或 CC-），在另一个终端里改名，再重新启动。
  • 如果你在改名前有未保存的 init.el 内容，先在 Emacs 里 Cx s 保存。名字改掉之后文件还在、内容不会丢，但如果你压根没保存过就退出了，那就真丢了。
  • 恢复之后记得改回来，并且把这次故障的原因记下来。反复「改名 → 启动 → 成功」只能证明「问题在配置文件里」，不告诉你是哪一行。真正的定位手段是 --debug-init。

B. 卡死与强制退出

15.5 已经讲过 Cg 家族，这里补上「什么时候用哪个」的决策顺序，以及一件必须避免的事。

  1. 先按 Cg。绝大多数情况（命令在跑、minibuffer 里输了一半、搜索没结束）一次就解决。
  2. 没反应，再来一下。第二个 Cg 在文本终端上触发紧急逃生。恢复后 Emacs 会问两个问题：「Auto-save? (y or n)」答 y 会立刻把开了自动保存的缓冲区全部存盘；「Abort (and dump core)? (y or n)」答 y 会让 Emacs 崩溃并 dump 核心（这是给开发者用的），答 n 则带着原状态继续。如果 Emacs 其实只是慢而不是卡死，两个都答 n 就行。
  3. 在嵌套提问里出不来：C] 一次退一层，M- x top-level 一次全退。
  4. MS-DOS / Windows 原生构建的终端：用两次 C<Break> 代替 Cg。手册说得很明确，原因是 Windows 上无法在命令执行过程中识别 Cg，而 C<Break> 任何时候都能识别。
易错

高危：Emacs 卡住时直接 kill -9（Windows 上是任务管理器里「结束任务」）。后果是你还没保存的修改全部丢失，而且没有任何提示。你在 Windows 上用任务管理器强杀，等于绕过了 Emacs 的自动保存机制——而那个机制本来是你唯一的保险。

正确顺序是：先试 Cg；不行试两次 Cg；还不行，去另一个终端用温和的方式让它退出（Linux 上给 Emacs 发 SIGTERM，而不是 SIGKILL；SIGTERM 会让 Emacs 有机会先保存再退出）。真的只能强杀时，也不会全丢——Emacs 会周期性写自动保存文件，文件名的形式是 # 包住原文件名再加一个 #，例如编辑 notes.org 时会看到同目录下的 #notes.org#。它什么时候能被救回来、有哪些限制我下面单独讲。

自动保存文件怎么救：

  1. 在文件所在的目录里找 #文件名#（注意是井号，不是别的符号）。
  2. 在 Emacs 里 M- x recover-file（我实测这个命令存在），输入原文件名（不是 #文件名#，Emacs 会自己去找那个井号文件）。
  3. Emacs 先弹一个目录清单让你比较两个文件的大小和时间；关键的一步是它接下来的提问：答 yes 才恢复。手册明确告诉你，从 Emacs 30 起还可以答 diff（或 =）——它会先显示原文件与自动保存文件之间的差异，再重新问你一遍，所以拿不准就先 diff。
  4. 答 yes 之后，自动保存的内容会被直接装进这个文件的缓冲区，不存在「再写到一个临时文件」这一步——老文章里说的那个中间步骤是 Emacs 早期的 recover-file-continue，那个命令在今天的 Emacs 里已经没有了。检查无误之后，按 Cx Cs 就把内容写回真正的文件。

所以正确的心智模型不是「手工合并」，而是「 Emacs 替你把自动保存版本装进缓冲区，你确认或微调后正常保存」。真要保留旧版本，先把原文件另存一份再动手。

还有一条更省事的路：M- x recover-session（我实测存在）能找回被强杀前的整个 Emacs 会话——打开过哪些缓冲区、光标在哪、窗口怎么分的。但它同样依赖会话文件还在，而且只恢复「会话」不恢复「未保存的文件内容」。

D. 调试你自己的 Elisp

上面那些是调试「Emacs 内部」的工具。下面这组是调试「你的 init.el」的工具，按「从便宜到贵」的顺序排：

  1. 先问 Emacs，而不是问搜索引擎。Ch v RET 查变量的当前值和文档（Emacs 31 起它还会提示你「这个变量该用 setopt 设」）；Ch f 查函数；Ch m 查当前模式的一切；Ch k 查按键。这四个键能回答你 80% 的「为什么和我以为的不一样」。
  2. 不确定函数/变量叫什么名字：Ch a（apropos-command，我实测存在）按名字模糊搜命令，Ch d（apropos-documentation，实测存在）按文档内容搜。这一招专治「我记得有这个东西但想不起名字」。
  3. 括号配错了：M- x check-parens（实测存在）。报错信息经常是「Arity mismatch」或者某个奇怪的运行时错误，而根因就是 init.el 里某个括号多了一层或少了一层。这一条请记住，它是 init.el 出错时命中率最高的检查。
  4. 宏展开看不明白：M- x pp-macroexpand-last-sexp（实测存在且确实是命令）把光标所在的 S 表达式展开成实际会被执行的代码并漂亮打印出来；对整个缓冲区做同样的事要用函数 macroexpand-all——但请按 M- 输入 (macroexpand-all (car (read-from-string (buffer-string))))：本机实测 macroexpand-all 虽然有 ;;;###autoload 标记、函数也存在，却没有 interactive 声明，M- x 调它只会得到 Invalid command。调试 use-package、with-eval-after-load、条件展开这类「运行时才拼出来」的代码，这是唯一可靠的办法。
  5. 边写边看帮助：M- x eldoc-mode（实测存在）。它会在你敲完一个函数名后，在回显区显示这个函数的参数列表和文档字符串。顺带一个实测结果：eldoc-mode 这个变量在本机 Emacs 32.0.50 上的默认值是 t，也就是说这个功能默认就开着，你不需要做什么。
  6. 最后才上字节编译：M- x byte-compile-file（实测存在）。对 init.el 这么小的文件，它报出来的警告质量远高于运行时才暴露的问题——「变量未定义」「函数未定义」「给常量赋值」这些在运行时报错会很费劲，但字节编译会直接点名。不过要注意：字节编译报出来的「警告」里有很大一部分是无害的（比如变量在后面才定义），别把它当错误清单，逐条判断即可。
  7. 打印调试信息：在 init.el 里插一行 (message "配置装到第 %d 行" 42)，然后按 Ch e（view-echo-area-messages）打开 *Messages* 回看输出。这条土办法在「配置跑到一半就静默失败」的情况下是唯一有效的手段——因为错误被吞掉了，你没有任何其他线索。

E. 该报 bug 给谁

Emacs 手册「Understanding Bug Reporting」的最后一节给了明确分工，原文是：

For problems with packages that are not part of Emacs, it is better to begin by reporting them to the package developers.

也就是说：第三方包的 bug 报给包的作者，Emacs 自身的 bug 报给 Emacs。后者用 M- x report-emacs-bug（实测存在）。手册说它会「automatically inserts some of the essential information」，但也提醒你 它不能提供全部必要信息，剩下的关键部分你还得自己补，补完按 Cc C c 发送。

手册反复强调的一条原则也抄在这里，因为很多人不知道：报 bug 要报事实，不要报猜测。手册举了个例子——不要写「我访问了一个大文件，Emacs 显示了 ‘I feel pretty today’」，而要写「我输入了 C-x C-f /glorp/baz.ugh <RET>，访问了一个（你知道的）相当大的文件，然后 Emacs 显示了 ‘I feel pretty today’」。区别在于后者能被原样复现，前者不能。

技巧

报 bug 之前先做两件事，能省你一半时间：一、试 emacs -Q，手册说「If you can reproduce the bug this way, that rules out bugs in your personal customizations」；二、试最新版——手册说「try to use the latest release of Emacs to see if the problem has already been fixed. Even better is to try the latest development version. We recognize that this is not easy for some people, so you should not feel that you absolutely must do this before making a report.」也就是说你不必强求，但试过了会显著提高被接受的概率。

练习 21　你的 Emacs 启动时在 *Backtrace* 里刷红字，窗口只闪一下就没了。下一步该敲什么命令？为什么不是直接去改 init.el？

先敲 emacs -Q。它的作用是「完全不加载初始化文件」，能立刻分辨两种情况：-Q 能正常启动，说明问题在你的配置文件（这时才轮到 --debug-init 和改名救援）；-Q 也起不来，说明是 Emacs 本体或环境的问题，跟你的配置无关。手册「Understanding Bug Reporting」正是这么建议的：emacs -Q means that Emacs starts with no initial customizations，而如果能在这里复现，就 rules out bugs in your personal customizations。不建议直接改 init.el，因为在错误原因未知时改配置往往只是把问题藏得更深。

练习 22　你照着老教程在 early-init.el 里写了 (setq debug-init t)，Emacs 报 Symbol's value as variable is void: debug-init。正确做法是什么？Emacs 32 里它是怎么实现的？

改用命令行选项 emacs --debug-init，不要在配置里设 debug-init。我查到的依据：(boundp 'debug-init) 与 (boundp 'debug-init-form) 在本机 Emacs 32.0.50 上都是 nil；在 share/emacs/32.0.50/ 整个目录里搜字符串 debug-init，命中项全是 --debug-init 选项的字符串、etc/DOC 里的说明，以及 edebug.el 里无关的 edebug-initial-mode；上游 emacs-29、emacs-30、emacs-31 分支的 startup.el 与 debug.el 对照下来也没有这两个变量。Emacs 32 的实现是：--debug-init 把 init-file-debug 置 t（lisp/startup.el 第 1419 行），随后加载启动文件时改用 handler-bind 把错误接进调试器（第 1097 行的判断）。

练习 23　Emacs 启动即崩，你需要临时让它「什么都不加载」。有人说「把 init.el 删掉」，有人说「改名」。你选哪个？为什么还必须连 early-init.el 一起处理？

选改名，命令是 mv ~/.emacs.d/init.el ~/.emacs.d/init.el.bak。删除是不可逆的，而 init.el 里往往有你很久的积累；改名的逆操作就是改回来，零风险。

还要连 early-init.el 一起改名，因为 Emacs 27 以后启动分两阶段：early-init.el 先执行，然后才轮到 init.el。只处理后者而前者里有错，故障照旧。另外一个实践细节：改名要在 Emacs 外面做（先完全退出，在另一个终端里改名），因为运行中的 Emacs 对已打开文件的改名不敏感，而且你可能还没保存当前编辑中的 init.el。

练习 24　你把 debug-on-error 设成了 t，但有一类错误（比如「到达缓冲区开头」beginning-of-buffer）从来不进调试器。为什么？

因为 debug-ignored-errors 这张表会跳过调试器，并且它覆盖 debug-on-error——这条覆盖关系是 etc/DOC 里写明的。本机实测它的默认值是一串符号：beginning-of-line beginning-of-buffer end-of-line end-of-buffer end-of-file buffer-read-only file-supersession mark-inactive user-error。所以「移动到缓冲区边界」和 user-error 这类被视为「正常的」错误永远不进调试器，这是设计而不是 bug。etc/DOC 还提醒了一句实操细节：如果你用 --debug-init 启动并且想从这张默认表里删掉某几项，要用 setq 给整个列表赋一个新值，不要用 delq 原地删，因为后者会破坏 Emacs 的期望状态。

练习 25　Emacs 在你的手机上彻底卡死了。直接用 kill -9 杀掉，会有什么损失？有什么东西能救回来一部分？怎么救？

损失是所有还没保存的修改，而且没有任何提示——因为 kill -9 绕过了 Emacs 的自动保存机制。正确的顺序是：先试 Cg；不行试两次 Cg（文本终端上会触发紧急逃生，恢复时还会问你要不要立刻 auto-save，答 y 就会把开了自动保存的缓冲区全部存盘）。能救回一部分：Emacs 周期性写的自动保存文件还在磁盘上，文件名是原文件名用两个 # 包起来（编辑 notes.org 就找 #notes.org#）。救法：在 Emacs 里 M- x recover-file，输入原文件名；Emacs 先给你一个目录清单比较两个文件，提问时可以答 diff 先看差异（Emacs 30 起的新功能），答 yes 就把自动保存内容装进缓冲区，确认后 Cx Cs 正常保存回去。这里没有「写到临时文件再手工合并」这一步——那是老版本 Emacs 的 recover-file-continue 流程，现在的命令里已经没有了。另外 M- x recover-session 能找回被强杀前的会话布局，但不找回未保存的文件内容。

要点

整章最后留一句经验性的话（这是我个人的判断，不是有据可查的事实）：这一章里所有平台差异，归根结底来自一件事——Emacs 假定它独占一台 POSIX 机器。Android 用沙箱和进程数限制打破这个假定，iOS 把它彻底否定，WSL 帮你把假定重新建立起来。所以「选平台」这个动作的本质，是判断「这个环境能不能让 Emacs 独占自己」。能，就上；不能，就用远程。
