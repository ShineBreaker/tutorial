三、移动理论（一）：基础动作、窗口与标签页

这一章解决三件事：① 搞懂 Emacs 移动的三层划分，知道本章该记住什么；② 建立 buffer / window / frame 三层心智模型——Emacs 的 window 不是别的编辑器里那种固定分屏，它是随用随建、用完就删的显示区，frame 才是你在屏幕上看到的那个 GUI 窗口；③ 掌握打开、保存、退出、切换 buffer 这几个基础命令，以及窗口、frame、标签栏、标签行各自的键位。这一章的键位我都在本机 GNU Emacs 32.0.50 上用 (key-binding (kbd "…")) 逐条查过，凡是与原书写成时的年代不符的地方（键位改过、默认值改过、命令被合并或删除）都标了出来。

要点

本章的命令和键位我是在本机 Emacs 32.0.50 上逐条实测的（emacs --batch -Q --eval '(key-binding (kbd "C-x C-f"))' 这类查询），版本相关的结论来自本机安装的 GNU Emacs 手册（版本标注 updated for Emacs version 32.0.50）与 etc/NEWS.29/30/31 原文。凡是我无法在本机核实、又需要联网查证的结论，正文里都明确写了「未核实」，请以你自己环境的实际结果为准。

一、移动分三层：局部、区域、全局

Emacs 用户常说的「移动」其实是三样东西。原书把它们分成三层，我沿用这个划分，因为分清了层次，你才知道哪些命令值得背、哪些只是路过看看。

  • 局部移动（local movement）：在光标附近挪动，不离开当前这块文本。移动的语法单元（syntactic unit，指 Emacs 里能被整体识别的一组字符，比如一个词、一行、一个括号对）可以是字符、词、行、句、段、S 表达式。这一层是第 4 章的内容。
  • 区域移动（regional movement）：比局部移动大一号的整块结构。写代码时是整个函数、整个类定义；写文档时是整章、整节。这一层同样在第 4、5 章。
  • 全局移动（global movement）：从一个 buffer 到另一个 buffer，或从一个 window 到下一个 window。本章只讲这一层。

为什么先讲全局？因为零基础的人第一次打开 Emacs，卡住他的往往不是「Cf 前进一个字符」这种局部移动，而是「我明明只想打开一个文件，怎么屏幕上突然多出一半来？」这种全局问题。Emacs 会自己开窗口这件事，不理解它，后面所有的操作都会变成背命令。

要点

Emacs 官方手册把这一整块内容拆成 Buffers、Windows、Frames、Tab Bars 四个节点（我用 zcat …/share/info/emacs.info.gz 在本机核对了节点名）。本章就按这个顺序讲：buffer 是文本本体，window 是显示位置，frame 是外框，标签栏是窗口布局的集合。

二、最重要的心智模型：buffer、window、frame 三层

先给定义，每个定义都用你已经在用的编辑器经验打个比方：

  • buffer（缓冲区）：一段正在编辑的文本。它不等于文件。文件只是 buffer 的一种「落脚点」；Emacs 自己生成的临时文本（帮助、编译日志、shell 输出、抓取网页）也是 buffer，只不过没有对应文件。你在 VS Code 里关掉一个标签页，那个 tab 就是一个 buffer。
  • window（窗口）：frame 里面的一块显示区域，负责显示某一个 buffer。这是初学者误解最深的一个词——它不是操作系统的窗口，而是 frame 内部的「一块格子」。
  • frame（框架）：你在操作系统任务栏里看到、可以拖动、可以最小化的那个窗口。别人说的「打开一个新窗口」，在 Emacs 里必须说成「打开一个新 frame」。

把三层关系记成一句话：一个 frame 装着一堆 window；每个 window 显示一个 buffer；同一个 buffer 可以同时被好几个 window 显示。官方手册 Basic Window 节点确认了最后这点：同一 buffer 出现在多个 window 里时，这些 window 会同步显示修改，但各自的 point（光标位置）互相独立，而 mark 只有一份。

想知道自己在哪个 frame，不用做任何按键——看模式行。第 2 章讲过：frame 编号（更准确说是 frame 名，Emacs 31 起才有）就显示在模式行上、缓冲区名的左边，初始那个 frame 叫 F1。想知道当前 buffer 名，也看模式行，就是中间那一段。别去按 Cx b 来问这件事：它是 switch-to-buffer，会把当前 frame 整个换成 buffer 列表窗口，既不回答问题，还把你正在编辑的内容顶掉了。

Emacs 会自己开窗口，这不是 bug

Emacs 的设计里，window 是临时工位：需要时开，不需要时关，窗口布局本来就是经常变的。官方手册 Basic Window 节点说得很直接：显示信息的命令（比如 Ch f 看函数说明、Cx Cb 列 buffer）通常是在非当前 window 里显示，不会动你正在编辑的那个 window；而 Cx 4 系列命令则明确要求 Emacs 去「另开一个 window」。

你自己会遇到的典型三件事：

  1. 按 Ch 任何键（帮助）→ Emacs 弹出一个叫 *Help* 的 buffer，通常放在屏幕下半部分的一个新 window 里，不打断你原来的位置。
  2. 按 Mx compile 编译 → *compilation* buffer 出现在另一个 window。手册 Compilation 节点原话是：「Starting a compilation displays the ‘*compilation*’ buffer in another window but does not select it.」
  3. 按 Mx shell 开 shell → 同理，*shell* buffer 单独占一块。
易错

所以：Emacs 30 起新增了变量 warning-display-at-bottom（我核对了本机 lisp/emacs-lisp/warnings.el:124，默认值确实是 t），含义是警告 buffer 一律显示在当前 frame 的底部——源码注释写得很细：「Emacs will attempt to display the window showing the warning buffer at the bottom of the selected frame, whether by reusing the bottom-most window or by creating a new window at the bottom of the frame」，并且会滚动到 buffer 末尾显示最后一条警告。它影响的范围包括字节编译器和原生编译器（native compiler）发出的警告，还有 check-declare 之类的检查结果。设成 nil 就回到「由 display-buffer 自己决定显示在哪」的旧行为。

你可能会在本章第二节那个「Emacs 自己开窗口」的清单里再补一条：编译警告、字节编译警告，都会开一个底部窗口。而 etc/NEWS.30 的原始条目是：「Warnings are now by default displayed in a new window at frame's bottom.」——注意它说的是「new window」，而源码注释说得更细：能复用底部已有的 window 就复用，必要时才新建。

练习 1　你把屏幕切成上下两块，想在两块之间来回跳，用哪个键？如果是两块都在同一个应用窗口里，Cx o 和 Cx 5 o 分别是什么？

同一 frame 内切 window 用 Cx o（other-window），连按可以轮转所有 window；切 frame 用 Cx 5 o（other-frame），它会切换并把目标 frame 抬到最前。两个键的第三个字符都是字母 o，区别只在第二个字符是 x 还是 5。

官方手册 Frames 节点特别提醒过：删 frame 是 Cx 5 0，是数字 0，不是字母 o。我在 Emacs 32.0.50 上实测这两个绑定分别是 other-window 和 other-frame，没变。

练习 2　你说「打开三个文件」，在 Emacs 里准确的说法是什么？Emacs 会不会因为你「用完」一个文件就自动把它扔掉？

准确说法是「打开了三个 buffer」，如果这三个 buffer 同时要看见，就再分裂出三个 window 来显示它们；如果你想让它们变成任务栏上的三个独立窗口，那才需要三个 frame。

Emacs 不会自动扔掉 buffer。buffer 会一直存活在你的 Emacs 进程里，直到你显式 Cx k（kill-buffer）或退出 Emacs。原书作者的说法是：认真用 Emacs 的人手上同时挂着几百上千个 buffer 也毫无压力，因为一个 buffer 除了少量元数据和它自己的编码系统，内存占用就只比文本本身的字节数多一点点。这条属于「知道了会安心、但不需要做什么」的知识。

反过来推论也成立：你不必养成「随手关文件」的习惯，这和 VS Code 里「不关 tab 内存就涨」的直觉正好相反。

三、还不会用 Emacs 时，先摸菜单栏

原书给新手的建议是：在你把键位记熟之前，菜单栏（menu bar，GUI 和终端 Emacs 顶部都有的那一行 File / Edit / Buffers / Tools / Help）是完全正当的学习工具。我同意这个建议，但有两个前提必须说清楚，否则你会卡住。

前提一：菜单栏能用键盘激活。按 F10 就能把菜单栏点亮。手册 Menu Bars 节点明确写着这个键运行的命令是 menu-bar-open，并且给出了完整的键盘走法：用方向键或 Cb / Cf（左右）、Cp / Cn（上下）在菜单之间移动，RET 选中，Cg 或 ESC ESC ESC 退出菜单导航。手册还提醒了一句很实际的话：如果 Emacs 是用 GUI 工具包构建的（比如 GTK），菜单由工具包自己画，取消导航的按键可能和上面描述的不同。

我需要说明一处验证的边界：在本机 emacs --batch -Q 里查 (key-binding (kbd "F10")) 返回 nil，因为 batch 模式既没有终端也没有 GUI，菜单栏根本没被初始化。所以「F10 在交互环境里绑到 menu-bar-open」这条我依据的是手册原文而不是本机键位实测——这是本次全章里少数几条没有键位实测支撑的断言之一。

终端 Emacs 还有个额外选项：把变量 tty-menu-open-use-tmm 打开后，F10 会改为运行 tmm-menubar，把菜单渲染在回显区而不是下拉；也可以随时按 M` 直接调 tmm-menubar。

前提二：终端里能不能用鼠标，取决于有没有开鼠标次模式。在终端里跑 Emacs 时，鼠标事件是靠终端转发给 Emacs 的，Emacs 这边要有一个次模式来接收。xterm 系终端（xterm、gnome-terminal、konsole、iTerm2）用 Mx xterm-mouse-mode（我实测确认命令存在）；Linux 文本控制台（tty1 那种）要用 Mx gpm-mouse-mode，前提是系统里装了并跑着 gpm 服务。

这里有个新手容易困惑的点：xterm-mouse-mode 是个全局次模式，Emacs 启动时如果检测到你的终端支持鼠标，它会自己打开——所以很多时候你以为「要先开」其实它早就开着。敲 Mx xterm-mouse-mode 是切换它：开着的时候再敲一次就关掉。想知道当前状态，按 Mx describe-mode。

开着之后也有个限制值得知道：手册 Text-Only Mouse 节点说，这个模式下「基本上只支持不带修饰键的单击」；想让终端自己做它那套（典型场景是拖选文本），得按住 Shift 再点。

技巧

菜单栏不只是「新手拐杖」。每个 major mode（Emacs 给 buffer 选的语言模式，比如 emacs-lisp-mode、python-mode、sh-mode）通常会往菜单栏里塞一条自己的菜单，把该模式最常用的操作列出来。你可以把它当成「这份模式的说明书」用——想知道某个模式下有哪些命令，打开菜单看一眼比翻文档快。

要点

等你确实用顺了再隐藏菜单栏：Mx menu-bar-mode 是切换命令（我实测确认它是命令），执行一次关掉、再执行一次开回来。之所以值得等到后期，是因为它会占掉一行屏幕高度。原书作者也是这个建议。

如果你的配置是从 starter kit（比如 Doom Emacs、Spacemacs）或别人的 init.el 里抄来的，菜单栏可能已经被关掉了、而你还不知道该怎么打开。原书特别提醒过这种情况：这时候 Mx menu-bar-mode 可以救你，但你还得回头把自己配置里隐藏它的那行找出来删掉，否则下次启动又没了。

进阶：xterm-mouse-mode 之外，终端里还有哪些鼠标相关的坑

终端 Emacs 的鼠标支持是一层套一层的：

  • Mx xterm-mouse-mode 只覆盖常见的 xterm 系终端（xterm、gnome-terminal、konsole、iTerm2 都兼容）。在 tmux 或 screen 里跑 Emacs 时，鼠标事件能不能到你手上取决于终端复用器有没有转发鼠标：现代 tmux 默认就是开的（我在本机 tmux 3.7c 上用 tmux -f /dev/null start-server ';' show-options -g mouse 查过，返回 mouse on），老版本 tmux 默认是关的，那时需要在 ~/.tmux.conf 里写 set -g mouse on；screen 则要开 mouse。这些是终端侧的开关，和 Emacs 里的 xterm-mouse-mode 是两件事，两个都到位鼠标才可用。
  • 鼠标抢走单击，但没抢走拖选。这是 xterm 鼠标协议的设计取舍：Emacs 只接管「不带修饰键的单击」，而按住 Shift 的点击仍然归终端——所以终端里的拖选文本照常能用。你会发现「单击跳光标」和「拖选」并存，这正是这个协议规定的。
  • GUI Emacs 不需要 xterm-mouse-mode，鼠标天生可用；xterm-mouse-mode 只影响终端 Emacs。在 emacsclient 客户端窗口里鼠标行为跟随你连的那个服务端 Emacs（因为所有帧都是服务端画的）。

这一节列的三点里，「哪些终端需要额外开关」是你自己在自己的环境里才能定的：Emacs 端看 xterm-mouse-mode / gpm-mouse-mode 有没有开（Mx describe-mode），终端复用器端看它自己转发不转发鼠标。我无法替你确认。

四、打开文件：Cx Cf

原书反复强调的一件小事值得放在最前面：Emacs 不区分「打开已有文件」和「新建文件」。你按 Cx Cf 敲一个路径，Emacs 就去找那个文件，找到就显示内容，找不到就给你一个空 buffer，等你打字，Cx Cs 保存时才真正在磁盘上创建它。原书管这个动作叫 visit（访问）一个文件，但也说「叫 open 也完全没问题」，我就不额外造词了。手册 Visiting 节点用的词是 find-file（命令名）。

Emacs 怎么知道该用哪种语言模式

打开文件时 Emacs 会挑一个 major mode（Emacs 给 buffer 选的语言模式，决定缩进、注释符号、语法高亮、Tab 键行为、菜单栏内容）。它有四层判断，从前往后套：

  1. 文件内局部变量（file-local variables）：写在文件头或文件尾的指令。
  2. 解释器声明（interpreter-mode-alist）：文件第一行的 #! Shebang 行，例如 #!/usr/bin/env python、#!/bin/bash。Emacs 靠它认出这是个脚本并启用对应 major mode。
  3. 魔数匹配（magic-mode-alist）：拿文件开头的内容去匹配正则。历史功能，今天默认是空的（详见下面的方框）。
  4. 文件名 / 扩展名匹配（auto-mode-alist）：一张大表，把扩展名或文件名映射到 major mode 函数。这是绝大多数情况的实际决策者。

文件头写法长这样（这一行要放在文件第一行，或紧跟在 Shebang 行后面）：

# -*- mode: python -*-
或者文件尾：

Local Variables:
mode: python
End:
易错

关于 magic-mode-alist：原书说它是 Emacs 判断模式的一个机制，这一点没错，但今天的默认值是空的。我在 Emacs 32.0.50 上实测 (default-value 'magic-mode-alist) 返回 nil，源码 lisp/files.el:3461 的定义就是 (defvar magic-mode-alist nil …)。也就是说，纯靠内容匹配的「魔数模式」在默认配置下不会发生任何事。你要是想用它，得自己往这张表里加正则。

同一个源码文件里我实测确认的两个真实默认值是：enable-local-variables = t（允许文件里的局部变量生效）、enable-local-eval = maybe（文件里 eval 型的局部变量要问你一句才生效）。这就是为什么你打开一个别人写的文件时，Emacs 偶尔会弹出一个「这个文件想设置这些变量，你信吗？」的小询问。

要点

手册 Saving Files → Backup 之后的 Customize Save 提到：Emacs 把「来自文件内部的变量」分成安全（由 Emacs 维护者判定，比如缩进宽度）和不安全（能让 Emacs 执行任意代码）两类。不安全的默认会被询问而不是直接执行——因为 Emacs 本质上是在「直接运行一个文件里的话」，这不是小事。

如果你打开一个陌生仓库的文件总被弹窗烦到，可以把 enable-local-eval 设成 nil 一劳永逸（代价是那些文件靠 eval 声明的设置失效）；Mx customize-option RET enable-local-eval RET 就能改。

编码和行尾：Emacs 帮你省掉的麻烦

除了 major mode，Emacs 打开文件时还会顺手判断两件事：编码系统（coding system，字节到文字的映射规则，中文环境尤其重要）和行尾符（line ending）。

  • 编码：Emacs 的 Unicode 支持很完整，能在不同编码之间透明读写。看当前 buffer 用的是什么编码，按 Ch C（describe-coding-system，我实测绑定确认）。
  • 行尾：文件用 CRLF（DOS/Windows）打开，保存时还写 CRLF；LF（Unix）也保持 LF。这是 Emacs 少有的贴心设计之一，能避免「在我机器上是好的，传到服务器就崩了」。

模式行（mode line，每个 window 底部显示 buffer 名的那一行）手册 Mode Line 节点给出的整体格式是 CS:CH-DFR  BUF    POS LINE   (MAJOR MINOR)。这一行几乎每一格都是条件显示的——某一格出不出现在什么情况下，跟你跑在终端里还是图形界面里直接相关，所以「为什么我看到的和书上的不一样」通常不是出错。拿第 2 章那条 *scratch* 的实例逐格对照：

技巧

格式再复杂也有绕开的办法：改变量比记格式快。每一格都有对应的变量：mode-line-format（整行）、mode-line-buffer-identification（BUF）、mode-line-position（POS）、mode-line-frame-identification（FR）、mode-line-remote（R）。按 Mx 输入 mode-line-format 回车能看到格式串里每个 % 记号的文档（比如 %m 是模式名、%b 是缓冲区名）。想查某一格当前由谁控制，先按 Ch v 查上面这几个变量名。

唯一必须靠查询才能搞清的是编码那一格：按 Ch C（describe-coding-system）看当前 buffer 到底在用哪套编码，本书作者在 Emacs 32.0.50 上实测这个绑定确实存在。

进阶：文件局部变量为什么既是特性也是攻击面

文件局部变量（file-local variables）让你把「这个文件缩进用 4 空格、Tab 宽度 2」这样的设置直接写进文件本身，随文件走——这在团队协作里非常顺手。

但机制上是这样的：Emacs 读到一个文件时会去解析文件头/文件尾的指令块，然后对变量求值。这就是为什么 Emacs 把变量分成 safe / unsafe 两类，并把求值类指令的默认策略设成 maybe（询问）。如果某个变量被判定为 unsafe，Emacs 会停下来问你要不要接受。

与之相关的几个可调项（都是我在 Emacs 32.0.50 上实测存在且有默认值的）：

  • enable-local-variables，默认 t——控制是否采纳文件里的局部变量。
  • enable-local-eval，默认 maybe——控制 eval 型局部变量是直接执行、忽略还是询问。
  • safe-local-eval-forms——白名单，即使 enable-local-eval 设成 nil，这张表里的形式仍会执行（lisp/files.el:3871 处定义，默认值里全是时间戳相关的钩子，比如往 write-file-hooks 里塞 time-stamp）。

顺带说一句：手册 Undo 节点里有一条很少人注意的规则——名字以空格开头的 buffer 永远不记录撤销信息。Emacs 内部有一批这样的 buffer 存临时文本，比如源码里写死的 " *temp*"、" *nslookup*"、" *Input History*"（注意开头那个空格）。在里面编辑到的东西是撤不回来的。

练习 3　你想新建一个还不存在的文件 notes/hello.md。Emacs 里怎么操作？如果只按 Cx Cf 敲这个路径就回车，磁盘上会出现文件吗？

操作就是 Cx Cf，输入 notes/hello.md，回车。Emacs 不区分打开和新建：文件不存在时它给你一个空 buffer，模式行上的 buffer 名就是 notes/hello.md。

磁盘上不会出现文件，要等你按 Cx Cs（save-buffer）才真正写入。

有个真实的坑要提醒：如果中间目录 notes/ 也不存在，保存会失败并报错。这不是 Emacs 的 bug，是文件系统在拒绝你；Emacs 32 的错误提示里会写明原因。

练习 4　Emacs 判断一个 buffer 该用哪种 major mode，检查顺序是哪四层？（提示：原书把它们列出来了，其中一层在今天的 Emacs 里默认是空的。）

按原书给的顺序：① 文件局部变量（文件头 -*- mode: xxx -*- 或文件尾 Local Variables: 块）→ ② 解释器声明（interpreter-mode-alist 变量识别的 #! Shebang 行）→ ③ 魔数匹配（magic-mode-alist）→ ④ 自动模式匹配（auto-mode-alist，扩展名和文件名映射表）。

第 ③ 层的现代情况：magic-mode-alist 这个变量在 Emacs 32.0.50 里仍然存在但默认值是 nil（我实测 (default-value 'magic-mode-alist) = nil，源码 lisp/files.el:3461）。所以默认配置下这一层等于不存在。

第 ④ 层才是主力：/etc/passwd 会被 etc-passwd-generic-mode 打开，.zip 会被 archive-mode 打开——原书这两个例子我核对过手册的 Visiting 与 Major Modes 描述，仍然准确。

练习 5　一个文件在编辑器里显示乱码，你怀疑是编码问题。用哪个按键可以确切地知道 Emacs 认为它是什么编码？模式行上那个开头的字母又是什么意思？

确切的办法是 Ch C，即 describe-coding-system（我实测该绑定在 Emacs 32.0.50 上成立）。它会列出与当前 buffer 关联的所有编码系统；对于普通文件，它们几乎总是同一个。

模式行最左边是 CS:CH 这一小段（手册 Mode Line 节点给的完整格式是 CS:CH-DFR BUF POS LINE (MAJOR MINOR)）。CS 是编码系统的助记符：- 表示没做特殊处理、= 表示完全不转换、1 表示 ISO Latin-1，多字节编码则显示各自的助记符（UTF-8 是 U）。紧跟其后的符号说明行尾：: 是 Unix 风格，DOS 风格显示成 (DOS) 或 \，老 Macintosh 风格显示成 (Mac) 或 /（手册说具体用哪一个「取决于操作系统」）。

注意这是「提示」不是「保证」——手册明确说过确切记号取决于你用的几百种编码系统里的哪一种，所以拿不准就按 Ch C。

五、保存与退出：Emacs 会先问你，而且问得很有礼貌

Cx Cs：保存当前 buffer

Emacs 里每个 buffer 都能保存，哪怕它根本没有对应文件——帮助 buffer、编译日志、shell 输出都能存，Emacs 会问你要个文件名。你通常见到的情形只有两种：

  • buffer 已经关联了文件 → 直接写回那个文件，回显区显示 Wrote /path/to/file；
  • buffer 没有关联文件（临时 buffer）→ Emacs 问你要文件名。

想让当前 buffer 存到另一个文件（其他编辑器的「另存为」），用 Cx Cw（write-file）。想一口气把所有改动过的文件存一遍，用 Cx s（save-some-buffers），它会一个一个问你。

手册 Save Commands 节点还给了两个冷门但有用的：M~（not-modified）把当前 buffer 标记回「未改动」，Cu M~ 反过来标记成「改过了」。前者用来回答「这文件到底改没改」，后者用来骗过 Emacs 的修改检查——属于知道了就好，不要用来绕过别人的代码评审。

Cx Cc：退出 Emacs

Cx Cc 绑的是 save-buffers-kill-terminal。用两段式按键是为了防止误触。它的工作流程：先逐个询问是否保存改动的文件 buffer；如果你选择不全保存，Emacs 会再问一次确认，因为不保存的内容真的会丢；如果还有子进程在跑（比如 shell），Emacs 也会问一次，因为杀掉 Emacs 会连带杀掉这些进程。

技巧

下次退出时不想被一个个问，直接在第一个提示敲 !，Emacs 会把所有改动过的文件都存下来。手册 Exiting 节点确认了 Cx Cc 如果有改动过的「访问文件的 buffer」会先挨个问；Mx kill-emacs 则完全不问直接杀——那等同于「我确定所有东西都存好了」，别乱用。

还有两个可调的确认开关，两个默认值我都在本机实测过：confirm-kill-emacs 默认 nil（非 nil 时它被当成一个「是否允许退出」的判断函数，比如设成 yes-or-no-p 就会每次退多问一次）；confirm-kill-processes 默认 t（有子进程时问一次；设成 nil 则不问）。

要点

六、切换 buffer：Cx b 和它的补全世界

为什么 buffer 名字有两副面孔

Emacs 用 buffer 名字里有没有 * 来区分两类 buffer：名字带星号的（*Help*、*compilation*、*shell*、*Messages*）是 Emacs 自己生成的，要么跟外部程序交互，要么存临时信息；不带星号的通常是你从文件打开的正经 buffer。还有第三类别忘了：名字以空格开头的内部 buffer（" *temp*"、" *nslookup*" 这种），Emacs 专门用它们存中间结果（前面讲撤销时提过，这类 buffer 连撤销记录都没有）。星号和空格这两条约定在模式行和 buffer 列表里都一眼可见，看多了自然就认得。

原书还提到一个 Emacs 特有的用法：scratch buffer（草稿 buffer）——敲一个不存在的 buffer 名按 Cx b，Emacs 会直接给你新建一个。比如把一段代码复制进一个叫 scratch 的 buffer 里随便改，改坏了扔掉也不心疼，因为那本来就没有对应文件。

补全：这一章里变化最大的部分

原书写这段的时候，建议分版本选方案：「Emacs 27 以下用 IDO，27 及以上用 FIDO（FIDO 是 IDO 的替代实现）」，并点名了一堆框架 Helm、Ivy、Selectrum、Vertico、Icicles、Icomplete。**这套推荐今天已经过时了，而且过时的方式很能说明问题**——Emacs 把 FIDO 收编进了内置代码。

易错

Emacs 32 里已经找不到 fido.el 这个文件了。我在本机 Emacs 32.0.50 上用 (locate-library "fido") 查询返回 nil，并在整个 Emacs 安装目录 find 也搜不到任何 fido* 文件。fido-mode 这个命令还在——我实测 (require 'icomplete) 之后 (commandp 'fido-mode) 为真——但它的定义搬到了 lisp/icomplete.el:543，文档字符串第一行现在是「An enhanced icomplete-mode that emulates ido-mode」。也就是说 FIDO 变成了 Icomplete 的一个模式，你仍然可以照原书敲 Mx fido-mode，效果和以前一样，不需要装任何东西。

所以本节给你的今天的建议是：先什么都不装，用内置的；觉得候选列表不顺眼了，再开 fido-mode；觉得还不够，再考虑第三方的 consult。

内置补全在 Emacs 29 经历了一次大改：新增了补全样式（completion style，即候选怎么算出来）这个概念，由变量 completion-styles 控制。我在本机 Emacs 32.0.50 上实测它的默认值是：

completion-styles   ; => (basic partial-completion emacs22)

意思是「依次尝试三种风格：精确前缀匹配 → 部分（子串）匹配 → Emacs 22 老行为」。这就是为什么今天的 Cx b 比老版本「好按一点」：你敲片段它也能匹配上。至于 use-completion 这个开关变量，我需要明确说明：在 Emacs 32.0.50 的全部 Lisp 源码（lisp/ 整个目录）和本机安装的 info 手册里，grep 都找不到这个变量——只剩下 use-completion-under-point 这类同前缀的函数。如果你在别处读到「把 use-completion 设成 t 就能开新补全」，那是旧版本或博客里的过时说法，在今天的 Emacs 上照抄会得到一个 void-variable（变量不存在）错误。

要调补全的样子，用这几个变量（都在 minibuffer 这个 customize 组里，Mx customize-group RET minibuffer 就能打开面板）：

  • completion-styles——换候选算法，加 flex（模糊匹配，把 fzq 匹配到 foo-zebra-quux）或 basic 都可以。
  • completion-auto-help——决定 *Completions* buffer（候选列表）什么时候出现。我在本机 Emacs 32.0.50 的 lisp/minibuffer.el:1138 处核对了它的文档字符串：可取 nil（不显示）、t（默认值，只在补全失败时显示）、lazy（失败两次才显示）、visible（失败一次就显示并保持可见）、always（每次尝试都显示）。
  • completion-cycle-threshold——候选超过多少个就不再自动全部显示。
技巧

把 Mx ibuffer 绑成默认的 Cx Cb，是回报率最高的一处配置。原书给的写法是 (global-set-key [remap list-buffers] 'ibuffer)——这里的 remap 意思是「不是新增按键，而是把 list-buffers 这个命令本身换成 ibuffer」，所以 Cx Cb 依然按，但弹出来的界面可以边打字边过滤、实时排序。

练习 6　Cx Cb 列 buffer 的界面很难用。换成 ibuffer 的那行配置怎么写？原书推荐的 FIDO，在 Emacs 32 上还需要装吗？

配置写在自己的初始化文件里（Emacs 启动时读的用户配置）：

(global-set-key [remap list-buffers] #'ibuffer)

改完怎么生效不用重启：Mx eval-buffer，在弹出的文件名里选你的初始化文件（默认是 ~/.emacs.d/init.el 或 ~/.emacs），回车即可重新加载整个配置。

FIDO 不用装。我实测 (locate-library "fido") 在 Emacs 32.0.50 上返回 nil，安装目录里没有 fido.el；但 (require 'icomplete) 之后 (commandp 'fido-mode) 为真，定义在 lisp/icomplete.el:543。Mx fido-mode 照敲即可。

练习 7　「关掉当前文件」在 Emacs 里有两个不同的按键，你该怎么选？

先问自己想关的是哪一层：

  • 只是想不再显示这个 buffer，绝大多数情况下什么都不用做——直接 Cx b 切走就是了，buffer 会安静地留在后台等你回来。
  • 真的要删除这个 buffer：Cx k（kill-buffer）。它会先在 minibuffer 里问你要杀哪个 buffer，直接 RET 就是当前这个；如果这个 buffer 关联着文件而且改过，Emacs 要求你输入完整的 yes 才肯删。
  • 想一次清一批：Mx kill-some-buffers 会挨个问。注意它完全跳过名字以空格开头的内部 buffer（" *temp*" 那一类），这类 buffer 要删得自己 Cx k 并点名。
  • 想关掉的是屏幕上的那块区域：Cx 0（delete-window）只删 window，不动 buffer。
  • 想关掉的是整个应用窗口：Cx 5 0（delete-frame）。

四个键对应四个不同的东西，这就是本章第二节那张对照表的价值所在。原书作者的态度是「不必强行杀 buffer，让它待着」，因为 buffer 的内存开销接近于文本本身。

七、卡住时的万能键，以及 Emacs 最反直觉的撤销

ESC ESC ESC：一键回到正常

连按三次 ESC（别连着手滑，按三下要有节奏地敲），命令是 keyboard-escape-quit（我实测绑定确认）。手册 Basic Files 之外的行为说明是：它会退出 minibuffer 提示、取消数字前缀、退出递归编辑层、把所有 window 收成一个。原书把它的口诀写成「如果卡住了就敲三下 ESC，大概能解决」——这个建议在今天依然成立。

易错

它会把窗口布局压回单窗口，你辛苦摆好的多窗口布局会被打散。这不是 bug，是它的设计目标（回到「最基本的正常状态」）。真怕丢布局，就先开 winner-mode（第八节），或者用标签栏记住那套布局。

撤销环：Emacs 的撤销和其他编辑器不一样

手册把撤销系统归在 Undo 节点（18.1 节）。核心机制叫撤销环（undo ring）：Emacs 把你做过的每一个改动都记在一个环里，包括「撤销」这个动作本身。而大多数编辑器用的是线性撤销栈——你撤销之后再打字，被撤销的那几步就永久消失了。

三条必须记住的规则：

  1. 一次 C/ 撤销的是「一个撤销单元」，不是一个按键。连续打字会被合并成一个单元；RET、退格、移动光标这类动作会「封口」，让前后分开。
  2. 只有「再敲一次撤销」才能继续往回撤。一旦你做了别的动作（哪怕只是移动光标），撤销序列就断了。
  3. 断了之后，刚才那串撤销本身被记进了环里。所以你再按 C/，撤掉的是「你刚才那些撤销动作」——也就是说它变成了重做。手册 Undo 节点的原话是：「Any command other than an undo command breaks the sequence of undo commands. Starting from that moment, the entire sequence of undo commands that you have just performed are themselves placed into the undo record.」

这三条的后果就是原书那句结论：在 Emacs 里你几乎不可能因为撤销而丢数据，因为「撤销」这个动作本身也能被撤销。所以原书建议「放心大胆地试」——这个建议在今天依然安全。

原书那个七步例子（值得你亲手敲一遍）

用一个新 buffer，把 █ 想成光标。下面的过程照抄原书第 101–102 页，我只是把文字描述换成了对照：

1. 输入两行：
   Hello
   Emacs█

2. 按一次 C-/：
   Hello
   █                 ← 只撤掉了 Emacs 这个词，换行留下了

3. 再按一次 C-/：
   Hello█             ← 换行也被撤掉了

4. 再按回车，输入 World：
   Hello
   World█             ← 此时你写过东西、撤过、又写了新东西

5. 连按两次 C-/：
   Hello
   Emacs█             ← 撤回到你最初写的样子！这就是「撤销本身被撤销」

6. 再连按 C-/，你会依次看到 World 被撤掉、回车被撤掉，
   最后一直能撤到整个 buffer 空白。

第 2 步「换行被保留」不是巧合。Emacs 的实际规则（手册 Undo 节点写的是 consecutive character insertion 通常合并，query-replace 之类会拆细），换行会触发 undo boundary，因为原书的理由很实在：想撤销时，你通常不想连带撤销一大段散文或代码，只想撤掉最近敲的那几个字。这条边界的存在本身就是为了让「一次撤一步」符合直觉。

要点

关于上面的过程我需要说明验证方式：我用 emacs --batch -Q 反复尝试模拟（batch 模式下 Emacs 的命令循环不运行，撤销记录无法建立，C-/ 会直接报 No further undo information），没能拿到逐帧的实测输出。所以上面这个七步过程是照原书书稿复述，而不是我实测的结果——它的每一步都和本机 Emacs 32.0.50 手册 Undo 节点的文字描述一致，但如果你要拿它当验收标准，请自己在交互式 Emacs 里敲一遍确认。

想要「经典撤销/重做」怎么办

Emacs 28 起有两个新命令专门解决「我也想要别的编辑器那种 undo/redo」的诉求：

  • Mx undo-only——就是 undo，但不会把你刚撤掉的东西重做回来。它没有默认键位（手册 Undo 节点只写「M-x undo-only」），要用 Mx 调。
  • Mx undo-redo，键位 C? 和 CM_——显式重做「刚才那些撤销动作」。手册特别注明：它自己不会被记录成可撤销的动作。

这两个绑定我在本机 Emacs 32.0.50 上实测确认（C? 和 CM_ 都指向 undo-redo；(where-is-internal 'undo-only) 返回 nil，说明它确实没有键位绑定，要用 Mx 调）。

原书的建议是别用这两个命令，去适应撤销环。原书作者的理由我觉得很值得转述：这个概念在 Emacs 里到处都是——register 轮转、mark ring、minibuffer 历史、tab bar 历史，全是「环」而不是「栈」。学会环，其他地方就都通了。

进阶：撤销记录存在哪、会丢吗

撤销信息存在 buffer 里（所以它跟着 buffer 走，切换 buffer 不会丢），但会被回收。手册给了三个以字节为单位的变量，我在 Emacs 32.0.50 上实测了默认值：

  • undo-limit，默认 160000 字节——软上限。Emacs 会保留足够多的历史到达这个大小，但不会为更早的改动继续保留。
  • undo-strong-limit，默认 240000 字节——硬上限。任何（除了最近一次）超过这个体积的历史会被丢弃。
  • undo-outer-limit，默认 nil——即使用内部默认值。手册说是 24,000,000 字节（24 MB）。超过它 Emacs 会丢掉全部撤销数据并警告你，「这是唯一一种你无法撤销最后一条命令的情况」。

结论很实用：你在正常写代码时几乎不可能撞到这些上限，因为撤销数据会被逐步回收；只有一次改动大到几十 MB 才会出问题。

另一条冷知识（同出自 Undo 节点）：名字以空格开头的 buffer 永远不记录撤销信息。如果某个临时 buffer 里东西被误改了，是撤不回来的。

还想更进一步的话，Emacs Wiki 上有个广受欢迎的第三方包 Undo Tree，它把撤销环画成一棵可点击的树，直观显示「哪条分支是我正在走的、哪条是你撤回去的」。原书脚注也提了它。它不在 Emacs 自带里，需要自己从 MELPA/ELPA 或源码安装。

练习 8　你写了三行文本，连按三次 C/ 全撤掉了，然后突然觉得第三行写得不好。你想在别的编辑器里那样「撤销一次把第三行变回来」——Emacs 里怎么做？再进一步，如果你连撤了三次又改了点别的，再按 C/ 会发生什么？

Emacs 的做法是把重做当成撤销的一部分：那串「撤销」本身已经被记进了撤销环，所以再按 C/，撤掉的就是「你刚才撤了三下」这个动作本身，效果正是把第三行变回来。手册 Undo 节点原话：「the entire sequence of undo commands that you have just performed are themselves placed into the undo record」。

第二个问题也一样：打断之后（比如你移动了光标或敲了新字），C/ 会先「撤销你打断前的那串撤销」= 重做，然后继续往后撤更早的改动。结论就是在 Emacs 里撤销历史几乎不可能真的丢掉。

如果你实在想要别的编辑器那种干净的 undo/redo，用 Mx undo-only（只撤不重做）和 C?（undo-redo，显式重做）。原书作者建议别用，把环学明白更划算。

练习 9　你在 minibuffer 里输到一半，突然想取消这次输入；或者你不小心敲了个 3 变成「接下来要做三次」的前缀。哪个键能一次解决这两种情况？它有什么副作用？

连敲三次 ESC（keyboard-escape-quit，我实测绑定确认）。它会取消 minibuffer 的输入、取消数字前缀、退出递归编辑，并把所有 window 收成一个。

副作用就是最后那条：如果你正开着三四个 window，一按就全没了。这个「回到最基本状态」正是它的设计意图，但在你精心摆好布局时是件大事。防一手的方法是开 winner-mode（Mc < left 撤销窗口操作），或者干脆用标签栏把布局固定下来——这正是第八节和第十节的内容。

顺带一提：Cg（keyboard-quit，我实测绑定确认）也能中止很多操作，但它是通用中止，行为不如 ESCESCESC 这么「一键归位」。

撤销窗口操作：winner-mode

窗口操作最容易出「手滑」——想 Cx 3 结果按成了 Cx 2。Emacs 自带一个次模式专门对付这个：winner-mode（默认关闭）。开了之后它会记住你的每一次窗口操作，可以用 Cc < left 退回去、Cc < right 前进。

我实测确认了：这两个键默认没有绑定（(key-binding (kbd "C-c <left>")) 返回 nil），只有开了 winner-mode 之后才变成 winner-undo 和 winner-redo。写进初始化文件：

(winner-mode 1)
技巧

winner-mode 和后面第十节要讲的 tab-bar-history-mode 默认抢同一对键：我实测 tab-bar-history-mode 开启后 Cc < left 变成 tab-bar-history-back、Cc < right 变成 tab-bar-history-forward（原书写这本书时这两个命令还没有默认键位，需要自己绑——这是它和今天的一处差别）。两个都开的话，赢的一定是 winner-mode，和谁先开后开无关（我两种顺序都试过：先开 tab-bar-history 再开 winner 是 winner-undo，反过来也是 winner-undo）——因为 winner-mode 的次模式键表在查找顺序上比 tab-bar-history-mode 写在全局键表里的绑定更靠前。想都用就自己挑一对没被占的键。原书脚注也提醒过这一点。

按方向切窗口：windmove

windmove 是 Emacs 自带的（不用装包），提供按罗盘方向移动光标的能力，而不必循环 Cx o。在初始化文件里加一行：

(windmove-default-keybindings)

实测结果：执行后 S< left、S> right、S↑、S↓ 分别绑定到 windmove-left / windmove-right / windmove-up / windmove-down（我实测 (key-binding (kbd "S-<left>")) 等四项成立，而 (key-binding (kbd "S-<")) 这类「字符版」写法返回 nil——不要把它们和方向键弄混）。按住 Shift 加方向键就从「移动文本光标」变成了「在窗口之间跳」，各跳各的，互不干扰。原书写的就是这四个键。

易错

代价是 Shift 选择没了。手册 Window Convenience 节点明确提醒：windmove-default-keybindings 把命令绑到 S-方向键 上，而这么做的结果是 这些键的 Shift 选择功能会被关掉（*"doing so disables shift selection for those keys"*）。也就是说以后你没法用 S+方向键选文本了。

手册还给了另外三组可选的默认绑定，你要是不想要这个副作用就换一组用：windmove-display-default-keybindings（为「下一条命令要把 buffer 显示到哪个方向」提供绑定）、windmove-delete-default-keybindings（方向删除 window）、windmove-swap-states-default-keybindings（方向交换两个 window 的内容）。

要点

如果你不想动 Shift，改绑到别处也可以，但先查一下你要占的那几个键现在绑了什么。我在本机 Emacs 32.0.50 上实测的默认绑定是：M< left 和 M> right 已经是 left-word / right-word（按词左右移），M< up 和 M< down 才是真正的空绑定。好消息是：被占的 left-word / right-word 另有备份（C< left / C> right 同样是按词移动），而 beginning-of-buffer / end-of-buffer 在 M<、M>、C< home、C< end 四处都有绑定，覆盖 M 方向键不会让你丢掉「跳到文件首尾」。

(global-set-key (kbd "M-<left>")  'windmove-left)
(global-set-key (kbd "M-<right>") 'windmove-right)
(global-set-key (kbd "M-<up>")    'windmove-up)
(global-set-key (kbd "M-<down>")  'windmove-down)

练习 10　你在左边 window 编辑 a.txt，右边 window 放着 b.txt。你想把右边的 buffer 换成 c.txt。有几种做法？哪种最省按键？

两种做法：

  1. 笨办法：Cx o 跳到右边 → Cx b 换 buffer → 打完字再 Cx o 跳回来。三段操作。
  2. 一步到位：Cx 4 b（switch-to-buffer-other-window，实测绑定确认），在另一个 window 切 buffer 并且跳到那个 window。一段操作。

「另一个 window」大致就是「当前 window 之后的那个」（按 window 的环形顺序找）——所以如果你当前正好在右边，Cx 4 b 会作用到左边那个。这在只有两个 window 时无所谓，窗口一多就得先看清自己在哪。

要点

它内部调用的是 display-buffer：如果 frame 里确实没有别的 window 可用，Emacs 会现分裂一个出来。但不是无条件的——变量 split-height-threshold（默认 80）和 split-width-threshold（默认 150）管的是「现有窗口够不够大，值得再分一刀」。按 window.el 里的原始定义：split-height-threshold 是「window 至少要有这么多行，split-window-sensibly 才允许纵向分裂」，split-width-threshold 同理按列算。唯一的例外是：当这个 window 是 frame 里唯一一个，或者其余窗口都是 dedicated，那时可以无视这个值照分不误。所以在一个只有 40 行的终端里，只有这一个 window 时你按 Cx 4 b 还是会分；等到你有了两三个 window、每个都不够高，它就不肯再分了。两个变量都用 Mx customize 改，本书作者在 Emacs 32.0.50 上确认过这两个默认值（split-height-threshold 的 :version 标的是 23.1，也就是 Emacs 23 起就是这个默认）。

练习 11　你想把屏幕分左右两块，但按了 Cx 2。怎么改回来？另外，分裂完成后光标（point）留在哪个 window 里？

Cx 2 是上下分，Cx 3 才是左右分。记法：数字 2 像上下两行，数字 3 像竖着切三块的右侧那块。这只是助记，Emacs 本身没有强制约定。

分裂完成后，光标留在原来那个 window（上面或左边），新 window 虽然已经创建但没被选中。手册 Splitting Windows 节点确认了这点。所以你通常要立刻按一下 Cx o 跳进新 window。

补救办法：手滑了就按 Cx 1（delete-other-windows）清掉重来；或者一开始就开 winner-mode，用 Cc < left 退回去。

九、frame：Emacs 的「GUI 窗口」，以及它今天为什么不好使

现在可以正式介绍 frame 了。用一句话复述官方手册 Frames 节点的定义：Emacs 跑在图形界面时，会占一个系统级的图形显示区域，手册管它叫 frame，并且把这个词专门留给它，而把「显示 buffer 的那块区域」留给 window。

所以：别的编辑器里说的「窗口」= Emacs 的 frame；别的编辑器里的「分屏格子」= Emacs 的 window。这就是为什么原书在这一节专门加了一句「frame 在终端 Emacs 里也能用」——终端 Emacs 的 frame 是整块终端屏幕，同一时刻只能显示一个。

还有一个值得知道的便利行为：如果那个 buffer 已经在某个 frame 里可见，Cx 5 系列会直接切到那个 frame，而不是新建一个。手册 Creating Frames 节点原话是：「If an existing visible or iconified frame already displays the requested buffer, that frame is raised and deiconified」。所以 Cx 5 f 打开一个你正开着的文件时，不会多出窗口，只是把那个 frame 抬起来。

今天的实际情况：frame 体系比原书写的时候更不好用

原书写这段时对 frame 的评价就已经偏保守了：所有 frame 共享同一个 Emacs 会话，管理起来「有点别扭」，作者建议「试试看合不合手」。这个评价在今天的 Wayland 和 macOS 上更成立了，原因不是 Emacs 的代码退化了，而是桌面环境变了。下面是我在本机能核实的部分——引用全部来自本机安装的 Emacs 32.0.50 手册和 etc/NEWS.* 原文。

易错

Wayland：窗口的位置不由 Emacs 决定。手册 Environment Variables 节点里关于 WAYLAND_DISPLAY 只有一句：「Pgtk Emacs (built with --with-pgtk) can run on Wayland natively.」也就是说 Wayland 上的图形 Emacs 走的是 GTK 那一套纯 GTK 构建（--with-pgtk）。

而 etc/NEWS.29 里对这个构建有一段明确的警告，照抄要点：这个构建可以跑在任何 GDK 支持的窗口系统上（Wayland、Broadway 等），但作者建议只在你用的窗口系统不是 X 的时候才用它；在 X 上跑它「已知有问题」（known to have problems），具体表现为「令人不快的 frame 定位（undesirable frame positioning）」和各种键盘序列输入问题，并点名了 C; 和 CSu 这类键。

这条 NEWS 出自 Emacs 29 的开发期，它说明两件事：一是 Wayland 上的 Emacs 是「能用」的，二是这条路上仍有已知毛刺。我没有办法在本机（X11 与 Wayland 环境都在，但无法判定 Emacs 32.0.50 在 Wayland 下的实际表现）验证今天的状态，也无法联网核对最新的 bug 进展——如果你的 Wayland 桌面下 Emacs 的 frame 行为异常，第一时间该看的是 *Messages* buffer 和 Mx report-emacs-bug，而不是硬调参数。

要点

合成器带来的另一个坑，Emacs 30 才补上。etc/NEWS.30 里有一条：「Emacs now updates invisible frames that are made visible by a compositor.」——意思是「如果一个被 Emacs 判定为不可见（invisible）或已图标化的 frame 被合成器（compositor）显示出来了，Emacs 现在会重绘它」。此前这类 frame 因为 frame-visible-p 返回 nil 而不刷新，症状是「窗口出现了但内容是花的、或者干脆空白」。这是典型的「Emacs 的窗口模型和现代桌面合成器的模型对不上」的 bug，而它到 Emacs 30 才被修。

技巧

macOS：先搞清楚你的 Emacs 是哪种构建。本机安装的 Emacs 32 手册在附录 F（Emacs and macOS / GNUstep）里写得很清楚：「On macOS, Emacs can be built either without window system support, with X11, or with the Cocoa interface; this section only applies to the Cocoa build.」手册还解释了为什么相关命令都以 ns- 开头：「Emacs uses the term ‘Nextstep’ internally, instead of ‘Cocoa’ or ‘macOS’」。

Cocoa 构建上还有几条 frame 相关的行为差异，举两个手册原文点名的：ns-use-native-fullscreen（是否使用系统原生全屏，手册注明原生全屏需要 macOS 10.7 及以上）；工具栏的处理——「NS builds consider the tool bar to be a window decoration, and therefore do not display it when a window is undecorated」，以及「On macOS the tool bar is hidden when the frame is put into fullscreen, but can be displayed by moving the mouse pointer to the top of the screen」。也就是说 macOS 上 Emacs frame 的行为和 X11 上并不完全一样。具体你的构建是哪种，判据是 M: 执行后看 system-configuration-features 里有没有 ns 这一项——这一步需要你自己在 macOS 上确认，我没有 macOS 机器可验。

顺带说清一件事：native-comp 和 frame 没关系

很多人把「Emacs 28+ 改了 native-comp」和「Emacs 的窗口系统在现代桌面下有问题」混在一起讲，但这两件事是分开的。核对本机 etc/NEWS.28 和 NEWS.29 的原文，事实是这样：

  • Emacs 28「optionally supports native compilation of Lisp files」——构建时加 --with-native-compilation 开启，依赖 libgccjit，这是把 Elisp 在运行时用 JIT 编译成本机代码，目标是让 Lisp 跑得更快。
  • Emacs 29 让这件事更好用了：可以用 --with-native-compilation=aot 请求把整棵 Emacs 源码树里的 Lisp 全部提前（AOT，ahead-of-time）原生编译。NEWS 原文承认：「This feature existed in Emacs 28.1, but was less easy to request.」同版还新增了 native-compile-prune-cache 命令，并让 symbol-file 能报告 .eln 文件。
  • Emacs 31 又补了 native-compile-directory 函数和 native-comp-async-on-battery-power 选项。
要点

所以准确的结论是：native-comp 解决的是启动速度和运行速度，跟 frame 在 Wayland/macOS 下好不好用完全是两码事。你如果看到有人说「装上 native-comp 就没有多窗口问题」，那是不成立的；native-comp 影响的是 Emacs 启动时加载你的配置快不快。本书第 13 章会专门讲这件事，这里点到为止。

唯一真正把两者连起来的地方是上一条：native compiler 发出的警告也会受 warning-display-at-bottom 影响——所以一个用 native-comp 的配置里，编译警告同样会在 frame 底部开窗口。

所以你该怎么办

三条实用建议：

  1. 多显示器时用 frame。这是它唯一无可替代的场景——你想让 Emacs 在两个物理屏幕上各占一块并且互不干扰地滚动，这是平铺式窗口管理器和标签栏都做不到的。Emacs 内部完全支持一块屏幕一个 frame。
  2. 同一块屏幕上，别用 frame，用标签栏。下一节的 Tab Bar 就是「像 frame 一样的逻辑分组，但不用真的开多个系统窗口」，原书作者也是这么定位它的。
  3. 用了平铺式窗口管理器（i3、Sway、Hyprland、niri 之类）就别用 frame。窗口管理器会接管 frame 的摆放，Emacs 再去争就会打架。这一条是我的经验判断，不是手册规定：你自己试一次就知道冲突在哪。

练习 12　有人说「Emacs 的窗口」，可能指系统窗口，也可能指 frame 里的一块区域。「我要关掉这块区域」和「我要关掉整个 Emacs 应用窗口」分别按哪个键？哪个键特别容易被按错？

「关掉这块区域」是删 window：Cx 0（delete-window），只影响当前这个 window，buffer 还在。「关掉整个 Emacs 应用窗口」是删 frame：Cx 5 0（delete-frame），Emacs 进程继续跑，其他 frame 和所有 buffer 都在。

最容易按错的是 Cx 5 0 和 Cx 5 o：一个数字零、一个字母 o，位置一样含义完全相反——o 是切到另一个 frame，0 是把当前 frame 关掉。手册 Frames 节点专门加了一句括号提醒「that is zero, not ‘o’」，可见连文档作者都觉得需要标出来。

同一规律也覆盖 window：Cx o 切 window、Cx 0 删 window。所以字母 o 表示「移动过去」，数字 0 表示「把它删掉」，这套规律在 window 和 frame 两套键位里都成立。

十、标签栏与标签行：Emacs 27 起内置的「那一排 tab」

Emacs 一直没有浏览器那种「标签栏」，是它被吐槽很多年的点。Emacs 27 一口气加了两个内置功能，解决两个不同的问题——原书这一节的标题就是「Tab Bars and Tab Lines」，别把它们混成一个东西：

  • Tab Bar（标签栏）：位于 frame 顶部，每个「标签」是一整套 window 配置（这个 frame 被怎么分成几块、每块放哪个 buffer）。它对应 IDE 里的「工作区 / 项目」。前缀键是 Cx t。
  • Tab Line（标签行）：位于每个 window 顶部，每个「标签」是这个 window 曾经显示过的 buffer。它才对应浏览器 / VS Code 那种「一排文件标签」。用 Mx global-tab-line-mode 开关。
要点

这两者的区别在手册里说得很明确（Tab Bars 与 Tab Line 两个节点都写了）：Tab Line 的标签用来在同一个 window 内换 buffer，Tab Bar 的标签用来在不同的 window 配置之间切换。想「同时看四个 buffer」用 Tab Bar；想在同一个格子里来回翻 buffer 用 Tab Line。

Tab Bar：把一整套窗口布局存成一个标签

原书对这个功能的定位很准：Tab Bar 相当于「有名字的、持久的窗口配置」，像 IDE 的工作区。如果你经常在「日程 + 邮件」和「代码 + 终端」这两套布局之间来回切，每个标签就是一套。

开启方式三选一：Mx tab-bar-mode（临时，立即生效，对所有 frame 生效）、Mx customize-option RET tab-bar-mode RET（图形化改默认值并保存）、或者写进初始化文件：

标签页历史：tab-bar-history-mode，以及它和原书不一样的地方。标签页的窗口布局也容易乱掉，你需要一个「退回刚才那套布局」的机制，这就是 tab-bar-history-mode（默认关）。开启方式：Mx customize-option RET tab-bar-history-mode RET，或者写 (tab-bar-history-mode 1)。

和原书的差别：原书说「在能在历史里前后走的命令没有绑定按键，你需要自己写两行绑定」，并给出：

(global-set-key (kbd "M-[") 'tab-bar-history-back)
(global-set-key (kbd "M-]") 'tab-bar-history-forward)

在 Emacs 32.0.50 上我实测：这两个命令仍然存在（(commandp 'tab-bar-history-back) 为真），但现在已经自带默认键位了——开启该模式后 Cc < left 变成 tab-bar-history-back、Cc < right 变成 tab-bar-history-forward（未开启时这两个键实测是空绑定）。所以今天你不用再写那两行了，直接开模式即可。

同时提醒：winner-mode 也用 Cc < left / Cc < right，而且两者同开时永远是 winner-mode 赢（不是「后开的赢」——我两种顺序都实测过，结果一样）。想让 tab 布局历史也能用，得自己另绑一对键。

十二、常见误区速查

  • 「window 是屏幕上的那块区域」——错。window 是 frame 内部的显示区；屏幕上能拖动的那个叫 frame。判断方法：能拖到第二块显示器上去的，是 frame。
  • 「Emacs 乱开窗口是 bug」——不是。帮助、编译、shell、甚至警告信息都会新开一个 window，这是设计。Emacs 30 起警告固定开在 frame 底部（warning-display-at-bottom，默认 t）。
  • 「Cx Cf 是打开文件」——半对。它同时是「新建文件」，两者走同一条命令，这是 Emacs 有意的设计。
  • 「不用了就 Cx k 关掉」——没必要。buffer 留着几乎不占额外内存，直接 Cx b 切走就行。
  • 「撤销是线性的，撤销后再改就丢了」——在 Emacs 里不成立。撤销动作本身也在撤销环里，见第七节。
  • 「Cx 5 0 是切 frame」——错。o（字母）才是切，0（数字）是删。
  • 「标签栏和标签行是一个东西」——不是。标签栏在 frame 顶部、管的是窗口配置；标签行在 window 顶部、管的是 buffer。而且它们和窗口工具栏抢同一块位置。
  • 「要用 FIDO 得先装包」——Emacs 27 以后不用。FIDO 已并入内置的 Icomplete，Mx fido-mode 直接可用（Emacs 32 的安装目录里已经没有 fido.el 这个文件了，我实测确认）。
  • 「把 use-completion 设成 t 就能开新补全」——在 Emacs 32 上会报错。这个变量在本机全部源码和手册里都查不到。
技巧

练习 13　用一句话分别解释这四个词：window、frame、tab bar、tab line。它们各自「管理」的是什么？

window：frame 内部的一块显示区域，显示一个 buffer；Emacs 的 window 是随用随建、用完就删的临时工位，不是固定格子。frame：你在任务栏上看到、可以拖动和最小化的那个操作系统窗口，里面装着若干 window。tab bar：frame 顶部那一排标签，每个标签是一整套window 配置（怎么分屏、每块放哪个 buffer），对应 IDE 的工作区。tab line：每个 window 顶部那一排标签，每个标签是这个 window 曾经显示过的buffer，对应浏览器 / VS Code 的文件标签。

记忆口诀：frame 装 window，tab bar 管 window 的排法，tab line 管 window 里的 buffer。

再补一个实战细节：tab line 和窗口工具栏占同一块屏幕位置，同一时刻只能显示一个（手册 Tab Line 与 Window Tool Bar 两个节点都写了这点）。

练习 14　你想试一下「标签栏」，又不想在顶部留一行碍眼。分别用什么命令开？开完之后怎么把那一行藏起来（功能还保留）？

标签栏（Tab Bar）用 Mx tab-bar-mode 开，或在初始化文件写 (tab-bar-mode 1)。它默认是关的（我实测 tab-bar-mode 默认 nil）。标签行（Tab Line）用 Mx global-tab-line-mode 开，同样默认关（实测 global-tab-line-mode 默认 nil）。

隐藏标签栏但保留功能：把 tab-bar-show 设成 nil。手册 Tab Bars 节点明确说：设成 nil 后「仍然可以在不显示标签栏的情况下，用 tab-next、tab-switcher 等提供标签名补全的命令在命名的窗口配置之间切换」。tab-bar-show 的默认值我实测是 t，它的其他取值还有 1（只有一个标签时隐藏）和正整数（标签数超过它才显示）。

如果你要的其实是「window 顶部那排 buffer 标签」，那应该开 global-tab-line-mode 而不是 tab-bar-mode。这两个名字里的 bar 和 line 就是「frame 顶部」和「window 顶部」的区别。
