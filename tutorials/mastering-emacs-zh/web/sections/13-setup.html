十三、现代安装与配置工程

前十二章讲的是「Emacs 里面怎么用」。这一章讲外面那一层：在哪个平台装、装哪个版本、配置文件放哪、包从哪来、启动为什么慢、坏了怎么救。读完你手里会有一套能长期用、能搬到第二台机器、坏了能在五分钟内定位问题的 Emacs 环境。

要点

本章所有关于「某个变量存不存在、默认值是什么、某个包是不是内置」的断言，都在本机 GNU Emacs 32.0.50 上用 emacs --batch -Q --eval '…' 与 locate-library 实际跑过；涉及版本起点的部分，对照 Emacs 28/29/30/31 的 NEWS 原文（etc/NEWS.29 等）与 31.1 发行包的 doc/emacs/*.texi 手册原文逐条核对。凡是我无法核实的说法，正文里会直接写「未能核实」，不拿猜测凑数。

一、先做一个决定：你在装「一个程序」还是在装「一份可复现的环境」

零基础读者最常犯的第一个错误，是一上来就纠结「装哪个 Emacs」。其实在敲第一条安装命令之前，你要先回答一个更上层的问题：你希望这台机器上的 Emacs 长什么样，多久之后还能再装出同样的一份？

这个问题有两个极端，中间是绝大多数人的位置。

  • 模型一：装程序。用发行版包管理器、Homebrew、官方安装器装一个二进制，配置写在自己电脑上。它更新得慢（要等发行版打包），但零折腾。
  • 模型二：装可复现环境。用 Nix 或 Guix 这样的声明式包管理器，把「Emacs 本体 + 系统库 + 你的配置」写成一份声明文件。好处是任何一台 Linux 机器上都能一键还原同一份环境，代价是你要额外学一套语言和一个哲学。

本节的判断很直接：如果你是第一次用 Emacs，先走模型一。理由很实在——模型二出问题时，你分不清是 Emacs 配置错了，还是 Nix/Guix 表达式写错了，两套系统同时报错会让你完全无从下手。等你用 Emacs 满三个月、配置超过三百行、并且已经开始关心「我的包到底装了哪些版本」的时候，再迁移到模型二，成本最低。

反过来说也有该直接选模型二的人：你要在一台不属于自己的机器上工作（比如公司发的开发机、CI 容器、临时租的云主机）；或者你用 Emacs 做的是需要长期一致性的事（比如维护十年的文档、发布到 App Store 的 Org 导出）。这种情况下「重现一次环境」比「调好一次环境」重要得多。

易错

很多人在装 Emacs 之前先装一堆包，期望「装完之后一切都是现成的」。这是本世纪最常见的时间浪费。Emacs 的配置生态里有大量包已经十几年没更新了——在 2026 年从 MELPA 上装包之前，至少先看一眼它的仓库最近一次提交是什么时候（本章后面会给具体命令）。装了一个 2017 年最后提交的包，你会花两天时间查一个已经被修好或者被废弃的问题。

二、Linux：三条路，先看你的发行版给了什么

Linux 上装 Emacs 有三条路：发行版仓库、第三方仓库（有的第三方 APT 源、Homebrew on Linux、Nix）、自己编译源码。对初学者的建议顺序是：发行版仓库 → 第三方仓库 → 源码编译，理由是每往后一条路，自由度越大，出问题时能查的东西越少。

2.1 先看看你的发行版给的是什么版本

动手之前先查版本。Emacs 的功能差异很大，29 和 32 之间差着好几年的东西，而各发行版的打包节奏完全不同。

# Debian / Ubuntu
$ apt policy emacs-nox | head -3
  Installed: (none)
  Candidate: 28.2

# Fedora / RHEL
$ dnf info emacs-common | head -5

# Arch
$ pacman -Si emacs | grep -E 'Version|Repository'

# NixOS（配置在 /etc/nixos/configuration.nix 里）
$ nix eval --raw nixpkgs#emacs.version

看到 28.x 不必恐慌：28 自带 project.el（25.1 起）、display-line-numbers（28 起），日常够用了。但有两件事要提醒：use-package 和 eglot 都是 Emacs 29 才进本体的（NEWS.29 各给了独立小节），在 28 上它们还是第三方包；Completion Preview 是 Emacs 30 才有的（completion-preview-mode，NEWS.30），而 31 才带来 treesit-x.el 那批简易 tree-sitter 模式。想要这些，就得升级。下面按「你能接受多少折腾」给三档方案。

2.2 方案 A：发行版仓库（最省事）

# Debian / Ubuntu / Mint
$ sudo apt update
$ sudo apt install emacs-nox        # 纯终端版，不要 X11
$ sudo apt install emacs           # 带图形界面（会拉一堆 GTK 依赖）

# Fedora
$ sudo dnf install emacs-enhanced   # 带 X 的界面
$ sudo dnf install emacs-terminal   # 纯终端

# Arch
$ sudo pacman -S emacs

# NixOS（写在配置里，然后 nixos-rebuild switch）
$ sudo nix-env -iA nixpkgs.emacs
技巧

emacs-nox 和 emacs 的区别只在图形界面。如果你在 X11、Wayland 或 SSH 里跑 Emacs，就装带界面的那个；如果你只在终端里跑（tmux + ssh 是很多人的常态），装 -nox 版本会少拖几十兆 GTK 依赖，启动也快一点。

方案 A 的代价要说清楚：发行版的包是「够用就好」的构建——往往有一批额外特性被关掉。比如 Debian 的 emacs-nox 默认不带 tree-sitter（NEWS.29 记录 tree-sitter 是编译期选项 --with-tree-sitter），不带某些字体支持，也不带最新版本的原生编译（native compilation）优化。而且它不会自动升级——你可能要等一两年才能从 28 跳到 29。

2.3 方案 B：官方二进制 / 第三方仓库（中间档）

GNU 官方在 ftp.gnu.org/gnu/emacs/ 下发布的预编译二进制只有 Windows 版（下面第三节会讲），Linux 上没有。所以 Linux 上的「二进制」都是别的项目打包的：

  • 第三方打包的 APT/DEB 仓库（业界常提到的是 Erlang Solutions 的 APT 源）。这一条我无法在本次写作中核实——我既没装也没访问他们的站点，所以请你在采用之前自己确认它当前的仓库地址、支持哪些发行版、以及它构建 Emacs 时开了哪些开关。
  • Homebrew on Linux（brew install emacs，注意是 formula 不是 cask——Homebrew 的 cask 是 macOS 独有的机制，Linux 上没有 cask 这条路），包多、更新快，但在一台机器上再装一整套 Homebrew 本身有额外成本。
  • nixpkgs 本身（不走 NixOS 也行，见第五节）。
# 在 Debian/Ubuntu 上用 Nix 只装 Emacs，不装 NixOS
$ curl -L https://nixos.org/nix/install | sh -s -- --daemon
$ nix profile install nixpkgs#emacs-gtk       # 装带界面的
$ nix profile install nixpkgs#emacs            # 装终端版
$ emacs --version | head -1

# Homebrew on Linux（只有 formula，没有 cask）
$ brew install emacs

2.4 方案 C：源码编译（最后的手段）

只有在你明确需要某个发行版没开的功能时才值得。比如你需要一个带 tree-sitter 的 Emacs，或者你要调试 Emacs 本身。步骤是标准的 GNU 三件套，但有几个坑：

$ wget https://ftp.gnu.org/gnu/emacs/emacs-31.1.tar.xz
$ tar xf emacs-31.1.tar.xz && cd emacs-31.1
$ ./configure --prefix=$HOME/.local \
              --with-native-compilation \
              --with-tree-sitter \
              --with-x-toolkit=gtk3
$ make -j"$(nproc)"     # 并行编译，这一步要 10~40 分钟
$ make install
$ echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
易错

源码编译最大的坑不是编译本身，而是它把 Emacs 和系统库焊死在一起。你的 Emacs 会链接你自己装的 GTK、自己的 harfbuzz、自己的 libgccjit。半年后你升级系统库，Emacs 突然起不来了，而这类「起不来」通常没有清晰的错误信息。所以：编译完请立刻记下 ./configure 的完整命令，或者干脆把命令行写成一个 build.sh 提交进你的 dotfiles。

编译完记得验证这两个开关到底生效没有，这是本节最实用的一条检查：

$ emacs --batch -Q --eval '(princ (format "native-comp: %S\n"
    (locate-library "native-comp")))'
native-comp: "/usr/share/emacs/31.1/lisp/emacs-lisp/native-comp.elc"
;; nil 就说明这个 Emacs 是 --with-native-compilation=no 编出来的

$ emacs --batch -Q --eval '(princ (format "treesit: %S\n"
    (locate-library "tree-sitter")))'
treesit: nil

我在本机跑出来的结果就是 native-comp: nil 和 treesit: nil——这台机器上的 Emacs 32.0.50 是不带原生编译、不带 tree-sitter 构建的。所以本章讲到原生编译那节，我会告诉你怎么自己确认，而不是假设它有。

三、Windows：官方安装器、Scoop、winget、MSYS2

Windows 是唯一有GNU 官方预编译二进制发行版的主流平台。GNU Emacs 官方在 ftp.gnu.org/gnu/emacs/windows/ 下按版本目录发布 Windows 构建。我拉了 emacs-31/ 那个目录，里面同一个版本有四类东西：emacs-31.1.zip（免安装包）和 emacs-31.1-installer-UCRT64.exe（图形安装器）各有一份，而且每个都还有 -UCRT64 与非 -UCRT64 两个变体，另外还有 -nodeps（不带依赖 DLL）和 -deps（单独给依赖 DLL）版本。装 31.1 你要认准 emacs-31.1.zip 或 emacs-31.1-installer-UCRT64.exe 这两个名字。

我在本章写作时从 winget 的官方清单仓库（microsoft/winget-pkgs）里读到的 31.1 条目是这样的：

# microsoft/winget-pkgs/manifests/g/GNU/Emacs/31.1/
PackageIdentifier: GNU.Emacs
PackageVersion: "31.1"
InstallerType: nullsoft
Scope: machine
InstallModes: [interactive, silent, silentWithProgress]
InstallerUrl: https://ftp.gnu.org/gnu/emacs/windows/emacs-31/emacs-31.1-installer-UCRT64.exe
ReleaseDate: 2026-08-24

也就是说 Windows 官方安装器是 NSIS 打包的，支持静默安装，这一点在企业环境里很关键（--silent 开关）。

3.1 方案 A：官方 zip 免安装（最可控）

# 1. 下载 emacs-31.1.zip，解压到 C:\tools\emacs-31.1
# 2. 把 C:\tools\emacs-31.1\bin 加进 PATH
# 3. 之后在 PowerShell 里直接
emacs --version

取舍：这个版本完全在你的用户目录下，卸载就是删文件夹，没有注册表残留，没有提权，是最容易「装坏了就重来」的方式。代价是没有开始菜单快捷方式、文件关联、PATH 需要手动改。

3.2 方案 B：官方图形安装器

# 下载 emacs-31.1-installer-UCRT64.exe 后双击安装
# 静默安装（企业批量部署用）：
emacs-31.1-installer-UCRT64.exe /S /D=C:\tools\emacs-31.1

取舍：安装器会创建开始菜单项、注册 run.exe、emacsclient 的路径，也支持 emacs -nw（无窗口模式）。需要管理员权限（Scope: machine）。卸载要通过「设置 → 应用」面板。

要点

文件名里的 UCRT64 是指它链接的是 Universal C Runtime，这是 Windows 10 以后系统自带的 C 运行库。同一目录里不带 UCRT64 的那个变体链接的是老的 MinGW-w64 运行库，只适合更老的 Windows。更早的 Emacs（27.x 及以前）用的就是 -w64 这种命名；从 Emacs 28 起官方主推的就是 -UCRT64，31.1 的目录里已经没有 -w64 文件了。所以你下载时认准 -UCRT64 就对了。

3.3 方案 C：Scoop

PS> scoop bucket add extras
PS> scoop install emacs
PS> scoop update emacs
PS> scoop info emacs       # 看版本、来源、许可证

我读到的 ScoopInstaller/Extras 仓库里 bucket/emacs.json 的内容是：版本 31.1，许可证 GPL-3.0-or-later，下载地址 https://ftp.gnu.org/gnu/emacs/windows/emacs-31/emacs-31.1.zip。注意两点：

  • 它装的是 zip 版，不是安装器版，所以不写注册表、不需要管理员权限，卸载就是删目录。清单里把可执行文件链到 Scoop 的 shims 目录，emacs 命令照常可用。
  • 它照样会建开始菜单快捷方式。清单里有一段 "shortcuts"，给 bin\runemacs.exe 和 bin\emacsclientw.exe 各建一个开始菜单项（后者还带 -c -n -a "" 参数）。所以「zip 版就没有快捷方式」是个常见误解。
  • 该清单的 notes 字段写着「32 位版本请装 versions/emacs27.2」，也就是说 Scoop 的 64 位 Emacs 不支持 32 位 Windows。

取舍：Scoop 的强项是用户态、免管理员、一条命令装一串东西，并且 scoop update * 能批量更新。如果你的 Emacs 配置依赖 git、ripgrep、fd、fzf 这些外部程序（本书第 14 章的工作流会大量用到），Scoop 一次装齐非常舒服。

3.4 方案 D：winget（Windows 10/11 内置）

PS> winget search emacs
PS> winget install GNU.Emacs
PS> winget upgrade GNU.Emacs
PS> winget list --id GNU.Emacs

取舍：winget 是 Windows 10 1809 以后系统自带的，不需要额外安装任何东西，这是它相对 Scoop 最大的优势——很多新机器上根本没人装过 Scoop。清单由社区维护，但 `GNU.Emacs` 这个条目我验证过是存在的，且指向官方 ftp.gnu.org。

技巧

emacsclient + -daemon 是在 Windows 上体验 Emacs 的关键。以 daemon 模式启动一次之后，后续每次编辑都只是把文件丢给已有的 Emacs 进程，启动时间从两三秒降到几十毫秒。Windows 上建议开一个 PowerShell 终端先跑 emacs --daemon，然后用 emacsclientw（带窗口）或 emacsclient（纯终端）连上去。

3.5 方案 E：MSYS2（Mintty 用户选这个）

# MSYS2 的 MinGW64 环境（包名在 pacman 里带 x86_64 前缀）
$ pacman -Syu
$ pacman -S mingw-w64-x86_64-emacs
$ pacman -S mingw-w64-x86_64-emacs-pdf-tools-server   # 可选，pdf-tools 的配套
# 纯 MSYS 环境版本
$ pacman -S emacs

我在 MSYS2 的软件包索引（我拉了 repo.msys2.org/msys/x86_64/ 和 repo.msys2.org/mingw/mingw64/ 两个仓库的索引）上查到的当前版本是：emacs 31.1-1（MSYS 环境）、emacs 31.1-2（MinGW-w64 环境）、emacs-pdf-tools-server 1.3.0-1。注意 MSYS2 仓库里同时躺着多个历史版本（比如 mingw64 里还有 emacs 31.1-1 和 emacs 30.2-8），pacman 装的是仓库版本号最高的那个。

取舍：MSYS2 版本的好处是自带 Mintty（带滚动条和复制粘贴的终端模拟器），适合在 Windows 上习惯终端工作流的人。坏处是引入了整整一层 MSYS2 环境（bash、pacman、依赖链），如果你只是想编辑文本文件，这是杀鸡用牛刀。

本节相关命令

命令命令名作用
emacs --version—确认装的是哪个版本
emacs -Q—完全跳过所有配置启动，排障用
emacs --debug-init—让 init 文件里的报错进入调试器
emacs --daemon—以守护进程模式启动，不开窗口
emacsclient -nw FILE—把文件交给已在运行的 Emacs，纯终端窗口
emacsclientw FILE—同上，但打开图形窗口

练习 1　在 Windows 上你已经用 emacs --daemon 起过一个后台 Emacs，现在想用当前这个 PowerShell 窗口编辑 notes.txt，又要保留 Emacs 的 GUI 能力，该敲哪条命令？

emacsclientw notes.txt。带 w 后缀的版本会弹出独立窗口；如果你要的是在当前终端里编辑，用 emacsclient -nw notes.txt。

练习 2　你在 Windows PowerShell 里敲 scoop install emacs 报错说找不到 bucket。缺的是哪一步？

先敲 scoop bucket add extras。Scoop 的 Main 仓库（核心工具）和 Extras 仓库（GUI 与非核心软件）是分开的，Emacs 在 Extras 里。

四、macOS：Emacs.app、Homebrew、MacPorts

macOS 上有个 Linux/Windows 都没有的概念：Emacs.app，也就是一个标准的 macOS 应用包（bundle）。有 bundle 和没 bundle 的 Emacs 在系统里的行为差别很大：能不能出现在 Dock 里、能不能被 Cmd+Tab 切到、Finder 里右键「用 Emacs 打开」有没有——全看有没有 Emacs.app。

所以 macOS 上的第一个决定是：你要「应用」还是「命令行程序」？

4.1 方案 A：Emacs.app（社区构建，推荐给 macOS 用户）

macOS 上的 Emacs.app 主要来自 emacsformacosx.com，David Caldwell 从 2009 年起维护的社区构建（站点页脚写着「© 2009 - 2026 David Caldwell」，它给自己的定位是「Pure builds of Emacs for Mac OS X. No extras! No nonsense!」）。它是非官方的，但长期稳定、版本跟得上、提供 universal 二进制（同时跑 Intel 和 Apple Silicon）——我写作时它给的是 Emacs 31.1 universal 包。

Homebrew 的 cask 我读到的定义是这样的（Homebrew/homebrew-cask 的 Casks/e/emacs-app.rb，下面是节选，省略了 sha256 和 zap trash 那几段）：

cask "emacs-app" do
  arch arm: "arm64-11", intel: "x86_64-11"
  version "31.1"
  url "https://emacsformacosx.com/emacs-builds/Emacs-#{version}-universal.dmg"
  homepage "https://emacsformacosx.com/"
  app "Emacs.app"
  binary "#{appdir}/Emacs.app/Contents/MacOS/Emacs", target: "emacs"
  conflicts_with cask: ["emacs-app@nightly", "emacs-app@pretest"]
end

安装命令就是：

$ brew install --cask emacs-app
# 顺带说明：cask 名字是 emacs-app，不是 emacs。
# $ brew install --cask emacs 会 404。

$ open -a Emacs          # 打开应用
$ emacs --version        # cask 把 Emacs.app 里的二进制链成了 emacs
易错

macOS 上有 Apple 自带的一个 Emacs，它藏在 /usr/bin/emacs。这个版本的版本号常年停在 22.1，而且没有 GUI。如果你直接敲 emacs 得到一行 GNU Emacs 22.1.1，那不是你装的那个——是系统自带的。在 zsh 里检查 PATH 顺序：which -a emacs，正确的那个应该排在 /usr/bin 前面。

4.2 方案 B：Homebrew formula（终端版）

$ brew install emacs          # 注意：没有 --cask，这是终端版
$ emacs --version
$ brew upgrade emacs

我读到的 Homebrew/homebrew-core 里 Formula/e/emacs.rb：version "31.1"、revision 1、license "GPL-3.0-or-later"，从 ftpmirror.gnu.org/emacs/emacs-31.1.tar.xz 拿源码，并且为 macOS arm64（Tahoe / Sequoia / Sonoma）、Linux x86_64 都预编译了 bottle。

取舍：终端版启动更快、依赖更少、更新更勤（跟着 Homebrew 的每日更新走）。但它没有 Emacs.app，所以用不了 macOS 的全局快捷键服务（Cmd 系列）、不能被 Cmd+Tab 切到、在 Finder 里也没有「用 Emacs 打开」。如果你只是 Emacs + tmux + iTerm2 的终端流，这个版本完全够用，而且是我会推荐的。

4.3 方案 C：MacPorts

MacPorts 是比 Homebrew 更老的 macOS 包管理器，特点是从源码编译 + 极其细粒度的编译选项。我读了 macports/macports-ports 仓库里 editors/emacs/Portfile（407 行），它定义了这些 subport 和 variant：

  • subport：emacs（基础）、emacs-devel、emacs-app（应用包）、emacs-app-devel
  • variant：gtk（GTK+3 界面）、x11、motif、dbus、imagemagick、rsvg、xwidgets、nativecomp、treesitter
$ sudo port selfupdate
$ sudo port install emacs-app                # 装 Emacs.app
$ sudo port install emacs-app +nativecomp    # 显式要原生编译（其实默认已经开）
$ sudo port install emacs                    # 只要终端版

取舍：MacPorts 的价值在于它那一堆编译变体，以及默认就替你把几个关键开关打开。我读了 Portfile 末尾，它有 default_variants-append +treesitter 和 default_variants-append +nativecomp（后者在 i386 和 ppc 上排除，因为 JIT 在这两类架构上会段错误）——所以现在 emacs-app 默认是带原生编译、带 tree-sitter 的，手写 +nativecomp 是保险而不是必需。那句 +nativecomp 之所以存在，是因为它把 --with-native-compilation=no 换成 --with-native-compilation=aot，并额外把 libgccjit 挂进 rpath。

代价是 MacPorts 会和你已有的 Homebrew 安装打架（两套 dylib 搜索路径互相污染），而且 MacPorts 社区的活跃度明显低于 Homebrew。如果你的机器上已经有 Homebrew，我建议不要同时上 MacPorts。

要点

macOS 上装 Emacs 之后值得做的一件事：把 server 打开。在 init.el 末尾写 (server-start) 就行；想让它变成一个随配置开合的开关，就用 (server-mode 1)（这两个函数我在本机确认过都存在）。之后用 emacsclient -nw 文件 就能秒开。

;;; init.el 末尾
(server-start)

至于「在 Finder 里双击文件就用 Emacs 打开」，那不是 init.el 能配的。macOS 用 Launch Services 把「文件类型 → 默认应用」记在系统数据库里，只有 Emacs.app（bundle）能被登记进去；终端版 Emacs 没有 bundle，所以在 Finder 里看不到它。Emacs 在 macOS 上被 Finder 调用，靠的是系统发来的 ns-open-file Apple Event——31.1 手册 (macos) Mac / GNUstep Customization 一节写着：「This event occurs when another Nextstep application requests that Emacs open a file. A typical reason for this would be a user double-clicking a file in the Finder application. By default, Emacs responds to this event by opening a new frame and visiting the file in that frame (ns-find-file).」可用 ns-pop-up-frames 改这个默认行为。所以正确顺序是：先装 Emacs.app（4.1 的 cask 或 4.3 的 MacPorts emacs-app），再在 Finder 的「显示简介 → 打开方式」里指过去。具体工作流见第十四章《现代工作流实战》。

易错

网上有一段流传很广的「macOS Emacs 必做配置」：(setq mac-auto-save-file-modes nil)，再加一行往 auto-mode-alist 里塞 .org。这个变量在 Emacs 源码和 31.1 手册里都不存在（我 grep 过 lisp/ 与 doc/emacs/，一处都没有），而 auto-mode-alist 本来就已经有 .org 的条目，你再 add-to-list 一次纯属重复。抄到这种代码，说明写它的人自己多半也没跑通过。

练习 3　在 macOS 上用 Homebrew 装带图形界面的 Emacs，命令是什么？注意 cask 的名字和直觉不一样。

brew install --cask emacs-app。cask 叫 emacs-app；不带 --cask 的 brew install emacs 装的是终端版 formula。

练习 4　你在 macOS 终端敲 emacs --version，回显 GNU Emacs 22.1.1。系统里其实装了新版 Emacs。用一条命令确认 PATH 里到底有几个 emacs、谁排在前面。

which -a emacs。你会看到 /usr/local/bin/emacs（或 /opt/homebrew/bin/emacs）排在 /usr/bin/emacs 前面才是对的；反之说明你的 PATH 顺序有问题，或者新版的那个没链进来。

五、Nix 与 Guix：声明式安装 Emacs

如果你在第一节选了「模型二」，这一节是你的主战场。Nix 是「把每个包连同它的依赖装进一个独立目录」的系统；Guix 在这之上又加了一层「配置本身也是用 Scheme 写的、可以被复制和求值」的完整方案（guix.gnu.org）。

5.1 NixOS（系统本身就是声明式的）

# /etc/nixos/configuration.nix 里加：
environment.systemPackages = with pkgs; [
  emacs
  ripgrep        # rg 二进制本体；Emacs 里要用的 M-x rg 来自第三方 ripgrep 包
  fd             # 快速 find
  git
  graphviz       # 第三方 graphviz-mode 需要（Emacs 本身不含它）
];

# Emacs 自己的配置在 NixOS 上要额外声明：把 ~/.config/emacs 做成 symlink
# 或者用 home-manager 管理你的 Emacs 配置

$ sudo nixos-rebuild switch   # 改完配置执行这条
$ nix profile list            # 看当前 profile 里有什么

NixOS 的关键概念是 profile：nix profile install nixpkgs#emacs 会创建一个 profile 目录并把 Emacs 链进去；nix profile remove nixpkgs#emacs 删掉；升级时 nix profile upgrade nixpkgs#emacs。nix profile list 看当前 profile 里到底有什么。这套机制不是 NixOS 专属——任何 Linux 发行版上都可以只装 Nix 来管理 Emacs 这一个软件，这也是初学者最实用的中间路线。

5.2 Guix（配置与系统一起声明）

Guix 和 Nix 的哲学差异在于：Guix 让你用 Scheme 写一份声明，然后 guix reconfigure 让系统状态向声明靠拢。Emacs 配置在 Guix 上的典型写法：

;; ~/.config/guix/user.scm 片段（示意语法，实际字段随版本变化）
(use-modules (gnu home))

(service
 'home-bash-service-type
 (home-bash-configuration
  (home-bashrc-configuration
   (home-bashrc-content
"exec ~/.local/bin/emacs-server &")
   (home-bashrc-paths (list (local-file ".config/emacs/init.el"))))))
要点

上面这几个符号你从别处抄来之前，得先知道它们是哪来的——这一段最容易变成「照抄了，但不知道属于哪个系统」。

  • home-bash-service-type、home-bash-configuration、home-bashrc-configuration、home-bashrc-paths 这些符号来自 Guix 的 home-services 模块，属于 guix home 那一套「管理你自己家目录里的配置文件」的机制，不是 guix system（管整个操作系统那一套）里的东西。
  • 用之前得先把模块引进来，也就是代码第一行的 (use-modules (gnu home))。少了这一行，后面每一个符号都是 undefined，报错还很难懂。
  • 怎么查一个字段到底叫什么：按 Mx 输入 info guix 回车打开 Guix 手册，进去之后按 Cs（isearch-forward）搜 home-bash-configuration，手册会跳到那一节并逐条列出它接受的字段。这是唯一可靠的查法——Guix 的字段名随版本变，本书给出的任何字段清单都可能过期。
  • 如果你根本不想碰这些字段：guix home edit 会打开一个现成模板让你填，guix home build 把它应用到你的家目录，guix home reconfigure 让它长期生效。

本节不做完整的 Guix 教程——那是一本书的篇幅——只提醒一件事：在 Nix/Guix 环境下，use-package 的 :ensure 基本用不了。因为 package-install 要联网下载、还要往用户目录里写东西，而声明式环境的哲学恰恰是「所有依赖在构建时就确定了，运行时不联网」。在声明式环境里装包，正确做法是在声明文件里把它们列成依赖，让包管理器负责，构建出来的 Emacs 一开始就带着这些包。

5.3 非 Linux 用户能不能用 Nix？

能，而且用得越来越多。macOS 上 Homebrew 会和 nix-darwin 共存；Windows 上有 nix-portable 这个社区项目，可以在没有 WSL 的情况下跑一个 Nix 环境。但我不建议零基础读者一上来就走这条路——如果你只是想「我的 Emacs 配置在两台机器上一致」，那么把 init.el 放进 Git 仓库（第十一节会详细讲）成本低得多，效果几乎一样。

技巧

判断你有没有走过头的一个信号：如果你的 Emacs 启动命令需要写成 nix run /home/you/emacs-config#emacs 才能跑起来，或者你花在「为什么 libgccjit.so 找不到」上的时间超过了花在「怎么配置 Emacs」上的时间，那就是该退回简单方案的时候了。

六、配置文件放哪、按什么顺序加载

Emacs 的配置文件体系比大多数人以为的复杂。它有一个「初始化目录」的概念，里面可以放好几个文件，而且加载顺序不是你想的那样。搞清楚这三点，后面所有的排障都省一半力气。

6.1 Emacs 到底去哪个目录找配置

Emacs 内部确实算出过一个叫 startup-init-directory 的目录，但要先泼一盆冷水：它是 command-line 函数里的一个局部变量，启动结束后就随栈帧一起消失了。你在 --eval 里引用它，只会得到 Symbol's value as variable is void: startup-init-directory（我在本机 Emacs 32.0.50 上实测过这个错误）。真正能查询、也是你配置里会读的那个变量是 user-emacs-directory。

目录本身的判定规则写死在 lisp/startup.el 的 startup--xdg-or-homedot 函数里。规则是按顺序判断，谁先存在用谁：

  1. ~/.emacs.d/ 目录存在 → 用它。
  2. ~/.emacs 文件存在 → 也用 ~/.emacs.d/。（在 Windows 上这一条放宽成正则 [._]emacs\(\.elc\)?，顺带认 .emacs.elc 和历史名 _emacs；在 Linux/macOS 上只认 .emacs 这一个文件名。）
  3. ~/.config/emacs/ 目录存在 → 用它（这是 XDG 规范路径，Linux 上现在的标准）。
  4. 都不存在 → 默认 ~/.emacs.d/。

在本机跑 emacs --batch -Q --eval '(princ user-emacs-directory)'，作者本机的结果是 /home/you/.config/emacs/（用户名已替换）——说明那台机器上 ~/.config/emacs/ 已经存在，所以 Emacs 选了 XDG 路径。macOS 上传统是 ~/.emacs.d（虽然 macOS 也有 XDG 规范，但 Emacs 并不强制跟随 macOS 的 ~/Library/Application Support）。

易错

规则 1 的优先级陷阱：一旦你有了 ~/.emacs.d/，Emacs 就永远不看 ~/.config/emacs/了。所以「我明明在 ~/.config/emacs/init.el 里改了配置却没生效」这类问题，八成是因为某个历史原因留下了一个 ~/.emacs.d 目录。确认办法就是上面那条命令，把 startup-init-directory 换成 user-emacs-directory：emacs --batch --eval '(princ user-emacs-directory)'。

6.2 完整的加载顺序（这是本节最有价值的一段）

Emacs 启动时按这个顺序读文件，每一步我都对照过 lisp/startup.el 的源码和 Emacs 31.1 手册的 (emacs) Init File 节点：

  1. 预编译的 dump 文件（emacs.pdmp 或 emacs.dump）。这是「Emacs 还没读你的任何配置之前就已经具备的全部功能」，包含绝大多数内置的 Elisp 字节码。这一步极快，因为它不是从源码读。
  2. site-start.el（由 site-run-file 变量指定，默认值就是字符串 "site-start"）。管理员级别的配置，只有系统管理员才会用它。
  3. early-init.el（由 early-init-file 变量指定）。你的第一个用户级配置文件。
  4. package.el 自动初始化（如果 package-enable-at-startup 非 nil）。这是 package.el 存在的唯一理由——让 Emacs 能自己安装你之后配置里要用的包。
  5. init.el（由 user-init-file 变量指定）。你的主配置文件。
  6. default.el。发行版管理员的兜底配置，你可以在自己的 init.el 里用 (setq inhibit-default-init t) 跳过。

这条顺序是 Emacs 31 之后才这样的，版本差别必须记住。NEWS.31 有一条：「site-start.el is now loaded before the user's early init file. Previously, the order was early-init.el, site-start.el and then the user's regular init file, but now site-start.el comes first. This allows site administrators to customize things that can normally only be done from early-init.el, such as adding to 'package-directory-list'.」也就是说：Emacs 29/30 上第 2、3 步是反过来的（先 early-init.el 再 site-start.el），31 起才对调。对读者个人配置基本没影响，但如果你写过「只在站点环境下生效」的配置，跨版本时会看到不同的结果。

前四步的骨架在 lisp/startup.el 的 site-run-file 文档字符串里写得很清楚：「Thus, the run-time load order is: 1. file described in this variable, if non-nil; 2. early-init-file, 3. user-init-file; 4. default.el」。注意它只列了四步——package.el 那一步不在文档字符串里，是 command-line 函数在 site-run-file 与 early-init-file 两次加载之间插进去的一段代码。

要点

early-init.el 存在的唯一理由，就是它夹在「dump 文件」和 package.el 之间这个位置。你需要用它来做那些「必须在 package.el 启动前设好」的事：比如改 package-user-dir（包装到哪），加 package-archives（从哪下载），设置 straight 或 elpaca 的目录。这些设置如果你写在 init.el 里就太晚了——package.el 已经在你读 init.el 之前跑完了。

在本机可以验证 package-enable-at-startup 默认是 t：(bound-and-true-p package-enable-at-startup) 返回 t。

6.3 最小可用的 early-init.el

;;; early-init.el --- -*- lexical-binding: t; -*-
;;; 这个文件在 dump 文件之后、init.el 之前加载。

;;; 1. 让启动画面别挡路（如果你不需要那个欢迎页）
(setq inhibit-startup-screen t)

;;; 2. 设置 package.el 的下载目录（必须在 init.el 之前！）
(setq package-user-dir
      (expand-file-name "elpa" user-emacs-directory))

;;; 3. 增加 MELPA 归档（默认只有 GNU ELPA 和 NonGNU ELPA）
(add-to-list 'package-archives
             '("melpa" . "https://melpa.org/packages/"))

;;; 4. 如果你的网络慢，关掉并行的内容抓取
(setq package-archive-ping-contents nil)
易错

别再用 (package-add-archive 'melpa :url … :key-id …) 这套写法了。package-add-archive 这个函数在 Emacs 31 里已经彻底消失——我在本机 32.0.50 和一份 31.0.91 源码里都 grep 不到它的定义（fboundp 返回 nil），它原本所在的那个文件 package-x.el 现在被挪进了 lisp/obsolete/，文件头写着 Obsolete-since: 31.1，NEWS.31 有一条「package-x.el is now obsolete」。如果你在网上抄到这段老代码，抄到的会是一个 void-function。

现在的正确写法就是上面那样：package-archives 本身就是一个列表，默认内容是 (("gnu" . "https://elpa.gnu.org/packages/") ("nongnu" . "https://elpa.nongnu.org/nongnu/"))，直接 add-to-list 进去就行。Emacs 29/30 上两种写法都能用，但新写的配置没必要再用会消失的 API。

关于包签名：Emacs 32 里 package-check-signature 的默认值是 allow-unsigned（允许未签名包）——这个我在本机实测过。所以第三方归档（尤其是 MELPA）通常根本不做 GPG 签名，「配一个 :key-id 指纹」这种写法在默认配置下是形式上的东西，不必学。真正想严格校验，需要自己导入 ELPA 的密钥并把 package-check-signature 设成 sign-and-verify 或 require-all，新手用默认值就好。

6.4 init.el 拆分：什么时候该分文件

init.el 没有内置的「多文件」机制，但有一种被广泛采用的手工约定：把所有配置拆成 modules/ 下的若干文件，在 init.el 里按顺序 load 它们。

;;; init.el 顶部：定义一个加载辅助函数
(defconst my-emacs-dir
  (file-name-directory (or load-file-name buffer-file-name))
  "这个 init.el 所在目录。")

(defun my-load (rel)
  "加载 modules/REL.el，出错就大声报出来。"
  (let ((path (expand-file-name (concat "modules/" rel) my-emacs-dir)))
    (if (file-exists-p path)
        (condition-case err
            (load path)
          (error (message "加载 %s 失败: %S" path err)))
      (message "跳过不存在的模块: %s" rel))))

;;; 基础设置（必须最先，因为它设定后面模块依赖的变量）
(my-load "00-basic")
(my-load "10-editing")

;;; 外观
(my-load "20-appearance")

;;; 语言支持
(my-load "30-langs")

;;; 大件 / 重量级包，放最后，这样前面报错时不用等它们装完
(my-load "40-heavy")
易错

这段里的 load 有个坑，你迟早会踩到，所以现在就说清楚。load 拿到的路径不带扩展名时，会优先加载字节编译过的 .elc（本书第 12 章有一个要点框专门讲这件事）。后果很具体：你改了 modules/00-basic.el，重启 Emacs 却什么都没变——因为它加载的是上一次编译出来的 00-basic.elc，不是你刚改的那个 .el。

解决办法挑一个：① 开发期把 load 换成 load-file——它只加载你给的那个确切文件，改完立刻生效；等模块稳定了再换回 load，换取启动时少一点编译检查的开销。② 把那个陈旧的 .elc 删掉或重新生成——Mx 输入 byte-compile-file 回车重编一次，或者直接把文件删掉。

第 10 节那份「可以直接抄的最小骨架」里，两处 my-load 用的也是 load，同样适用这条提醒。

技巧

文件名加数字前缀是为了控制加载顺序。Emacs 加载 load 的文件时是严格按你写的顺序，不是按文件名排序——但数字前缀让你在读 init.el 的时候一眼看出顺序，少犯「把 evil 的配置写在它的 use-package 之前」这类错误。

什么时候不该拆：如果你 init.el 不到两百行，拆了反而增加心智负担——你要同时记住「内容在哪」和「顺序为什么是这样」。拆分的收益要到文件超过三百行、或者你开始需要在不同机器/不同场景下只加载一部分模块时（比如工作机和私人机共用一份 dotfiles，但只共享 00-basic）才显现出来。

七、声明式配置：use-package、straight、elpaca 怎么选

「声明式配置」的意思是：你写下「我想要什么」，而不是「按什么顺序执行什么」来得到它。这三者都自称声明式，但实现思路完全不同。先把底层的 package.el 说清楚，再讲三个宏。

7.1 package.el：两个内置归档和两个社区归档

ELPA（Emacs Lisp Package Archive）是 Emacs 官方的包分发机制，package.el 是它的客户端。归档（archive）就是一个可以从 HTTP 下载包索引的站点。你可以在 Emacs 里问它默认连哪几个归档：

$ emacs --batch -Q --eval '(progn (require (quote package))
  (princ (format "%S\n" package-archives)))'
(("gnu" . "https://elpa.gnu.org/packages/")
 ("nongnu" . "https://elpa.nongnu.org/nongnu/"))

这两个默认归档的分工是：

  • GNU ELPA（gnu）。由 Emacs 官方维护，收录的都是社区认为「质量够、值得进官方归档」的包，而且需要走一遍 Emacs 开发团队的审核流程，所以进得慢。好处是版本保守、更新有保障、和 Emacs 本体的兼容性被认真考虑过。我写作时下载并解析了 https://elpa.gnu.org/packages/archive-contents：里面是五百多个包（我数到 509 个），use-package、eglot、corfu、vertico、consult、orderless、cape、project、modus-themes 都在里面。这个数字每周都在涨，你要用的时候自己重新数一遍。
  • NonGNU ELPA（nongnu）。审核更宽松，主要是那些许可证不是 GPL 的包，或者作者不想等官方审核的包。它是从 Emacs 28 开始就默认启用的——Emacs 28 的 NEWS 原话是「The new NonGNU ELPA archive is enabled by default alongside GNU ELPA」。

社区维护的第三方归档里，你要认识两个：

  • MELPA（melpa.org）。全称是 Milkypostman's Emacs Lisp Package Archive（milkypostman 是 Emacs 社区一位老贡献者的网名，不是「The Modern Emacs Lisp Package Archive」——后者是网上常见的讹传）。它只收 git 仓库的默认分支，自动构建，没有审核，更新极快。我解析它的 archive-contents 时是六千多个包（我数到 6325 个），包含 magit、projectile、helm、embark、tree-sitter-langs 这些大名鼎鼎的东西。风险是：作者的默认分支今天推坏了，你的 Emacs 明天就起不来。
  • MELPA Stable（stable.melpa.org）。同样的包，但只在作者打了 tag 的版本上构建，我数到三千四百多个（3483 个）。牺牲新鲜度换稳定性，适合生产环境。
易错

MELPA 快是有代价的。很多包作者把「已发布可用」的代码放在 master，把「正在写的」放在 develop——但这不是 Emacs 社区的强制约定，个人项目经常不遵守。所以一条经验规则：你在 MELPA 上看到的版本号很可能是空的或者只到 0.1.x，那说明这个包没走 tag 流程，你正在用一个开发中的版本。判断办法是去包的 GitHub 仓库看 Releases 页面。

7.2 use-package：从 Emacs 29 起是内置的

这是个很多人不知道的事实：use-package 不再是第三方包了。Emacs 29 的 NEWS 里有一整个小节写着「use-package: Declarative package configuration. use-package is now shipped with Emacs.」，并且告诉你去读新的 Info 手册 (use-package) Top。我在本机 Emacs 32.0.50 上用 (locate-library "use-package") 查到了它在内置 lisp 目录里。

它的写法长这样：

;; magit 只在 MELPA 上（GNU ELPA 里没有），所以要 :ensure 保证装得上。
;; 键位用它自己的推荐绑定，别抢：magit 默认把 C-x g 绑到 magit-status、
;; C-c g 绑到 magit-dispatch（我读了 magit.el 里的
;; magit-maybe-define-global-key-bindings），你覆盖 C-c g 就等于废掉了
;; magit-dispatch 的键位。
(use-package magit
  :ensure t
  :bind (("C-c M-g" . magit-dispatch)))

;; 内置包不用写 :ensure：display-line-numbers 是 Emacs 28 起自带的库，
;; 写成 :ensure t 反而会让 use-package 去归档里找一个根本不存在的包
(use-package display-line-numbers
  :custom (display-line-numbers-mode 1))

;; 明确用某个版本
(use-package vertico
  :ensure t
  :pin "1.15")   ; 锁在这个版本
要点

关于 M-x magit：本书作者在本机实测过，它是真实存在的命令，不要因为老资料说「magit 没有 magit 命令」就以为敲了会报 void-function。在装了 Magit 4.7 的 Emacs 32.0.50 上，(fboundp 'magit) 返回 t、(commandp 'magit) 也返回 t，(documentation 'magit) 原文是：

Begin using Magit.

This alias for ‘magit-status’ exists for better discoverability.

Instead of invoking this alias for ‘magit-status’ using
"M-x magit RET", you should bind a key to ‘magit-status’
and read the info node ‘(magit)Getting Started’, which
also contains other useful hints.

也就是说：magit 就是 magit-status 的别名，敲 Mx magit RET 会打开 Git 状态缓冲区，完全能用。文档里那句「you should bind a key to magit-status」是 Magit 作者的风格建议（他希望你给它一个固定键，而不是每次敲 Mx），不是「这个命令不存在」。看到这句时不要反向推断。

那 magit-mode 呢？它也存在，(fboundp 'magit-mode) 同样返回 t——但角色完全不同。它的文档字符串是 “Parent major mode from which Magit major modes inherit.”，也就是说它是 Magit 各种 buffer 模式（magit-status-mode、magit-diff-mode 那些）的父模式，不是「打开状态缓冲区」的入口。Magit 4 拿掉的是「用 magit-mode 当全局开关」那种老用法，命令本身没有被删。

于是这一段应该这么记：入口是 magit-status（等价写法 magit）和 magit-dispatch（速查菜单，「我现在能干什么」问它）；magit-mode 是模式继承关系，跟入口无关；magit-init 是第三个东西——文档字符串是 “Initialize a Git repository, then show its status.”，只在你需要在一个新目录里 git init 时才用，不是「装 Magit」或「初始化 Magit」的命令。

use-package 的各个关键字对应的是传统写法里的这些步骤：

use-package 关键字对照表

关键字等价于传统写法作用
:ensure tunless (package-installed-p 'x) (package-install 'x))缺包时自动安装
:pin 版本（无直接对应）锁定包版本，不随归档更新而变
:load-path(add-to-list 'load-path "…/elpa/x-1.2")只加路径，不 require、不配置
:init包的加载 hook 里跑装完、require 之后立刻执行
:config顶格写设置代码require 之后执行，配置主体的位置
:bind / :bind-keymapglobal-set-key / define-prefix-command绑全局键
:commands—声明「我要绑的这些命令存在」，从而触发延迟加载
:magic—需要 Elisp 魔法但不常用，配置里用少数几个
:defer t—完全不加载，用到时按需加载
:custom(setq x val)用 defcustom 方式设置，并让 Customize 能看到
要点

:ensure t 在字节编译你的 init.el 的时候就会真的去装包，这条要记住，否则你会对「为什么每次编译都那么慢」感到莫名其妙。本书作者在本机 Emacs 32.0.50 的 lisp/use-package/use-package-ensure.el 第 153–161 行读到了这段逻辑（函数是 use-package-handler/:ensure）：

(if (bound-and-true-p byte-compile-current-file)
    ;; Eval when byte-compiling,
    (funcall use-package-ensure-function name ensure state)
  ;;  or else wait until runtime.
    (push `(,use-package-ensure-function ',name ',ensure ',state) body))

上面那段的注释还解释了为什么要这么写：“We want to avoid installing packages when the use-package macro is being macro-expanded by elisp completion (see lisp--local-variables), but still install packages when byte-compiling, to avoid requiring package at runtime.”——翻译过来就是：编译期真的装，宏展开期（比如按 C-Mi 触发补全）不装。所以你每次编译 init.el 都要联网下载一遍包。

后果有两个：一是编译 init.el 会真的联网下载包，编译机上的副作用也会跟着跑；二是编译结果和运行结果不完全等价，你在编译机上「顺手」装上的包，在别人机器上不会自动出现。解决办法有两个：要么别字节编译 init.el（这本来也是常见做法），要么接受这个语义。另外提醒一句：如果你读到某篇文章说 Emacs 32 把 :ensure 改成了「只在运行时安装」，那是错的——我在 32.0.50 上核对过源码和 etc/NEWS（Emacs 32 的 NEWS 全文里根本没有 use-package 小节），:ensure 至今仍按编译期安装的逻辑走。

use-package 的全局默认开关有两个，值得知道：

;; 让所有 use-package 形式都自动 :ensure t（省掉到处写）
(setq use-package-always-ensure t)

;; 反过来，让所有包都锁到当前版本
(setq use-package-always-pin 'keep)

我读了本机 Emacs 32.0.50 的 lisp/use-package/use-package-core.el 源码：use-package-always-ensure 和 use-package-always-pin 的 :version 都是 "29.1"，默认值都是 nil；它们是通过 use-package-defaults 这个 alist 生效的。不想用就都保持 nil。顺带一提，Emacs 32 把 use-package 拆成了好几个文件：:ensure 和 :pin 的实现搬到了 lisp/use-package/use-package-ensure.el，绑定相关的搬到了 use-package-bind-key.el；上面这两个变量仍然留在 use-package-core.el。

7.3 straight.el：直接从 git 仓库装，可在源码上改

straight.el 是一个第三方包管理器（不是包装 package.el，而是完全绕开它）。它的工作方式：克隆 git 仓库，把文件符号链接（symlink）到 Emacs 的 load-path 里。

它的仓库现在是 radian-software/straight.el（注意：早期的 github.com/rststraight/straight.el 已经 404 了）。我写作时该仓库是 3030 星、最近推送 2026-09-14，活跃维护中。它有完整的 README，讲清楚了它的定位是「next-generation, purely functional package manager for the Emacs hacker」。

安装方式（这段是从它的 README 里抄的官方 bootstrap 片段，能直接跑）：

;;; early-init.el 里
(defvar bootstrap-version)
(let ((bootstrap-file
       (expand-file-name
        "straight/repos/straight.el/bootstrap.el"
        (or (bound-and-true-p straight-base-dir)
            user-emacs-directory)))
      (bootstrap-version 7))
  (unless (file-exists-p bootstrap-file)
    (with-current-buffer
        (url-retrieve-synchronously
         "https://raw.githubusercontent.com/radian-software/straight.el/develop/install.el"
         'silent 'inhibit-cookies)
      (goto-char (point-max))
      (eval-print-last-sexp)))
  (load bootstrap-file nil 'nomessage))

然后 init.el 里：

(straight-use-package 'org
  :recipe (:host github :repo bzg/thisorg
         :branch "master"))
;; 用 :after 代替 use-package 的 :config
(straight-use-package 'some-package
  :after #'some-package-setup)

取舍，这是本节最需要你自己判断的地方：

  • 好处一：仓库就是你的。用 straight 装的东西，源文件是一串指向 ~/.emacs.d/straight/repos/… 的符号链接。你可以直接用编辑器和 M-x magit-status 在那个仓库里改源码、改完保存立刻生效、不用重装。调试第三方包时这个体验无可替代。
  • 好处二：锁文件（lockfile）机制。README 里的做法是运行 M-x straight-freeze-versions，它把所有包当前 checkout 的提交号写进 ~/.emacs.d/straight/versions/default.el。把这个文件和 init.el 一起提交进 git，就得到一份完全可复现的依赖清单；在新机器上装完之后跑 M-x straight-thaw-versions 就能把所有包回退到锁文件指定的提交。
  • 坏处一：首次安装慢。每个包都要 clone 一次，从零配置一台机器可能等十几分钟。
  • 坏处二：多了一层抽象。包的加载路径是符号链接而不是真实文件。绝大多数时候没问题，但如果你要排查「这个 .el 文件到底从哪加载的」，find-file 会把你带到 ~/.emacs.d/straight/repos/… 而不是包管理器目录里，偶尔会让人困惑。
  • 坏处三：和 package.el 的边界模糊。有些包会自己调 package.el。混用时会出现「同一个包有两份」的情况。

7.4 elpaca：另一个思路，界面更好

elpaca（现在是 progfolio/elpaca，我写作时 950 星、最近推送 2026-09-21）的定位是「Emacs 自带的那个包管理器 package.el 的替代品」——和 straight 一样，它也不走归档：straight 和 elpaca 都不在 GNU ELPA 和 MELPA 的索引里（我核过两个 archive-contents，都搜不到这两个名字），而是直接从 git 仓库构建。

易错

关于 elpaca 的「三条主打卖点」，本书作者没有核实，所以这里干脆不写结论。写本章时他的网络被拦，没能重新打开这个项目的 README。按本书自己的规矩（凡是没能查证的技术性断言就不当结论），「安装全异步并行」「自带搜包和装包的图形界面」「默认接上多个归档」这三条一律以你打开 github.com/progfolio/elpaca 后看到的 README 为准——那个仓库首页就是唯一该信的东西。上一段那句「straight 和 elpaca 都不在 GNU ELPA / MELPA 的索引里」是不同性质的信息（作者核过两个 archive-contents），可以直接用。

与其背任何一个包管理器的卖点，不如学会三十秒自己判断——这条路对所有包都管用：① Mx package-list-packages 打开列表，看最近更新日期和下载量；② 打开它的仓库，看最近一次 commit 是什么时候；③ 翻 issue 里有没有人报「装不上 / 启动报错」而且没人理。本书推荐 elpaca 的唯一理由就是它在这三项上都还活着；它具体快在哪、界面长什么样，装之前自己看一眼 README 就知道了，比读本书的转述准。

什么时候选它：你在意交互体验（用图形界面搜包、看文档、一键装），并且愿意接受它比 straight 还要「有主张」——elpaca 要求你不要混用 package.el，两套并存会打架。

7.5 三选一：我的建议

要点

零基础读者：先只用内置的 package.el + 内置的 use-package，一个第三方包管理器都别装。理由是：你需要学的东西已经够多了，而 use-package 从 Emacs 29 起就是内置的，它和 package.el 的配合是官方文档化的。第三方包管理器带来的是可复现性和源码可控性这两件事——只有当你真的需要其中之一（比如你要在五台机器上跑完全一样的配置），它们才值得。

练习 7　你有二十个 use-package 形式，每个都老老实实写了 :ensure t。有一个变量能让这二十处全部省掉吗？

(setq use-package-always-ensure t)。它在 Emacs 29.1 引入，默认 nil。设成 t 之后每个 use-package 形式都等于自动带上了 :ensure t（除非你显式写了 :load-path，那种情况下 use-package-core.el 的 use-package-defaults 逻辑会自动跳过 ensure）。

练习 8　你用 straight.el 管理包，想让这台机器的依赖版本能被完整记录下来并在另一台机器上还原。敲哪个命令？

M-x straight-freeze-versions。它把所有包当前的提交号写进 ~/.emacs.d/straight/versions/default.el。把这个文件提交进 git，在新机器装好包后用 M-x straight-thaw-versions 回退到锁定版本。

八、启动性能：先测量，再优化

「我的 Emacs 要 8 秒才打开」是新人最常见的抱怨，也是最常见的误判。因为在多数人的机器上，那 8 秒里只有 1.5 秒是 Emacs 自己在初始化，剩下 6.5 秒是别的包。所以本节的第一条建议是：不要凭感觉优化，用 profiler 测。

8.1 三种延迟，先分清是哪一种

  • dump 文件加载时间。Emacs 启动时先把预编译的 .pdmp 读进来，这通常在 50~150 毫秒。你几乎无法优化它，因为它取决于 Emacs 二进制的构建方式。
  • init 文件求值时间。读你的 early-init.el + init.el、require 包、跑设置代码。这是你能优化的绝大部分。
  • 运行时垃圾回收（GC，garbage collection）。Emacs 是动态分配内存的，它的 GC 策略是「分配到一定量就回收一次」。如果你的配置在启动时大量分配又释放对象，会触发多次 GC，在 *Messages* 窗口里表现为反复刷 Garbage collection: X%。

8.2 测 CPU 时间：profiler

Emacs 内置了一个采样 profiler。它的两个入口命令是 M-x profiler-start 和 M-x profiler-report（我在本机读过 profiler-start 的文档字符串：MODE 可以是 cpu、mem 或 cpu+mem）。要在 early-init.el 里就开始测，否则测不到包加载那段：

;;; early-init.el 末尾，只在设了环境变量时才测
(when (getenv "EMACS_PROFILE_INIT")
  (profiler-start 'cpu))

然后用一个干净的环境启动 Emacs：

$ EMACS_PROFILE_INIT=1 emacs -Q
# 进 Emacs 后按 M-x profiler-report

# 更直接的写法：在 dump 加载之后、init 之前挂钩子
$ emacs --eval '(profiler-start '"'"'cpu)'

进了 Emacs 之后按 M- profiler-report，弹出的 *Profiler Report* 缓冲区是一个按「自身耗时」倒序排的表格：

  1. 第一列是调用者（caller），第二列是被调用的函数（callee）。
  2. 「Self」列是它自己花掉的时间，「%」列是占总采样数的百分比。
  3. 你要找的永远是占比最高的那几行，不是那些被调用次数最多的。

典型的结果会长这样：某几个 use-package 的 :config 各占 3~8%，某个重量级包（比如 LSP 客户端、主题系统）占 15%，剩下是一串 garbage collection 占 12%。你会立刻发现优化的方向和自己的直觉完全不一样——这就是测量的价值。

技巧

测完记得关掉。profiler-start 重复调用只是重启计时，不会叠加，但它本身是常驻的。诊断完成后把 early-init.el 里那两行删掉，或者保证只在设了环境变量时才开。

8.3 原生编译（native compilation）

原生编译是把 Elisp 直接编译成机器码，而不是编译成字节码。它的收益有两条：一是代码跑得快——但要诚实地给个量级：常见的说法是「一两倍到几倍」，而不是「几十倍」；收益最大的场景是大量分配、频繁 GC 的代码（比如 LSP 客户端、大包的初始化），纯计算型代码的提升就小得多。二是函数调用不分配 cons cell，GC 压力小得多——这一条在启动阶段往往比速度本身更值钱。

但你必须先知道你的 Emacs 到底有没有它。这是本节最实用的一条命令：

$ emacs --batch -Q --eval '(princ (if (locate-library "native-comp")
    "有原生编译" "没有原生编译（--with-native-compilation=no）"))'
;; 本机输出：没有原生编译（--with-native-compilation=no）

没有的话，原生编译相关的所有配置都是摆设。发行版包经常是关掉的（Debian/Ubuntu 的 emacs-nox、Fedora 的包都算）；MacPorts 因为在 Portfile 末尾写了 default_variants-append +nativecomp，默认就是开的（i386 和 ppc 除外）；而 Homebrew 的 formula 并没有开——我读了 Formula/e/emacs.rb 的 configure 参数，里面有 --with-tree-sitter，但没有任何 --with-native-compilation。自己源码编译时显式加上这个开关才会打开。

打开之后怎么用：

;;; 1. 装包时就把它们提前原生编译（否则留到第一次加载时才编）
;;;    这是 Emacs 28.1 引入的用户选项，默认 nil。
;;;    它的文档字符串最后一句是：
;;;    "This option does not have any effect if Emacs was not built
;;;     with native compilation support."   <- 又回到 8.3 开头那条命令
(setq package-native-compile t)

;;; 2. 手动编译单个文件
;;    M-x native-compile-file

;;; 3. Emacs 31 新增：整个目录树一起编译
;;    M-x native-compile-directory

M-x native-compile-directory 是 Emacs 31 的新函数。NEWS.31 原文：「New function native-compile-directory. This function natively compiles all Lisp files in a directory and in its sub-directories, recursively, excluding those already natively compiled.」。第一次跑会持续几分钟，结果在 *Warnings* 缓冲区里。

要点

原生编译的警告该看还是得看，但不必恐慌。Emacs 30 起你可以控制异步原生编译汇报什么：NEWS.30 记录了用户选项 native-comp-async-warnings-errors-kind，默认值是「报全部错误 + 只报重要的警告」；如果你以前习惯把 native-comp-async-report-warnings-errors 设成 nil 或 silent 来消音，NEWS 明确建议别再这么做，而是「改成默认值，看看是不是真的只收到有意义的警告」。Emacs 31 又加了一条实用选项 native-comp-async-on-battery-power：设成 nil 就能在没插电源时不启动新的异步编译。

8.4 垃圾回收：调高阈值换启动时间

Emacs 的 GC 是「分配够一定量就触发」。我在本机查到的默认值是 gc-cons-threshold = 800000、gc-cons-percentage = 1.0。如果你看到 *Messages* 里刷 GC，调高阈值通常立竿见影：

;; 把阈值调到 64 倍（代价：常驻内存变大）
(setq gc-cons-threshold (* 64 1024 1024))

;; 每次 GC 之后重新设一次，避免阈值被越调越低
(defun my-post-gc ()
  (setq gc-cons-threshold (* 64 1024 1024)))
(add-hook 'post-gc-hook 'my-post-gc)

什么时候不该调：如果你在一台只有 4~8 GB 内存的机器上（或者是个虚拟机），调高 GC 阈值会让 Emacs 占用暴涨，最后被 OOM killer 干掉。GC 阈值是「用内存换时间」里最划算的一笔交易，但前提是你的内存真的够。

还有一个现代 Emacs 特有的性能陷阱：全局 minor mode 越多，启动后越卡。flymake-mode、show-paren-mode、whitespace-mode、column-number-mode 每个都会给每一个新建的 buffer 挂钩子和后处理函数，而 buffer 会越来越多。干净的做法是只给相关 mode 的 hook 加：

;; 只在真正需要的文件类型里开
(dolist (hook '(python-mode-hook emacs-lisp-mode-hook
                rust-mode-hook typescript-mode-hook))
  (add-hook hook 'flymake-mode)
  (add-hook hook 'show-paren-mode))

8.5 按需加载：advice 的正确用法

Advice（Emacs 的「建议」机制）能在不修改原函数的前提下，给它加一层前置或后置钩子。这是做按需加载最优雅的办法：平时什么都不做，用户真的用到某个功能时，才把那个重量级包加载进来。

;; 包里有 command，在它第一次被调用时才加载
(eval-after-load "some-big-package"
  '(advice-add 'some-big-package-command :before
               (lambda (&rest _)
                 (require 'some-big-package nil t))))

;; 更常见的写法：挂到 mode hook 上按语言加载
(add-hook 'python-mode-hook
          (lambda () (require 'pyproject-mode nil t)))

;; 查看某个函数当前挂了哪些 advice
;; 注意 advice-mapc 的回调签名是 (FUNCTION PROPERTIES)，
;; 不是 (SYMBOL HOW)；HOW 在 properties 这个 plist 里（:before / :after …）
(advice-mapc (lambda (fn props) (message "%S -> %S" fn props))
             'some-function)

advice-add 和 advice-remove 我在本机确认过都存在（fboundp 均为 t），advice-mapc 的文档字符串也确认了它对回调的调用方式是 (FUN FUNCTION PROPERTIES)。

易错

Advice 是「猴补丁」级别的工具，用多了会让配置变得无法推理。一个函数被七个 advice 包着，你就无法靠读代码判断它的行为了。原则：advice 用来「延迟加载」和「绕过上游 bug」，不要用来「配置」——配置有 defcustom，不需要 advice。

8.6 哪些包根本不该装

这一小节标题就叫「哪些包不该装」，内容是几条我认为是硬道理的规则：

  1. 一次只装一个补全前端。补全这块能装的包有 company、corfu、vertico、cape、helm、ivy……它们抢的是两个不同的位置，而且同一个位置只能有一个赢家：corfu 和 cape 往 completion-at-point-functions 这个 hook 列表里塞自己的后端，company 则用 advice 包住 completion-at-point 这个函数本身；而 vertico 压根不碰 completion-at-point——我读了 vertico.el 的 vertico-mode，它 advice-add 的是 completing-read-default 和 completing-read-multiple，也就是 minibuffer 那一侧；ivy/helm 抢的也是 minibuffer 这一侧。正确配法是：minibuffer 侧选一个（vertico 或 ivy 二选一），buffer 内侧选一个（corfu + cape 这套算一个，或 company）。同侧装两个的结果是随机的、时好时坏的、无法调试的。
  2. 不要一上来就装「全家桶配置框架」。doom-emacs 之类的框架确实能给你一个功能齐全的 Emacs，但你学到的全是框架的命令，一旦离开框架全都不会了。对「读完这本书想自己配一套」的读者来说，这是本末倒置。
  3. 装之前看最后提交时间。在 2026 年，一个 2020 年之后没有 commit 的包，你可以直接跳过。查它的最快办法是问 GitHub 一次（下面那条命令我就是自己用的）：
# 包的 GitHub 仓库最后一次推送时间（不需要 clone）
curl -s https://api.github.com/repos/OWNER/REPO | grep '"pushed_at"'
# 顺便看未关闭 issue 数量
curl -s https://api.github.com/repos/OWNER/REPO | grep '"open_issues_count"'

# 想看具体的最后提交（需要先 clone）
git clone --depth 1 https://github.com/OWNER/REPO /tmp/probe
git -C /tmp/probe log -1 --format='%ci  %s'

拿这个标准回头看本章举过的例子就很直观：magit 在 MELPA 上的构建日期是写作当天前两天，活的；而我原本想在这份骨架里推荐的 edit-list，MELPA 索引里记的构建时间是 2010-09-30，它清单里的源码地址 http://mwolson.org/static/dist/elisp/edit-list.el 我访问时已经 404。这就是「包会死」的样子，所以我已经把它从这个骨架里拿掉了。

  1. 装之前看未关闭的 issue 数量。一个 3000 行的包有 200 个未关闭的 issue，而且最近没有提交，说明它已经超出了维护者的能力范围。
  2. 先问「这个功能 Emacs 内置的是不是已经有了」。Emacs 内置了非常多东西：project、eglot、flymake、org、isearch、dired、vc、compile、package、faces。装包之前先 M- apropos RET 搜一下，能省很多事。

九、Emacs 28 到 32：哪些变化会直接影响你的配置

这一节按时间倒推，把「从哪个版本开始是这样」讲清楚。如果你用的是 29 或 30，有些条目直接跳过；如果你在准备升级到 31/32，这些就是你要提前改的地方。

9.1 Emacs 27（作为分界线）：completion-styles 和 project.el

这两样东西不新，但它们是后面所有变化的舞台。我查了 Emacs 的 NEWS：completion-styles 在 27 的 NEWS 里已被当作既有设施使用（有一整段讲「把 flex 加到 completion-styles 里」），而 26 的 NEWS 里完全没有这个变量——所以 completion-styles 是 Emacs 27 引入的。project.el 更早：Emacs 25.1 的 NEWS 第 1025 行有一条标题就是「New package Project」（本节小节头是 “Changes in Specialized Modes and Packages in Emacs 25.1”），25、26 两版 NEWS 里都搜不到这个包，27 版也没有。所以 project.el 是 25.1 进的本体，本书第 9 章那一节讲的是对的；如果你在别处看到「27 起」「28 起」「29 起」的说法，那些都是错的。

completion-styles 是理解后面所有补全变化的钥匙。它的机制是：completion-styles 是一个样式列表，补全时依次尝试每个样式，第一个产出结果的胜出。我在 Emacs 32.0.50 上查到的默认值是：

$ emacs --batch -Q --eval '(princ completion-styles)'
(basic partial-completion emacs22)

而 Emacs 31.1 手册 doc/emacs/mini.texi 里明确列出了默认的三个：basic（前缀必须从头匹配）、partial-completion（按 - 和空格分段，每段各自补全，* 是通配符）、emacs22（类似 basic 但忽略光标后面的文本，所以老名字）。

同一节手册紧接着列出定义了但不在默认里、需要你自己加的样式：substring、flex（也叫 flx、fuzzy、scatter）、initials，另外还有 emacs21。这里有个必须说清的事实：ido 和 flex 早就不在默认样式里了——flex 从来不是默认项，ido 则是随着 completion-styles 的引入（27）就从内置补全里退出、改由 ido-mode.el 这个单独的库提供了。

9.2 Emacs 28：NonGNU ELPA 默认开启

NEWS.28 的原话是：「The new NonGNU ELPA archive is enabled by default alongside GNU ELPA. Thus, packages on NonGNU ELPA will appear by default in the list shown by M-x list-packages.」 这就是为什么今天 M-x list-packages 默认能看到两个归档的包。

9.3 Emacs 29：三个大变化

第一，use-package 和 Eglot 进了 Emacs 本体。NEWS.29 各给了独立小节，use-package 那节的标题就是「use-package: Declarative package configuration. use-package is now shipped with Emacs.」，Eglot 那节说 eglot 现在内置，有自己的 Info 手册 (eglot) Top。这一节的两条注意事项：

  • NEWS 提醒你，如果想用 M-x package-install 把它们升级到 GNU ELPA 上的更新版本，要先把 package-install-upgrade-built-in 设为非 nil。我在 Emacs 32.0.50 上确认了这个变量存在（默认 nil），而 package-upgrade-from-built-in 不存在——如果你在网上看到有人这么写，那多半是别的 Emacs 配置框架的变量名。
  • 也就是说：Emacs 29+ 里 use-package 和 eglot 都是「内置的 ELPA 包」，它们被标记为内置，所以 M-x list-packages 里会标成 built-in 而不是让你升级。

第二，tree-sitter 变成编译期选项。NEWS.29 的 Installation Changes 里有一条：「Emacs can be built with the tree-sitter parsing library.」这是个 ./configure --with-tree-sitter 级别的开关。它在 29 只是「能编进去」，不是「默认开」。到你手上的 Emacs 有没有它，用 8.3 节那条 locate-library "tree-sitter" 就能查。

第三，ahead-of-time 原生编译。NEWS.29 有一条 Installation Changes：「Ahead-of-time native compilation can now be requested via configure.」也就是构建 Emacs 本身时可以把所有内置 Elisp 提前编成机器码，比「运行时才编 .eln」更快。

9.4 Emacs 30：补全预览来了，project.el 上模式行

  • Completion Preview（补全预览）。这是 Emacs 30 系列最重要的一次补全改动：一个叫 completion-preview-mode 的 minor mode，你打字时候选词就直接以幽灵文本（灰色）显示在光标后面。NEWS.31 里有一条说明它和第三方包的关系：「If you use this mode together with an in-buffer completion popup interface, such as the interfaces that the GNU ELPA packages Corfu and Company provide, you can set completion-preview-sort-function to the same sort function that your popup interface uses for a more integrated experience.」我在本机确认 completion-preview.el 是内置文件，(require 'completion-preview) 之后 completion-preview-mode 存在。
  • NEWS.31 还说明 completion-preview-sort-function 在 Emacs 30.1 里已经存在，只是当时是个普通 Lisp 变量，31 才把它变成可定制的 user option。所以你读到的教程如果写「Emacs 31 新增」，对 30.1 用户是成立的。
  • grep-use-headings。Emacs 30 新增，M-x grep 的输出会按文件分组显示标题，用新的 grep-heading face 着色（对应 rg --heading）。
  • project-mode-line。Emacs 30 新增，在模式行显示当前项目名，鼠标点它会弹项目切换菜单。
  • project-any-command。Emacs 30 新增（C-x p o），给项目切换器一个「完整键位表 + 全局命令」的入口，不再只有一小撮快捷命令。
  • native-comp-async-warnings-errors-kind。前面 8.3 讲过。

9.5 Emacs 31：补全系统重做，tree-sitter 上主线

Emacs 31 是近年变化最大的一版，逐条抄 NEWS（都是原话）：

  • flex 样式被重写。「flex completion style rewritten to be faster and more accurate. Completion and highlighting use a new, superior algorithm. For example, pattern "scope" now ranks elisp-scope-* functions well above dos-codepage and test-completion.」
  • completion-styles 可以带局部绑定。「In addition to a symbol naming a completion style, an element of completion-styles can now be a list of the form (STYLE ((VARIABLE VALUE) ...))」——也就是说你可以让同一个样式在不同绑定下出现多次，比如让 partial-completion 在 buffer 里和 minibuffer 里表现不同。
  • Completion Preview 的细粒度控制。新增 completion-preview-inhibit-functions，可以指定任意条件来抑制预览。
  • completions-format 变成 vertical 时导航键自适应。我在本机查到它的默认值是 horizontal。
  • tree-sitter 有一整个大节。包括 treesit-major-mode-remap-alist（可以一次性把一批 mode 切到 tree-sitter 版）、treesit-x.el（提供了若干简易的 tree-sitter mode）、新的 treesit-query-with-fallback / treesit-query-with-optional，以及 treesit-thing-settings 里新增了 list 和 comment 两类「thing」（配合 C-M-<up> / C-M-<down> 按结构跳）。注意 treesit-x.el 是 Emacs 31 才进主线的（我确认它在本机 Emacs 32.0.50 的内置 lisp 目录里）。
  • 原生编译两条：native-comp-async-on-battery-power 和 native-compile-directory（前面 8.3 讲过）。
  • grep 缓冲区可以编辑。「Like Occur Edit mode, typing e in the *grep* buffer will now make the grep results editable. The edits will be reflected in buffers visiting the originating files.」——这是把 grep 结果当成可编辑文本来用的能力。
  • lua-mode 从 NonGNU ELPA 进了 Emacs 本体，同时进了 system-sleep 这个新包。
  • newcomers-presets 主题：一个不改变颜色、只配置用户选项和 minor mode 的「新手预设」主题。

9.6 Emacs 32：正在发生的变化

Emacs 32 目前处于开发序列（本文写作时本机是 32.0.50 的开发快照），NEWS 文件按小节列出了已定的变化。对配置有直接影响的有：

  • :ensure t 仍然是编译期就装包（并没有改成只在运行时安装），细节和证据在 7.2。
  • query-replace-show-preview。新选项：在 M-% 替换时实时预览替换结果，而不用真的替换完再撤销。取值我在本机同时读了 lisp/replace.el 的文档字符串和 etc/NEWS 原文，不是什么 replacement-only：默认 nil（关闭）；设成 t 就是把每个匹配显示成替换后的样子（用新 face query-replace-preview 上色）；设成 both 则是匹配与替换并排显示、中间一个箭头（用 query-replace-preview-match 和 query-replace-preview 两个 face，继承自 diff-removed／diff-added 看起来就像 diff）；还可以给一个二元函数，由它决定每个匹配显示成什么字符串。文档字符串末尾给了个现成例子：(lambda (match replacement) (concat "[" match "]~>{" replacement "}"))。
  • markdown-ts-mode。新的 Markdown 主模式，基于 tree-sitter。
  • electric-pair-field-search-size。让电括号只在附近字段内生效，免得去配对进程输出里那些不成对的括号。NEWS 举的例子正是 M- shell 和 M- run-python 这类 comint 缓冲区。不过在 Emacs 32 里这已经不用你操心了：lisp/comint.el 里有一行 (setq-local electric-pair-field-search-size 1000)，comint buffer 一建立就自带这个设置。它真正还有用的地方，是你希望在别的模式（带字段标记的 buffer）里做同样的限制。
  • completion-ignore-case 变成可定制项（原来是内部变量）；icomplete-in-buffer 的行为也清理了——NEWS.32 的小标题原话就是「icomplete-in-buffer users need no longer advise completion-at-point」。如果你之前照 Emacs 30.1 的建议加过 (advice-add 'completion-at-point :after #'minibuffer-hide-completions)，现在可以删掉了。
  • 主题变体切换新增了两个函数：theme-list-variants 和 theme-choose-variant。这里有一处特别容易记反，我按本机 lisp/custom.el 的源码原样写：是 (defalias 'toggle-theme #'theme-choose-variant)——老名字 toggle-theme 现在是新函数的别名，不是反过来。语义不变：theme-list-variants 列出当前主题的同家族变体，theme-choose-variant 在它们之间切换。详见 9.7。
易错

关于「十色调色板」这个说法，我要在这里纠正一下。我逐条核对了 Emacs 28/29/30/31 的 NEWS 和 31.1 发行包里的全部 62 个手册源文件，Emacs 从来没有一个「固定十色调色板」的内置概念。真正存在的是 9.7 讲的 Modus 主题家族的命名调色板，而且它远远不止十个颜色。你如果在网上读到「Emacs 30 引入了十色调色板」，那个说法多半是把 Modus 主题（作者 Protesilaos）的设计理念误当成 Emacs 本体的机制了。下面这一小节告诉你实际该怎么改颜色。

Modus 的调色板是怎么组织的（我加载主题后读了 modus-operandi-palette 这个常量的实际值）：它是一个 328 条目的 alist，远不止「几个基础色」，开头是这么排的：

  (file-name-directory (or load-file-name buffer-file-name))

(defun my-load (rel)
  "加载 modules/REL.el。
第一次写的时候很容易漏掉 .el 后缀，所以两种都试一遍。"

11.2 依赖固化：三种程度，三种代价

光有 init.el 不够——包会变。你在 MELPA 上 M-x package-upgrade-all 一次，两周后在新机器上装出来的是完全不同的版本，配置报错的概率很高。三种固化方案：

方案怎么做代价
最弱：只锁 major 版本每个 use-package 写 :pin "1.15"包被删或被撤归档时会失效
中等：锁仓库分支或改用只发布 tag 的归档straight 的 :recipe (:branch "stable")，或把 package-archives 里的 melpa 换成 stable.melpa.org每次装包都要多考虑一层

11.3 备份策略：三层

  1. 版本库（git）。这是主备份。每次改配置 git commit 一次，提交信息写清楚改了什么。不要等到「配置稳定了」才提交——稳定是从来没有到达的状态。
  2. 远端克隆（GitHub/GitLab/自建 Gitea）。私库就行，配置里通常有内部项目名、机器名、甚至偶尔的凭据。如果不想开源，至少确认远端是私有的。
  3. 自动化（可选但推荐）。一个 cron 或系统自带的任务：git -C ~/.config/emacs pull --rebase 拉远端更新，git -C ~/.config/emacs push 推上去。

十二、排障：Emacs 起不来了怎么办

这一节是本章最实用的一节。Emacs 的坏处在于：配置错了不一定立刻报错，可能是启动到一半卡住、某个键失灵、或者某个模式莫名其妙不对。下面这套流程是按「从最狠的手段开始」排列的——先用最钝的锤子，实在不行再换精细的。

12.1 第一招：-Q 启动

如果你怀疑「是 Emacs 本身坏了」——它几乎不可能坏。99% 的情况下问题在你的配置里。-Q 就是回答这个问题的实验：

$ emacs -Q

Emacs 31.1 手册 (emacs) Startup Options 对 -Q 的定义是：「Start Emacs with minimum customizations. This is similar to using -q, --no-site-file, --no-site-lisp, --no-x-resources, and --no-splash together.」也就是说它把五件事一起关了：不读 init 文件、不读 site-start.el、不把 site-lisp 目录加进 load-path、不读 X 资源文件、不显示启动画面。emacs --help 上印的等价列表也是这五项，措辞略有出入（它把 --no-site-lisp 写成「do not add site-lisp directories to load-path」），以代码为准。

把这几件事分清楚：

启动相关命令行选项

选项等价于作用
-Q-q + --no-site-file + --no-site-lisp + --no-x-resources + --no-splash完全干净的环境，排障第一步
-q--no-init-file不读 init.el，但仍读 site-start.el 和 default.el 那一套
--no-site-file—不读 site-start.el。它没有短选项
-nsl--no-site-lisp不把 site-lisp 目录加进 load-path。注意别和上一行混：-nsl 管的是 site-lisp 目录，不是 site-start.el 这个文件。Emacs 手册 (emacs) Initial Options 里把 -nsl 那一条写成「Do not load site-start.el」，这是手册自己的笔误——src/emacs.c 里 argmatch 把它绑到的是 no_site_lisp，emacs --help 上印的也是 --no-site-lisp, -nsl。以代码为准。
--debug-init—init 文件里出错时进入 Elisp 调试器
emacs -q—跳过本次启动的 init.el。这只能在命令行做——Emacs 内部没有任何按键能做到这件事（常见误解是 M- Cx，我查过 32.0.50 的全部源码和手册，这个序列一个地方都没绑定）。所以习惯很重要：把它做成一个 shell alias，出事时才有退路。
--init-directory DIR—强制用 DIR 里的 init.el

-Q 能打开就说明 Emacs 二进制没问题，问题在配置；-Q 也起不来，问题在 Emacs 自身或环境（这时候先试 emacs --version，能回显就说明二进制是好的，问题更可能是显示层）。

12.2 第二招：--debug-init 让报错停下来等你

普通情况下，init.el 里的错误只会打印一行到 *Messages*，然后继续执行下一行——所以你看到的是「最后一条错误」，而不是「第一条错误」，而第一条才是真正的病根。--debug-init 改变这个行为。手册的定义是：「Enable the Emacs Lisp debugger for errors in the init file.」

$ emacs --debug-init

进去之后，如果 init 文件报错，你会直接落进 *Backtrace* 窗口，每一步求值都能看到当时的变量值。调试器里的常用操作（下面这份表是我从 lisp/emacs-lisp/debug.el 的 debugger-mode-map 和 backtrace.el 的 backtrace-mode-map 里逐条抄的）：

  • n / p：在回溯的各层之间前后移动。
  • b：把光标移到当前这一层（debugger-frame）。
  • j 数字 RET：直接跳到第 n 层（debugger-jump）。
  • e 表达式 RET：在指定那一层当时的变量环境里求值表达式（debugger-eval-expression）——查病根主要靠它。
  • d 单步求值，c 连续求值，u 抹掉当前层，r 插一个返回值，l 列出涉及的函数。
  • v：显示或隐藏当前层的局部变量。
  • RET：跟随光标处符号的交叉引用，跳去看它的定义。
  • q 退出调试器，C] 直接中止（abort-recursive-edit）。

顺带纠正一个流传很广的错法：调试器里没有 i（看源码）和 g（跳定义）这两个键——debugger-mode-map 和 backtrace-mode-map 里都查不到它们。想跳到某个符号的定义，按上面的 RET；想看这一层的变量，按 v。

如果你的 init.el 是字节编译过的（init.elc 存在），--debug-init 反而帮不上忙，因为调试器看到的是字节码。这时先删掉 init.elc，或者用 M- byte-recompile-directory RET 重编——注意这个命令要的是目录不是文件名（它的交互提示原文是 Byte recompile directory:，函数签名是 (DIRECTORY &optional ARG FORCE FOLLOW-SYMLINKS)），所以你该敲的是配置目录本身，比如 ~/.config/emacs。

12.3 第三招：读 *Messages* 和 *Warnings*

Emacs 的启动过程有两条输出通道，很多人只看了第一条。先说一个必须避开的坑：Cx Cm 后面跟 m/w/d 这套「看缓冲区」的键位是不存在的。我在本机把 Cx Cm 这个前缀下的全部绑定列了出来，它其实是编码系统前缀（set-language-environment、set-buffer-file-coding-system、set-input-method 等十一项），跟 *Messages* 毫无关系。查真实绑定可以用 M- describe-key RET C-x C-m RET。

;; 任何错误都进入调试器（比 --debug-init 范围更广）

;; 测量启动耗时。我在 Emacs 32.0.50 上实测过下面这个公式：
;; emacs -Q 时约 1.3 ms，载入一份小配置时是几十毫秒量级（batch 模式）。
(message "Emacs 启动耗时：%.1f ms"
         (* 1000 (- (float-time after-init-time)
                    (float-time before-init-time))))

12.4 第四招：二分法找病根

配置有五百行、报错信息只说「某个变量 void-variable」的时候，唯一有效的办法是二分。两个版本：

版本一（半小时内见效）：逐条注释。从 init.el 顶部开始，每注释掉三到五行就重启试一次。这听起来很笨，但在 500 行以内它是最快的。

版本二（配置在 git 里时用）：git bisect。如果你的配置进了版本库（第十一节），这是一个被严重低估的技巧——Emacs 的配置文件本身就是一个可以二分查找的程序：

cd ~/.config/emacs
git log --oneline | head -20          # 找到「最后能正常启动」的那个提交
git bisect start
git bisect bad HEAD                    # 现在这个是坏的
git bisect good <上次正常的提交>
# git 提示你去手动启动 Emacs 测试，好的敲 git bisect good，坏的敲 git bisect bad
git bisect reset                       # 测完退出二分

这之所以好用，是因为「Emacs 能不能正常启动」是一个天然的、非黑即白的测试用例——不需要你想出测试脚本，只需要每次重启看一眼。

技巧

每次改配置之前先 git commit，哪怕改的是一行注释。这不是为了「代码整洁」，是为了给 git bisect 准备足够密的检查点。如果你是「攒一个月才提交一次」，git bisect 二分出来的区间会有好几百行，那二分就失去意义了。

12.6 一份可以照抄的排障清单

遇到「Emacs 起不来了」，按顺序做下面五件事，每一步都会缩小范围：

  1. emacs --version —— 二进制本身能跑吗？
  2. emacs -Q —— 干净的 Emacs 能起来吗？
  3. emacs --debug-init —— 第一条错误是什么？
  4. emacs --batch --eval '(princ user-emacs-directory)' —— 它用的是哪个配置目录？
  5. 进去之后 Ch e —— *Messages* 最后十行说了什么？
要点

本章最重要的一句话：Emacs 的配置问题几乎全部是「你改的不是它读的那一份」。Emacs 会依次读 site-start.el、early-init.el、init.el、default.el，而「你的那份」到底落在 ~/.emacs.d/ 还是 ~/.config/emacs/，取决于哪条规则先命中。在花两小时调试一份配置之前，先花三十秒确认 Emacs 读的是哪一份。

练习 15　你的 init.el 有 600 行，第 400 行有个错误，但它不在报错的 *Messages* 里显示。怎么让它在第一个错误处停下来？

emacs --debug-init。它让 init 文件里的每一条错误都进入 Elisp 调试器，你在第一个错误处就能停下、反向追踪调用栈，定位到真正写错的那一行。如果 init.elc 存在，先删掉它或重新字节编译，否则调试器只能看到字节码。

练习 16　配置已经在 git 里了。上次能正常启动是三个月前的某个提交，现在起不来。用 git 二分找到是哪次改动引入的问题，前两步敲什么？

git bisect start，然后 git bisect bad HEAD（现在这个是坏的）加 git bisect good <三个月前的提交>。之后 git 会检出中间的某个提交，你手动启动 Emacs 测一次，好的敲 git bisect good、坏的敲 git bisect bad，重复直到 git 报出罪魁祸首的提交，最后 git bisect reset 退出。

进阶：读 Emacs 启动脚本源码的三个位置

遇到本文没覆盖的怪问题，值得直接去读 Emacs 的启动源码。本机 Emacs 32.0.50 的相关文件都在 lisp/startup.el，三个关键位置：

  • 配置目录的解析：startup--xdg-or-homedot 函数（6.1 节引用的那段规则就在这里）。
  • 加载顺序：command-line 函数里 site-run-file 加载那几行往后（6.2 节那六步都在这个函数里；early-init-file 紧跟其后，package.el 的初始化夹在两者之间，最后是 user-init-file）。
  • early-init.el 的名字：搜 early-init.el 会看到一段注释解释为什么这里硬写了 .el 后缀——为了让 startup--load-user-init-file 在文件不存在时把 user-init-file 设成 "early-init.el" 而不是像 .emacs 那样设成 "early-init"。这种「为什么这么写」的注释是 Emacs 源码里最有价值的部分。

在 Emacs 里读这些源码不需要找文件：M- find-function RET startup--xdg-or-homedot RET 会直接跳到源文件对应位置。
