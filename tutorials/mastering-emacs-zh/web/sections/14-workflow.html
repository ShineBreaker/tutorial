十四、现代工作流实战

前面十三章把 Emacs 的「内功」讲完了：移动、编辑、Elisp、配置。这一章讲「干活」——你在真实项目里每天要用的六件事：用 Magit 提交代码、用 LSP 补全和调试、用 project.el 管住一个大项目、用 Dired 和书签在文件间穿梭、用 Org-mode 管待办和数据、把 Emacs 接进 shell 与外部工具。读完你能配出一套能替代 VS Code 日常开发的工作流，并且知道每一块该用内置的、该用第三方的、以及它们的代价是什么。

要点

本章所有关于 Emacs 内置功能的断言，都在本机 GNU Emacs 32.0.50 上用 emacs --batch -Q 逐条查过源码或运行时行为；关于第三方包的版本与维护状态，查的是 2026 年 10 月 3 日的 GNU ELPA / MELPA 包索引与 GitHub 仓库。凡是我没查到、或者查到的结果和网上流传的说法不一样的，我都会单独标出来——这类地方恰恰是最容易照抄出错的地方。

要点

先说版本坐标。截至 2026 年 10 月，Emacs 的稳定版是 31.1，发布于 2026 年 8 月 24 日（这三个日期来自 Emacs 源码树里的 etc/HISTORY 文件：30.1 是 2025-02-23，30.2 是 2025-08-14，31.1 是 2026-08-24）。本章写作时开发版是 32.0.50。本书讲的是「原书（Emacs 26–30 时代）的内容 + 今天的正确做法」，所以凡是 28/29/30/31 变过的地方我都会写清楚「从哪个版本开始是这样」。

一、版本控制：Magit 全流程

版本控制（version control，记录你对文件的每一次改动、并且随时可以回退的系统）你已经在 VS Code 里用过 Git 了。Emacs 自带一套叫 vc 的版本控制框架和它的 Git 后端 vc-git，但今天没人用它——不是因为它坏了，而是因为它设计上假设「你已经知道该敲什么命令」，而不是把 Git 的状态摊开给你看。Magit（读作「马吉特」）是 Emacs 社区重写的 Git 前端，核心理念只有一句：把所有 Git 状态放进一个可编辑的文本缓冲区，让它像普通文本一样被搜索、跳转、复制。

1.1 安装：Magit 需要什么

Magit 是第三方包，装在 MELPA（Mel 的 ELPA，Emacs 的第三方包仓库；和官方保守的 GNU ELPA 并列，访问 https://melpa.org）里。截至 2026-10-03，MELPA 上的 Magit 版本是 20261002，上游仓库 github.com/magit/magit 最后一次提交是 2026-10-02，维护非常活跃（GitHub API 查到的 stars 约 7230）。

它不是单文件包，会自动拉四个依赖：compat、cond-let、llama、以及内置的 transient。我在本机装的 Magit 4.7.0 的文件头里读到它自己的声明：

;; Package-Version: 4.7.0
;; Package-Requires: (
;;     (emacs        "28.1")
;;     (compat       "31.0")
;;     (cond-let      "1.1")
;;     (llama         "1.0")

也就是说 Magit 需要 Emacs 28.1 或更高。装法（M-x package-install 之后依次输入 RET）：

M-x package-install RET
magit RET

如果你用第 13 章讲的 use-package，配置文件是这样：

(use-package magit
  :bind (("C-m g" . magit-status)   ; 用 C-m g 打开状态缓冲区
         ("C-m l" . magit-log)      ; 直接看提交历史
         ("C-m b" . magit-blame)))  ; 对当前行查 blame

transient 是什么？它是 Emacs 从 28 版起自带的「弹出式菜单」库（lisp/transient.el）。Magit 3.0 之后所有的 Magit 操作菜单都建立在它之上——你按 g 之后弹出来的那块浮层，里面一列列写着「What」「How to」「Display」的可选项，就是 transient 画出来的。这个东西很好用，但也是新手最容易不适应的地方，下面会专门讲。

1.2 状态缓冲区：一切从 magit-status 开始

Magit 模式（Magit mode）是一种「单缓冲区多窗口」的界面：你在一个文件里编辑，C-x C-m 之后多出一块小窗显示仓库状态，两块窗共享同一个缓冲区。命令是 magit-status（快捷键 C-x C-m，绑定在 global-magit-mode-keymap 上）。

Magit 缓冲区里按 j 会弹出一块 transient 面板，可以直接跳到各个分区。这些分区名是 Magit 的词汇表，先记住六个：

  • Untracked files（未跟踪文件）：Git 完全不认识的新文件。
  • Unstaged changes（未暂存的改动）：你改了，但还没 git add。
  • Staged changes（已暂存的改动）：git add 过、还没 git commit。
  • Stashes（贮藏）：git stash 存起来的东西。
  • Unpushed commits（未推送的提交）：本地提交了，还没 git push。
  • Conflicts（冲突）：合并时两边改了同一处。

「暂存」（stage）这个概念是 Git 独有的，两段式提交：先 git add 把改动放进暂存区，再 git commit 把暂存区打包成一个提交。你可以在一个仓库里暂存一部分文件、分两次提交，这是 Git 最有用的能力之一，也是 VS Code 的图形界面做得最别扭的地方。

1.3 暂存与提交

Magit 里所有字母键都在 transient 面板上等你选，所以不用背。常用的是这几个：

  • 暂存/取消暂存单个文件：光标放在文件名那行，按 s，弹出 transient 面板，选 Stage changes（暂存改动）还是 Unstage changes。如果按 s 之前先按 SPC（空格），Magit 会把光标移到下一个文件——这是 Magit 的通用技巧，叫 hunk/file cycling：SPC 移动，S-a 暂存然后自动跳下一个。
  • 逐块暂存：如果一个文件里有好几处改动，你只想暂存其中一段，就在 diff（差异视图，Magit 显示「这一行代码改前改后」的表格）里把光标移到某个 hunk（改动块）上按 s，弹出的面板里有 Stage this hunk。
  • 丢弃改动：在文件那行按 x，选 Discard changes。这一步不可逆，Emacs 不会给你撤销的机会。
  • 提交：按 c，在 *Magit-Commit* 这个缓冲区里写提交信息。C-c C-c 完成并关闭，C-c C-k 放弃。

提交信息缓冲区（log-edit）里有两个 Emacs 帮你写提交信息的工具：M-p 插入模板、M-t 往提交里加一行 Signed-off-by:（这个是 DCO，Developer Certificate of Origin 的缩写，很多开源项目强制要求）。

易错

最常见的 Magit 事故：暂存错了但已经 commit。如果你 commit 之后发现某个文件不该进去，处理顺序是：先 l（magit-log）找到那次提交，按 c 选 Commit 区域的 Reset this commit to HEAD~（把这次提交撤掉，改动回到暂存区），确认后再重新提交。不要用 git reset --hard——那个命令会连工作区的未提交改动一起抹掉。

技巧

在 diff 视图里，n / p 跳到下一个/上一个区块（magit-section-forward / magit-section-backward，区块就是一个 hunk 或一个文件），M-n / M-p 跳到同级的前后区块，TAB 折叠/展开当前区块，^ 跳到父区块，0 把 diff 的上下文行数恢复默认，+ / - 增加/减少上下文，SPC / DEL 上下滚动，C-c C-d 是 magit-diff-while-committing（一边写提交信息一边实时看 diff）。这些键定义在 magit-section-mode-map 和 magit-mode-map 里，所有 Magit 缓冲区通用，属于「学一次到处用」的那一类。

1.4 看历史：log 与 rebase

命令 magit-log（l）。Magit 不弹外部窗口，而是把 log 直接显示在当前的 diff / file 缓冲区里——所以你能在看 diff 的同时用 M-n 逐条翻历史，这是 Magit 比命令行 git log 顺手得多的地方。

常用的历史操作都挂在 l 的 transient 面板上：

  • 复现某次提交：光标在一条提交上按 c，选 Cherry-pick，把那次提交的改动拿到当前分支。历史上还有一个独立命令 magit-cherry-pick，绑定在 A（对应命令行 git cherry-pick）。
  • 丢弃某次提交：同一位置按 c，选 Remove this commit（内部走的是 git revert，会产生一个新提交，不会改写历史）。真要改写历史要用下面两种。
  • 改写历史：rebase。Magit 把交互式 rebase 做成了一个带复选框的缓冲区：每条提交左边有个复选框和 pick、reword、edit、squash、fixup、drop 六个动作，你在缓冲区里直接改这些单词，然后 C-c C-c 提交给 git 真的执行。这比自己敲 git rebase -i HEAD~5 打开一个临时文件改要安全得多——因为你在改的是 Magit 自己的缓冲区，改错了 C-c C-k 就能丢掉。
要点

rebase 会改写历史，所以只能用在你自己的、还没 push 给别人的分支上。如果一条提交已经推到远端共享给别人了，rebase 之后别人 pull 就会冲突得莫名其妙——这是新手最常见的「我把同事的仓库搞坏了」。Magit 在这一点上帮不了你，它不判断分支有没有共享。

1.5 blame 与 bisect

Blame（逐行追溯）回答的是「这一行代码是谁、哪一次提交写的」。命令 magit-blame，绑定在 b。它会创建一个 *magit-blame* 缓冲区，每一行源码左边加上「提交哈希 + 作者 + 日期」。在这个缓冲区里：

  • n / p：magit-blame-next-chunk / magit-blame-previous-chunk，跳到下一处/上一处「改动很近」的相邻行（Magit 会把连续的同提交行合并成一组，按键在组之间跳，不是逐行跳）。
  • N / P：跳到同一提交内的相邻块（不想离开当前 commit 时用）。
  • b / r：只看新增行 / 只看被删的行。
  • C-m：magit-show-commit，跳到那个提交的详情。
  • c：magit-blame-cycle-style，轮换 blame 的显示样式。
  • q：关闭（也有 C-c C-q）。

Bisect（二分查找）回答的是「从好版本到坏版本之间，是哪一次提交引入的 bug」。原理很简单：bug 有 N 个提交时，把 N 减半，所以只需要 log2(N) 次测试——1000 个提交只要 10 次。Magit 把状态机做进了仓库配置里：magit-bisect-start 开始，magit-bisect-good / magit-bisect-bad 标记，magit-bisect-reset 结束。

Magit 的 bisect 缓冲区里每条候选提交右边有一列按钮，直接按 b 标 bad、g 标 good、h 打开来看它改了什么、m 跳到某个提交手动改。关键的好处在最后：

The first bad commit is:
  abc1234  Fix the thing   (Jane Doe, 2026-03-02)

Magit 会把结论保留在仓库里，你 l 打开 log 时，这个结论会挂在提交上面，直到你 magit-bisect-reset。

1.6 那内建的 vc 怎么办

Emacs 的 vc（lisp/vc/vc.el 和 lisp/vc/vc-git.el，两个文件在本机 Emacs 32.0.50 里都存在）是官方自带的版本控制框架。它的全局键是：

  • C-x v v — vc-next-action（版本控制的「下一步」，对不同后端分别是 update / commit）
  • C-x v i — vc-include（相当于 git add）
  • C-x v c — vc-checkin（相当于 git commit）
  • C-x v a — vc-update（相当于 git pull）
  • C-x v b — vc-branch，C-x v = — vc-revert，C-x v s — vc-svn-command

进了文件缓冲区之后会多一个 vc-mode（主模式），里面绑了 C-c C-v（update）、C-c C-c（checkin）、C-c C-p（log）、C-c C-k（revert）等。

要点

结论：两者不要同时开。如果你已经决定用 Magit，就不要去 M-x customize 里动 vc-handled-backends，也不要给 vc-git 绑键。两个前端共用一套「这个文件被修改了吗」的钩子，混用会出现 Magit 缓冲区不刷新、C-x v v 抢走按键这类问题。反过来，如果你就是想要一个零配置的「C-x v v 提交一下」，那 vc 完全够用，只是没有 Magit 的状态视图。

易错

Magit 有两个「模式」容易混：global-magit-mode（全局次模式，负责让 C-x C-m 到处能用）和 magit-mode（在文件里显示 Git 的状态标记，比如行尾那个 +- 符号）。初学者常常只想开第二个，结果发现 C-x C-m 没反应。两个都要开。

易错

Magit 会把整份 diff 塞进 Emacs 的 undo 历史。一个几千行的改动会让 buffer-size-limit 报警、M-x garbage-collect 变慢、甚至触发 undo-list-too-big。Magit 4.x 已经处理了大部分场景，但你要是处理特别大的生成文件，加上 (setq magit-verbose-default t) 看看发生了什么。

练习 1　你刚装好 Emacs，什么都没配。想提交一个文件，应该按哪个键？为什么不该按 C-x v v？

M-x magit-status（即 C-x C-m）。C-x v v 是内置 vc 的入口，理论上也能提交，但如果你打算用 Magit 就不该碰它——两套前端混用会互相干扰。而且 vc 要求先手工设置 vc-handled-backends，对零基础读者不友好。

练习 2　在 Magit 状态缓冲区里，光标停在一个已修改但未暂存的文件名上，要把它加进暂存区，按什么键、选哪一项？

按 s，在弹出的 transient 面板里选 Stage changes。想暂存后自动跳到下一个文件，就先按 SPC 把光标移到下一个改动，再按 s。

练习 3　你 commit 之后发现某个文件不该进这次提交，已经 push 了。Emacs 里怎么撤销这次提交？为什么不用 rebase？

在 magit-log 里选中那次提交，按 c，在 transient 面板的 Commit 区选 Remove this commit——它内部用的是 git revert，会生成一个新提交来抵消原来的改动，不改写历史。rebase 会改写提交哈希，提交一旦 push 给别人，别人 pull 就会冲突，所以共享过的分支上只能用 revert。

要点

下一节讲语言支持：auto-mode-alist / interpreter-mode-alist 是怎么决定「一个文件用什么模式打开」的，内置 tree-sitter 模式覆盖了哪些语言，以及 Eglot 和 flycheck 该选哪个。

二、语言支持

Emacs 自己不认识 Rust、TypeScript、Go。它的办法很朴素：用正则表达式去认。这一节从「Emacs 怎么给一个文件挑主模式」讲起，然后依次引入语法高亮、语义支持（LSP）、调试器（DAP）和结构视图。

2.1 auto-mode-alist：Emacs 怎么决定用哪个模式

major mode（主模式）是 Emacs 给一个缓冲区选的「语言」。它同时决定：语法高亮规则、缩进规则、注释怎么定义（注释在哪结束）、以及这个模式下有哪些键。minor mode（次模式）是可选的开关，可以叠加。

Emacs 判断「这个文件该用哪个 major mode」由命令 set-auto-mode 完成，它按下面这个顺序一条条试，全落空才放弃（这段顺序对着 lisp/files.el 里的 set-auto-mode 核过）：

  1. 目录局部变量：先看文件所在目录的 .dir-locals.el 和 buffer 局部变量里有没有指定模式。
  2. 按 shebang 猜：拿 buffer 第一行去匹配 auto-mode-interpreter-regexp，把认出来的解释器名（如 python3）拿去查 interpreter-mode-alist。这个变量默认就有一条 ("python[0-9.]*" . python-mode)，所以一个没有 .py 后缀、但第一行是 #!/usr/bin/env python3 的文件，也会被 Python 模式打开。
  3. 按内容猜：magic-mode-alist，默认是空的，留给用户自己写内容特征规则。
  4. 按文件名猜：用文件名（含后缀）去查 auto-mode-alist。这个变量是正则表达式 → 函数的列表（「alist」就是「关联列表」，Emacs 里最常见的「表」结构），按 suffix . mode 匹配文件名，匹配上了就用它。扩展名 .rs 对应 rust-ts-mode、.ts 对应 typescript-ts-mode，都是这条规则。
  5. 兜底：magic-fallback-mode-alist（默认同样为空）。
  6. 全都不是：用 fundamental-mode（基础模式），也就是纯文本，什么高亮都没有。
易错

最常被说错的一条：auto-mode-alist 匹配的是文件名，不是文件内容。靠 shebang 认出解释器模式走的是另一个变量 interpreter-mode-alist，而它比文件名匹配更早执行——所以一个叫 Makefile.am 却以 #!/bin/sh 开头的文件，Emacs 会先用 shebang 认成 sh-mode，压根轮不到 auto-mode-alist。

你想加一条自己的规则，就往 auto-mode-alist 前面插。因为是从上往下匹配，插在前面才能覆盖内置规则：

;; 让 .log 结尾的文件用 js-mode 打开（log 里有 json 行）
(add-to-list 'auto-mode-alist '("\\.log\\'" . js-mode) t)
;; 去掉末尾的 t，就是追加到末尾（优先级最低）

;; 或者直接改文件关联
(assoc-set! auto-mode-alist "\\.foo\\'" 'fundamental-mode)
技巧

想知道 Emacs 到底给当前缓冲区选了什么模式：按 C-h m（describe-mode）看当前主模式的说明，或者看模式行右上角的名字。想知道「为什么是这个模式」，用 M-x describe-function RET auto-mode-alist 然后顺着点进去看；shebang 那条路要查的是 interpreter-mode-alist。

2.2 syntax-propertize-function：给没有主模式的格式打补丁

语法高亮的原理是：Emacs 把缓冲区切成一个个 region（区域），每个区域打一个 font-lock（字体锁定）属性指定用什么 face（字体样式）显示。这个「用什么正则切、每个块算什么」的规则表叫 syntax table（lisp/emacs-lisp/syntax.el）。

假如你天天处理一种 Emacs 不认识的格式（比如公司内部的 .tpl 模板），正确做法不是硬塞一个不相关的主模式，而是给它写一张专用语法表，再用变量 syntax-propertize-function 挂到 fundamental-mode 上。Emacs 32 的 Elisp 手册里文档化的就是这条路径（doc/lispref/syntax.texi）。完整例子——给一种 "字符串"、<类型> 的格式加高亮：

(defvar myfmt-syntax-table
  (let ((table (make-syntax-table)))
    (modify-syntax-entry ?\" "\"" table)   ; 双引号是字符串定界符
    (modify-syntax-entry ?\\ "\\" table)   ; 反斜杠是转义符
    table))

(defvar myfmt-font-lock-keywords
  `((("「[^」]*」") . font-lock-string-face)        ; 「中文引号」当字符串
    (("\_<[A-Za-z_][A-Za-z0-9_]*\_>") . font-lock-type-face))) ; <Server> 当类型名

;; syntax-propertize-function 要的是一个「函数」，
;; 它接受 start / end 两个位置参数，在这段范围内打 syntax-table 文本属性。
;; 规则用 syntax-propertize-rules 这个宏声明，一次扫描同时处理所有规则。
(defun myfmt--syntax-propertize (start end)
  (syntax-propertize-rules
    ("\_<[A-Za-z_][A-Za-z0-9_]*\_>" (0 (string-to-syntax "w_")))))

(add-hook 'fundamental-mode-hook
          (lambda ()
            (setq-local syntax-table myfmt-syntax-table)
            (setq-local syntax-propertize-function #'myfmt--syntax-propertize)
            (setq-local font-lock-defaults '(myfmt-font-lock-keywords))))

;; 最后把 .tpl 关联到 fundamental-mode，靠上面那个 hook 生效
(add-to-list 'auto-mode-alist '("\\.tpl\\'" . fundamental-mode))

四段的意思分别是：造一张新语法表；声明 font-lock 的搜索规则；写一个 syntax-propertize-function（Emacs 会在 syntax-ppss 和语法字体化时反复调用它，所以它必须把该模式用到的所有语法属性都打上）；最后把 .tpl 关联到 fundamental-mode。这里不需要自己 define-derived-mode，因为 syntax-propertize-function 本来就是设计成挂在基础模式上的。

易错

老教程里的 syntax-propertize 宏和今天的文档对不上。Emacs 32 的 Elisp 手册（doc/lispref/syntax.texi、modes.texi）文档化的入口是 变量 syntax-propertize-function 加宏 syntax-propertize-rules；我在本机 32.0.50 上 (documentation 'syntax-propertize) 只查到「接受一个 pos 参数」的函数，整棵 lisp/ 里 grep 也没找到那个接受 (syntax-table keywords [mode]) 的老宏定义。不同 Emacs 版本的裁剪方式可能不一样（你可以自己敲 M-x syntax-propertize 看补全列表），但按手册那条路写最稳——上面那段就是这么写的。

另外有一个坑：syntax-propertize-function 一旦非 nil，Emacs 会把 syntax-table 文本属性全部清掉再让你重打，所以它必须是完整的，不能只打你关心的那一部分——从 CC Mode 派生的模式尤其不能这么干，因为 CC Mode 用了另一套机制来维护这些属性（手册原文就这么警告）。

易错

什么时候压根不该走这条路？如果那种语言已经有成熟的主模式（哪怕第三方包提供的），直接换模式。写语法表只适合「没有模式、但格式很稳定」的场景——CSV、JSONL 日志、某种 IDL。代价是：语法表只管颜色，不管缩进、不管注释命令、不管代码结构。一份两千行的 Elisp 只为了高亮去写，值得掂量一下。

2.3 内置 tree-sitter 模式：现在开箱覆盖 18 种语言

Tree-sitter 是 2017 年后兴起的增量解析库：给一段文本，它产出一棵语法树，而不是一行行地做正则匹配。这带来两个传统正则做不到的好处——缩进跟着语法树走（不会因为字符串里有个括号就乱），以及高亮不受多行结构影响。

Emacs 从 29 版开始内置了 tree-sitter 解析库（NEWS.29 里明确写了「Emacs can be built with the tree-sitter parsing library」，并且可以用 --without-tree-sitter 关掉），并在 29、30、31 里逐步加入了用 tree-sitter 实现的内置模式。我在 Emacs 32.0.50 的 lisp 目录里数了一遍，一共 18 个内置的 *-ts-mode：

lisp/progmodes/:  c-ts-mode  cmake-ts-mode  dockerfile-ts-mode  elixir-ts-mode
                   go-ts-mode  heex-ts-mode  java-ts-mode  json-ts-mode
                   lua-ts-mode  php-ts-mode  ruby-ts-mode  rust-ts-mode
                   typescript-ts-mode
其它目录:          html-ts-mode  markdown-ts-mode  mhtml-ts-mode
                   toml-ts-mode  yaml-ts-mode

也就是说：C、C++、Go、Rust、Java、PHP、Ruby、Lua、Elixir、CMake、Dockerfile、JSON、TypeScript、HTML、Markdown、YAML、TOML、MHTML——这 18 种语言装好 Emacs 就有了，不用装任何包。Python 不在内置列表里（python-ts-mode 还没进 Emacs），JS 的内置模式是 typescript-ts-mode（它同时管 .js）。

要更多语言（Python、OCaml、Haskell、Elisp……）就得装第三方包：

(use-package tree-sitter
  :diminish t
  :config
  (global-tree-sitter-mode))

(use-package tree-sitter-langs
  :after tree-sitter
  :config
  (global-tree-sitter-mode)
  (add-to-list 'tree-sitter-extra-modes #'tree-sitter-python-mode)
  (add-to-list 'tree-sitter-extra-modes #'tree-sitter-haskell-mode))

tree-sitter 包在 MELPA（版本 20260116），仓库 github.com/emacs-tree-sitter/elisp-tree-sitter（约 854 stars，最近提交 2026-09-01；注意仓库已经改名，老的 alexanderkasting/tree-sitter.el 已经不存在了）。tree-sitter-langs 也在 MELPA（20260729），仓库 github.com/emacs-tree-sitter/tree-sitter-langs。

易错

tree-sitter 不是免费的。它要求 Emacs 是带 tree-sitter 库编译的构建（发行版打包时可能没带，Guix、Nix、Homebrew 一般都带）。而且每个语言都要有对应的 parser（用 C 写的动态库），tree-sitter-langs 会自动下载它们——这意味着第一次用某个语言时有编译延迟和磁盘占用。语法高亮不精确的文件树还会让缩进出错，这是它最大的实际风险：先用内置模式验证一遍，再决定要不要接 tree-sitter。

2.4 Eglot 还是 flycheck：先讲清楚这两者不是一回事

这是初学者最常混淆的地方。LSP（Language Server Protocol，语言服务器协议）是微软定的一套标准：编辑器负责界面和文件，语言服务器（一个独立进程）负责真正的语义分析——跳转定义、查引用、重命名、自动补全、诊断报错。Eglot 是 Emacs 内置的 LSP 客户端；flycheck 是第三方检查器框架，它跑的是 linter / type checker / 编译器，不是 LSP。

维度Eglot（LSP，内置）flycheck（检查器，第三方）
从哪来Emacs 29 起内置（lisp/progmodes/eglot.el），也能从 ELPA 升级MELPA 包 flycheck（2026-10-03 版本 20260902），仓库 github.com/flycheck/flycheck
做什么跳转定义、查引用、重命名、补全、格式化、诊断运行外部检查器并收集诊断（语法错、类型错、lint 警告）
需要外部程序吗要，每种语言一个 language server（pyright、rust-analyzer…）要，每种检查器一个可执行程序（flake8、shellcheck…）
快慢启动慢（每次要起一个语言服务器进程），之后很快启动快（通常是一次性命令），但每次检查都要重跑
适合大型项目、多语言、需要「改一处全项目更新」小项目、只想快速知道「有没有明显错误」

选择标准，我给你三条：

  1. 只用一种语言、代码量在几千行以内——先不上 LSP，用内置高亮 + 需要时手动跑检查。省下的启动时间和配置时间比功能值钱。
  2. 需要「改一个函数名，全项目 80 处调用点自动更新」——必须 Eglot（或等价的 LSP 客户端），flycheck 做不了这件事。
  3. 你在意「跨文件查找谁调用了这个函数」——还是 Eglot。这是 LSP 的核心价值，语法高亮和检查器都给不了。

Eglot 的配置很小，核心只有一行 eglot-ensure：打开文件时，如果该语言的 server 没起，就起一个。

(use-package eglot
  :diminish t
  :hook ((python-mode . eglot-ensure)
         (python-ts-mode . eglot-ensure)
         (rust-ts-mode . eglot-ensure)
         (go-ts-mode . eglot-ensure)
         (c-ts-mode . eglot-ensure)
         (c++-ts-mode . eglot-ensure)
         (typescript-ts-mode . eglot-ensure)
         (rust-mode . eglot-ensure))
  :config
  (setq eglot-autoshutdown t   ; 关掉文件后自动关掉语言服务器，省内存
        eglot-report-progress nil)  ; 别在 mode line 上刷进度
  :commands
  ((:eval eglot-ensure) eglot-find-declaration eglot-find-references
   eglot-rename eglot-format eglot-code-actions))

「有语言服务器找不到」的报错，答案在变量 eglot-server-programs 里（定义在 lisp/progmodes/eglot.el）。它的结构和普通 alist 有一个关键区别：key（CAR）可以是一个模式名列表，所以 alist-get 在这里经常返回 nil，得自己筛：

;; 正确写法：把 key 展开成列表再筛
(cl-remove-if-not

                  (memq 'go-ts-mode (car e))))

;; => ((("go-mode" "go-dot-mod-mode" "go-dot-work-mode"
;;          "go-ts-mode" "go-mod-ts-mode" "go-work-ts-mode") "gopls"))

;; 意思：打开 go 文件时启动 gopls（CDR 可以是程序名，

java-mode 其实已经在默认表里了（默认给的是 jdtls 和 java-language-server 供你挑），所以一般的 Java 项目不用自己加。只有当你想指定额外参数、或者想让某门语言走一个默认表里没有的程序时，才自己加一条：

(add-to-list 'eglot-server-programs

易错

网上大量教程说「Eglot 默认把 C-c C-d 绑成跳到定义」。这不是真的。我在 Emacs 32.0.50 的 lisp/progmodes/eglot.el 里查了 eglot-mode-map 的完整定义，它只有一条绑定：把 C-h（display-local-help）重映射到 eldoc-doc-buffer，也就是看文档。其余全部动作都要用 M-x，命令名见下表。所以务必自己绑键，否则「Eglot 装了却没反应」是最常见的新手困惑。

如果你两个都想留（我推荐的折中：LSP 负责跳转重命名，flycheck 负责额外的 linter），配置是这样：

(use-package flycheck
  :diminish t
  :config
  (global-flycheck-mode 1)
  (add-hook 'python-mode-hook 'flycheck-mode)
  ;; flycheck 会在 Eglot 诊断之外再加一层，例如：
  (add-hook 'sh-mode-hook 'flycheck-mode))

代价是诊断信息可能重复显示（同一个错误两边各报一次）。真要两个都用，flycheck 的新式诊断可以用 (setq flycheck-diagnostic-functions '(flycheck-define-diagnostic)) 让它们走同一条渲染通道。

2.5 dap-mode：调试器也走协议

调试（debugging）在 Emacs 里一直很弱——内置的 debug.el 面向的是调试 Emacs 自己的 Lisp，不是你的程序。dap-mode 补上了这一块：DAP（Debug Adapter Protocol，调试适配器协议）是 LSP 的调试版对应物，一个统一协议加上一个适配器进程，就能驱动 gdb、lldb、Delve（Go）、debugpy（Python）、Chrome DevTools（前端）等等。

安装：MELPA 包 dap-mode（2026-10-03 的版本是 20260616），仓库 github.com/emacs-lsp/dap-mode（约 1386 stars，最近提交 2026-06-19；注意它已经从 jimeh/dap-mode 搬到 emacs-lsp 组织下了，旧地址已不存在）。

(use-package dap-mode
  :diminish t
  :commands (dap-debug dap-debug-last dap-debug-recent dap-continue
            dap-next dap-step-in dap-step-out dap-eval)
  :config
  (dap-mode 1)
  (dap-ui-mode 1))

常用的交互式命令（我直接从 dap-mode.el 源码里列出来的，都是真实存在的函数名）：dap-debug、dap-debug-last、dap-debug-recent、dap-continue、dap-next、dap-step-in、dap-step-out、dap-debug-restart、dap-eval、dap-eval-region、dap-eval-thing-at-point、dap-breakpoint-toggle、dap-switch-thread、dap-switch-stack-frame、dap-stop-thread、dap-disconnect、dap-up-stack-frame、dap-down-stack-frame。

易错

我没法给你一份「 dap-mode 默认键位表」，因为它没有一个静态的默认键位表。我读了 emacs-lsp/dap-mode 仓库当前源码：dap-mode-map（dap-mode.el 第 2076 行）里只有两条鼠标绑定（行号边距点击切换断点），键盘绑定分散在 dap-ui.el 的各个小键表里，而主键位要靠你在 use-package 的 :bind 里自己定。dap-mode 的新 UI（dap-ui，2024 年之后）替换了老的 dap-hydra，行为和网上老教程不一样。正确做法：先按上面的命令把 :bind 写好，然后用 C-h m 在调试缓冲区里查当时的真实键位。

2.6 树形视图与折叠

最后一块是「看结构」。Emacs 内置了几套，各有各的用处：

  • Imenu（M-x imenu，默认全局键是 M-g i；我实测 Emacs 32.0.50 上 M-<i 并没有绑定）：按当前 buffer 的主模式抽出所有顶层定义（函数名、类名、标题），在一个小窗里列出。这是最通用的一套，主模式提供 imenu-create-index-function 就能用。
  • Outline（lisp/outline.el）：折叠机制。老的 hideshow.el 已经并进 outline.el，命令名全部加了 outline- 前缀，绑定也换成了 C-c 双键：C-c C-c 折叠当前段（outline-hide-entry）、C-c C-d 折叠整棵子树（outline-hide-subtree）、C-c C-a 全部展开（outline-show-all）、C-c C-s 展开子树、C-c C-n / C-c C-p 上下跳可见标题。「全部折叠」没有单独一个键，常用做法是 M-x outline-hide-sublevels 或 M-x outline-hide-body。不同主模式定义不同的「段」：Org 按标题、Outline/Info 按标题、Prog 按 defun。
  • tree-sitter 模式自带语法树导航（treesit 库提供，M-c 前缀）。这套键在 Emacs 29 到 30 之间改过名字（文件从 lisp/treesit.el 搬到了 lisp/tree-sitter/），我没法给你一份跨版本都准的表——以 C-h m 为准：在任何 *-ts-mode 缓冲区里按 C-h m，看 M-c 那一节。
  • Speedbar（speedbar.el，内置）：屏幕左边一条细长的文件树。它早年的依赖 fsf.el 早已从 Emacs 里删掉了，现在 M-x speedbar 直接能用，但在很大的目录上确实会明显变慢。

一个实用的组合——让 Imenu 常驻，并且给所有编程模式都打开 outline 折叠：

(add-hook 'prog-mode-hook #'outline-mode)

;; 全局开启 Imenu（按 C-h m 可以看到任何模式有没有提供索引函数）
(global-imenu-mode 1)

练习 4　你按官方步骤装了 Eglot，语言服务器也起来了，mode line 上出现了小图标，但按 C-c C-d 什么都没发生。为什么？

因为 Eglot 没有绑定 C-c C-d。Emacs 32.0.50 里 eglot-mode-map 只重映射了 C-h。所有动作都要用 M-x 调用，或者自己在配置里 :bind。网上那些「Eglot 自带 C-c C-d」的说法对应的是更早的第三方 eglot-langsrv，不是内置版本。

练习 5　Emacs 打开 script 这个没有扩展名的文件时，选了 Python 模式。Emacs 是靠什么判断的？

靠文件第一行的内容，但走的不是 auto-mode-alist。set-auto-mode 拿第一行去匹配 auto-mode-interpreter-regexp，认出解释器名（这里是 python3），再去查 interpreter-mode-alist——那个变量默认就有一条 ("python[0-9.]*" . python-mode)。文件名后缀匹配（查 auto-mode-alist）排在它后面，是第二道 fallback。

三、文件与项目

Emacs 里「打开文件」永远只是 C-x C-f。但真实工作不是「打开一个文件」，而是「在三千个文件的项目里快速找到并切换到那一个」。这一节讲三套机制：project.el 管住项目的范围，bookmark / recentf / savehist 记住你去过哪里，consult 把所有「选择一个东西」的界面统一成同一个样子。

3.1 project.el：Emacs 内置的项目管理

项目（project）在 Emacs 里是一个抽象：项目类型（project type）负责「怎么认出项目根目录」，项目实例（project instance）负责「这个项目有哪些命令」。project.el（lisp/progmodes/project.el）是 Emacs 25.1 进的本体——NEWS.25 第 1025 行的标题就是 “New package Project”，归属的小节是 “Changes in Specialized Modes and Packages in Emacs 25.1”；本书作者在 32.0.50 自带的 NEWS.24、NEWS.26、NEWS.27、NEWS.28、NEWS.29 里 grep “New package … Project” 全部零命中，所以 25.1 是唯一正确的答案（网上有说 27、28、29 的，都是以讹传讹）。要分清两个东西：包本身 25.1 就有，但 C-x p 这个前缀键表是 Emacs 28.1 才加的（NEWS.28 第 2261 行 “New prefix keymap ‘project-prefix-map’”），在 25–27 上你得用 M-x project-find-file。28.1 那一版还顺带宣布了新命令 project-switch-project、project-dired、project-shell、project-eshell、project-compile，以及新变量 project-list-file。

3.4 dired 与 dired-x：先纠正一个流传很广的说法

第 11 章已经讲了 Dired 的用法。这里补一件必须说清楚的事，因为网上到处在传：dired-x 不是第三方包了，它是 Emacs 自带的。

我实测的证据：Emacs 32.0.50 的源码树里有 lisp/dired-x.el（文件头写着 Copyright (C) 1993-2026 Free Software Foundation、Package: emacs、This file is part of GNU Emacs），而且 (require 'dired-x) 直接返回成功。判断「一个东西是不是内置」有个通用办法：M-x locate-library RET dired-x RET，路径落在 Emacs 自己的 lisp/ 目录下就是内置，落在 elpa/ 下才是装的。

易错

find-file 本身没法「增强」——它是 C 代码，不接受 Elisp 钩子。但你可以从两头动手：

练习 6　你现在在 monorepo 里的一个子包，Emacs 有三十几个缓冲区属于这个大仓库。项目管理那套前缀键里，哪三个能帮你收拾残局？

练习 7　你想找回三个月前读过的一个函数，但那个文件早就被重构掉了。用哪个功能？为什么不是另一个？

用 bookmark——它只记你手动标记过的位置，不会自动淘汰。recentf 只留最近 recentf-max-saved-items（默认 25）个文件，早就滚出去了。前提是你当时记得按 C-x r m。

练习 8　你想在 Dired 里批量把一百个 .png 改成 .jpg，需要装第三方包吗？

不需要。整目录重命名一直是 dired 本体自己的命令 dired-do-rename，键是大写 R（小写 r 在现代 dired 里已经没有绑定了）：按 R 打开查询和替换的 minibuffer，命令是 %.jpg，确认即可。想先按正则批量标记再改，就用 % r（dired-do-rename-regexp）。dired-x 现在也是 Emacs 自带的，而且它已经不再负责重命名了。

四、结构化文本：Org-mode 够用即可

结构化文本（structured text）是「有格式约定的纯文本」——Markdown、reStructuredText、Org-mode 都是。它相对 Word 的唯一优势是：它是文本，能 grep、能 diff、能进 Git、能被脚本处理。凡是「我需要一份能被别人用文本工具检索和比较的文档」，结构化文本就赢。

Org-mode（内置在 Emacs 里，本书写作时本机版本是 9.8.10）是其中功能最全的一种。它大到可以写一本书——那是《The Org Mode Manual》，几十页。这里只讲日常真正会用的四件事：capture（把任何东西随手记进文件）、outline（大纲与折叠）、agenda（按时间汇总待办）、refile（把条目从一个文件挪到另一个文件），再加 table（轻量数据表）。

4.1 先说一个必须知道的实测结果

易错

网上教 Org 的键位，绝大多数只在你装的那一版 Org 上成立。我在本机 Emacs 32.0.50 + Org 9.8.10 上逐条查了 org-mode-map：C-c 后面跟单个字母的绑定（C-c a 日程、C-c c 捕获、C-c l 存链接、C-c e 导出、C-c b 加粗、C-c w refile）以及 M-1/M-2/M-3 优先级键，在这一版里全都不存在（(lookup-key org-mode-map (kbd "C-c a")) 返回 nil；我还在 org-keys.el 全文 grep org-key-shortcuts，零命中）；同样，经典的表格子键 C-c C-c a（对齐）、C-c C-c n（插入行）、C-c C-c D（删列）也都不存在——C-c C-c 现在是一个命令 org-ctrl-c-ctrl-c，它会根据光标位置自己判断该干什么（光标在表格里就对齐表格，在标题上就改标签）。而 C-c C-w（org-refile）、C-c C-e（org-export-dispatch）、C-x n s（org-narrow-to-subtree）这些双键的是还在的——所以不是「双键的都没了」，是「单字母那一批没了」。

要说清楚为什么老教程不算错：这些键在更早的 Org 版本里是默认绑定的，它们通过一个叫 org-key-shortcuts 的变量批量安装，而那个变量在 Org 9.8 里已经没有了。你读到的那篇文章大概率写于 Org 9.x 早期，作者当时看到的就是对的。

易错

往下读之前先花二十秒确认你的 Org 版本，否则下一段那份配置会静默覆盖掉你本来就有的官方绑定。按 M-，输入：

M-: (org-version) RET
"9.8.10"

判读方法：

  • 你的 Org ≥ 9.8——那批单字母键本来就不存在，下一段那份 keymap-set 是凭空新增，放心用。
  • 你的 Org 是 9.7 或更早——那批键本来就有官方绑定（由 org-key-shortcuts 装的）。你照抄下一段会静默覆盖它们，Emacs 不会给你任何提示。用不用新键位随你，但要知道你覆盖了什么：先按 C-h m 看一眼你现在 org-mode-map 上这些键原本是什么命令，记下来，将来想退回去就按 global-set-key／keymap-set 改回去。

还有一个更省事的办法：干脆别抄。下一段末尾就说了——Org 的命令名很好记，M-x 输入 org-agenda、org-capture 这些就够用。键位是个人偏好，装 Org 的默认绑定随时可用；那份配置是给「想用老文章里那套键」的人准备的。

这条经验说明一件事：Org 的键位不值得背，也不值得抄。正确做法是用命令名：任何时候想知道某件事对应哪个键，按 C-h m 看当前模式的真实键位；或者干脆用 M-x 输入命令名——Org 的命令名都很好记（org-agenda、org-capture、org-store-link、org-export-dispatch、org-refile）。

如果你就是想要一套顺手的键位，自己绑一份就行（本节所有键位，凡是有的我都标了来源）：

(with-eval-after-load 'org
  (keymap-set org-mode-map "C-c a" #'org-agenda)
  (keymap-set org-mode-map "C-c c" #'org-capture)
  (keymap-set org-mode-map "C-c l" #'org-store-link)
  (keymap-set org-mode-map "C-c e" #'org-export-dispatch)
  (keymap-set org-mode-map "C-c w" #'org-refile)
  (keymap-set org-mode-map "C-c b" #'org-bold)
  (keymap-set org-mode-map "M-1" (lambda () (interactive) (org-priority-up)))
  (keymap-set org-mode-map "M-2" (lambda () (interactive) (org-priority-down)))
  (keymap-set org-mode-map "M-3" (lambda () (interactive) (org-priority-remove))))

keymap-set 是 Emacs 29 起推荐的写法——NEWS.29 里专门有一条「Use keymap-set instead of define-key」。它接受「字符串形式的键序列」而不是向量，省掉了 [?\C-c ?a] 这种噪音。

技巧

一个小坑：在 Emacs 32.0.50 上 (require 'keymap-set) 会报 Cannot open load file "keymap-set"，因为 keymap-set.el 这个文件已经不存在了，定义被并进了 lisp/keymap.el（我实测 (symbol-file 'keymap-set) 返回的正是 .../lisp/keymap.elc）。但 keymap-set 本身照常可用，不要写那行 require。

4.2 capture：把脑子里的东西一键倒进文件

capture 解决的是一个非常具体的痛点：你想到一件事，但不想为此去开文件、想好放哪儿、写好格式。capture 让你按一个键、在一个对话框里回答两三个问题，内容就落到了正确的文件里。

命令 org-capture，先定义模板：

(setq org-directory "~/org/")
(setq org-default-notes-file "~/org/notes.org")

(setq org-capture-templates
      '(("t" "Todo"
         entry (file+headline "~/org/todo.org" "Inbox")
         "* NEXT %?\n  SCHEDULED: <%t>\n  :PROPERTIES:\n    :CREATED: [<%t>]\n  :END:\n  %i"
         :immediate t)
        ("n" "Note"
         entry (file "~/org/notes.org")
         "* %?\n%i")
        ("l" "Link"
         entry (file+headline "~/org/refs.org" "Links")
         "* [[%x]]\n  %?\n  :PROPERTIES:\n    :CREATED: [%<%Y-%m-%d %H:%M>]\n  :END:\n  %i")))

这段模板的读法："t" 是快捷字母（进入 capture 后直接按 t 选它）；entry 是「插入一个条目」；(file+headline "文件" "标题") 意思是要先找到（或创建）这个文件里的这个标题，没有就新建；%? 是光标落点；%t 是时间戳；%i 是正文；<%t> 在 HTML 里必须写成 &lt;%t&gt;，Org 会把它变成活动时间戳。

没有「交互式模板向导」可用了。老教程里的 M-x org-capture-init-templates 在 Org 9.8.10 里已经不存在——我实测 (fboundp 'org-capture-init-templates) 返回 nil，整个 org 目录里 grep init-templates 也零命中。今天最省事的做法是：先在 *scratch* 里 M-x customize、找 Org Capture Templates 加一条（Customize 会把模板写成规范的列表，你只需要填「快捷键 / 标题 / 正文」三个字段）；或者干脆照着上面那段手写——模板写错时 M-x org-capture 会在选模板那一步就把错误报出来，不会有静默失败。

4.3 outline：大纲就是文件结构

Org 文件就是纯文本，标题以若干个 * 开头，* 的个数就是层级：

* 第一层标题
** 第二层标题
*** 第三层标题
** 另一个第二层
* 第二个第一层

这一层结构就是 outline（大纲），它同时是导航、折叠和改写的抓手。

  • TAB — org-cycle：折叠/展开当前位置的子树（实测存在的键）。
  • S-TAB — org-shifttab：连父级一起折叠（在 org-keys.el 里写作 <backtab>；C-c TAB 是另一个命令 org-cycle-force-archived，别记混）。
  • M-RET — org-meta-return：在当前位置插入一个新标题，层级和当前标题一样。
  • M-<left> / M-<right> — org-metaleft / org-metaright：降低/提升一级（就是在移动那些 *）。M-<up> / M-<down> — org-metaup / org-metadown：整棵子树往上/往下挪。
  • M-x imenu — 跳到任意标题（Org 没有给这个动作单独绑键；全局的 M-g i 是 Imenu 的键，在 Org 缓冲区里同样有效）。
  • C-x n s — org-narrow-to-subtree：临时只看当前子树。退出用 M-x widen（没有 C-x n w 这条绑定，我查过本机 Org 9.8.10 的 org-mode-map）。org-narrow-to-block（C-x n b）和 org-narrow-to-element（C-x n e）同理。
  • C-c C-r — org-fold-reveal：展开到光标所在层级。
要点

Org 的折叠是「文本级」的：被折叠的标题，行首那几个 * 会变成 ...，内容整段替换成一行提示。文件没有被改动，所以可以随便折叠、随便撤销。

4.4 agenda：把所有文件的待办按时间汇总

命令 org-agenda（C-c a 需要自己绑）。它扫过 org-agenda-files 列出的所有文件，把所有标题按「日程」重组，按天/周/月排成一张表。它本质上是一个视图——原始数据仍在各个 .org 文件里，agenda 缓冲区里的任何操作都是在改原文件。

(setq org-agenda-files
      '("~/org/inbox.org"
        "~/org/todo.org"
        "~/org/projects/alpha.org"
        "~/org/projects/beta.org"))

(setq org-agenda-span 7)          ; 一周视图（默认值就是 'week，写 7 等价）
(setq org-agenda-start-on-weekday 1)   ; 1 = 一周从周一开始（这才是默认值）；
                                       ; nil = 从周开始，别写反
(setq org-default-notes-file "~/org/notes.org")

;; org-agenda-files 里可以直接放目录：目录里所有匹配
;; org-agenda-file-regexp（默认 "\`[^.].*\.org\'"）的文件都会被收进来
(add-to-list 'org-agenda-files "~/org/projects")

4.5 refile：条目在文件之间搬家

命令 org-refile，C-c C-w（这个键 实测存在，不需要自己绑）。它在缓冲区里显示一棵文件树，选一个目标标题，条目就移过去了。常见用法是「待办先扔进 inbox.org，周末统一 refile 到各个项目文件」。

;; 定义 refile 的候选目标，让选择界面少翻很多层
;; 每项是「文件范围 . 候选标题的挑法」，挑法可以是 t（全要）、
;; (:level . N)（第 N 级标题）、(:tag . "TAG")、(:todo . "KEYWORD")
;; 或 (:regexp . "正则")。不设时默认就是 org-refile-targets 的 nil，
;; 即「当前 buffer 里的所有一级标题」
(setq org-refile-targets
      '(("~/org/inbox.org"    . (:level . 1))
        ("~/org/todo.org"     . (:tag . "refile"))
        ((org-agenda-files)   . (:regexp . "^Needs work"))))
易错

refile 的是「文件内容」，不是「副本」。条目会真的从原文件消失。好处是 inbox 永远保持干净，坏处是如果你 refile 错了，得自己 remember undo——Emacs 的撤销历史是按缓冲区分的，跨文件以后 C-x / 救不了你。所以先用 C-c C-w 在原地试一次、确认目标位置对了再真的搬。

4.6 table：够用的轻量数据表

Org 的 table（表格）不是电子表格，但比大多数人以为的能干。它是「管道符 | 围起来的文本块」，同样的东西你在 Markdown 里见过：

| 服务          | 延迟   | 状态     |
|---------------+--------+----------|
| user-service  |  12ms  | 正常     |
| order-service | 310ms  | 超时中   |
| pay-service   |   8ms  | 正常     |

用 C-c |（org-table-create-or-convert-from-region，实测存在的键）可以从已有的制表符文本一键转成表格；C-c C-c（org-ctrl-c-ctrl-c）在表格里会自动对齐；C-c =（org-table-eval-formula）重算 #+TBLFM 里的公式；C-c ?（org-table-field-info）显示光标所在单元格的坐标。

而在表格里，RET（org-return）是「跳到下一个单元格／行尾插行」，S-RET（org-table-copy-down）是「把上一行的内容复制到这一行」，M-<down> / M-<up> 在表格里是「插入行／删除行」，M-<left> / M-<right> 是「移动列」——因为这几个键在 Org 里是上下文相关的（org-metadown 在表格外的含义是「子树往下移」）。

想在表里算合计，在表格最后加一行，再在下面写公式：

| 服务     | 延迟 |
|-----------+------|
| user      |  12 |
| order     | 310 |
| pay       |   8 |
|-----------+------|
| 合计      |      |
#+TBLFM: $2=sum(v2)

然后按 C-c =。$2 里的 2 指第 2 列——这张表只有「服务」和「延迟」两列，所以合计写在第 2 列；sum(v2) 里的 v2 指的是表格第 2 列（v = vertical、h = horizontal）。公式写在别的列上，C-c = 会抱怨找不到可用的列。Org 还支持更多列操作（C-c = 之后选 Sum / Mean / Max 等）和按行筛选。

要点

什么时候用 Org table，什么时候别用。Org table 适合：几十行以内的对照表（接口清单、环境对照、命令速查、面试问题清单）。它不适合：几百行的数据、需要条件筛选排序、需要图表、或者要跟别人协作的数据——那是 CSV 加一个 Python/pandas 的活儿，别硬用 Org 硬扛。Org 表格的价值是「它就写在你的笔记里，和文字混排，Ctrl-C 一下能粘贴到任何地方」。

4.7 publish（发布）的边界在哪

命令 org-export-dispatch，C-c C-e（实测存在的键）。Org 有一套 export backend（导出后端），每种格式对应一个 ox-*.el 文件。我数了本机 Org 9.8.10 里实际存在的那些：ox-html、ox-latex、ox-beamer、ox-koma-letter、ox-man、ox-texinfo、ox-odt、ox-org、ox-md、ox-icalendar、ox-ascii、ox-publish。

易错

两个老教程常写的「导出命令名」今天不存在了。org-asciidoc-export 已经被一个通用的 ascii 后端取代（注册在 ox-ascii.el 里），没有 org-asciidoc-export 这个命令；org-pdf-export 也不是 Org 的命令——导出 PDF 是「latex 后端 + 外部 LaTeX 引擎」的组合，你在菜单里选的是 LaTeX 那一项，最后一步由外部程序完成。Markdown 是 ox-md，日历是 ox-icalendar，这两个后端都在。

边界在哪？分三档：

  1. 纯格式转换（该用）：Org 写文档，导出成 HTML / Markdown 发博客。这是最常见、最省事的用法，导出的 HTML 是静态的，不用 Org 就能看。
  2. 单人 PDF（看情况）：Org → LaTeX → PDF。听起来美好，实际要装 LaTeX 大礼包（几百 MB），编译中文还要处理字体和 CJK。而且导出的 PDF 你自己再改就麻烦了——正确做法是「以 Org 为源，PDF 当产物」，别反过来。
  3. 交互式发布（基本别用）：Org 老版本有个 org-publish，能把 .org 文件当成一个小网站发布。现在这条路已经不值得走了——你有一个 .org 源文件、一个静态站点生成器（任何一种）、和 CI。不要学那些十几年前的 Org 发布教程。
;; 最小可用的导出配置：导出成 HTML
(require 'ox-html)
(setq org-html-doctype "html5")

;; Markdown 导出（多行内容会被包进 <pre>，这是预期行为）
(require 'ox-md)

;; icalendar 导出（导出 .ics，导入日历）
(setq org-icalendar-include-todo "ALL")

;; 导出一个文件试试：
;; M-x org-export-dispatch RET  →  选 "HTML" / "Markdown" / "iCalendar"  →  RET
易错

按 C-c C-e 之后，如果列表里没有你想要的格式，Emacs 会提示先启用对应的 ox-* 库。这时用 M-x 打开 customize，或者直接 M-x 运行 (require 'ox-md) 再重试。哪些后端「开箱就在」取决于打包方式——本机 Org 9.8.10 里 (require 'ox-md)、(require 'ox-icalendar)、(require 'ox-html)、(require 'ox-latex)、(require 'ox-ascii)、(require 'ox-odt)、(require 'ox-man)、(require 'ox-texinfo) 我一次全部试过都成功，但别的发行版可能把其中一部分拆出去。最省事的自查办法是按 C-c C-e 看列表里到底有什么。

五、集成与胶水

前面的功能都是「Emacs 自己就能做」的。这一节讲的是把 Emacs 和外部世界缝起来的那几层薄薄的胶水：让它知道你在哪个项目、该用什么解释器；让你按下一个前缀键时它自己告诉你后面是什么；把 minibuffer 里那张老旧的候选表换成今天的样子。

5.1 direnv 与环境变量：让 Emacs 知道「我在哪个项目」

环境变量（environment variable）是操作系统传给你这个进程的一串「名字 = 值」。Emacs 启动时继承你从终端启动它时的那一份——然后就再也不变了。这就是很多新手遇到的怪事：「我在终端里 conda activate 之后 python 指向新版本，Emacs 里跑的还是旧的。」

Emacs 里操作环境变量的函数在 env.el 里：getenv（读一个变量）、setenv（写一个变量）、substitute-env-vars（把字符串里的 $VAR 展开成实际值）。

易错

在 Emacs 32 上，(require 'environment) 会失败，M-x environment 也没有了。我实测 Emacs 32.0.50 的源码树 lisp/ 里没有 environment.el，只有 env.el；(fboundp 'environment) 返回 nil，(require 'environment) 报 file-missing。具体从哪个版本改名我没法在这台机器上核实，你手上有旧版本的话可以用同样一条命令自查。老教程里 M-x environment RET 那个「可视化改环境变量」的界面，请改用 M-x shell 里的 export，或者用下面的 direnv。

direnv 是这个问题的标准解法。它的思路是：项目根目录放一个 .envrc 文件，写明这个项目需要哪些环境变量；每次 Emacs 切换到不同目录时，自动跑一次 direnv export 把结果喂给 Emacs。你不需要手动 activate 任何东西。

Emacs 侧的 direnv 包在 MELPA（2026-10-03 的版本是 20260630），仓库 github.com/wbolster/emacs-direnv（约 400 stars，最近提交 2026-06-30；注意它已经从 emacs-direnv/direnv 搬到个人名下了）。我读了当前源码，它暴露的入口是这几个：direnv-mode（全局次模式）、direnv-update-environment（按当前缓冲区文件更新）、direnv-update-directory-environment（按指定目录更新）、direnv-allow（手动更新并显示摘要）。

(use-package direnv
  :config
  (direnv-mode 1))

;; 更新的时机由 direnv 自己挂在这些钩子上：
;; post-command-hook 和 before-hack-local-variables-hook
;; 所以「切文件 → 环境自动跟上」是内置行为，不用配。

;; 安全提示：如果 .envrc 要执行任意代码，首次进这个目录时
;; direnv 会弹窗确认。可以配置自动允许：
(setq direnv-always-show-summary t)
(add-to-list 'safe-local-variable 'direnv-mode)

配置里 direnv-always-show-summary（默认 t，源码里是 defcustom）控制「每次环境变化都打一条消息」；direnv-show-paths-in-summary（默认 t）控制摘要里要不要把 PATH 的变化也列出来——路径很长，关掉清爽很多。

技巧

不想装 direnv 也有办法。很多语言服务器只需要知道「项目根在哪」，用 project.el 就够了（上一节讲过）——真正需要 direnv 的，是「不同项目的环境变量确实不同」这类场景，比如 Python 有多个虚拟环境、或者你需要 JAVA_HOME 随项目切换。如果你只有一个环境，装 direnv 只是白添一个每次敲命令都要跑一次的外部进程。

5.2 which-key：让键位自己告诉你

Emacs 的键位是前缀式的：C-x p f 要按三次，中间两次 Emacs 只能默默等着你。这对新手是灾难——你按了 C-x p 之后完全不知道接下来能按什么。

which-key 解决的就是这个：按下前缀键之后，等你没动静一会儿，它就在屏幕底部列出这个前缀后面所有可按的键和它们对应的命令名。

要点

which-key 从 Emacs 30 起是内置的（NEWS.30 第 1927–1929 行：「New package 'which-key'。The 'which-key' package from GNU ELPA is now included in Emacs」）。我确认了 Emacs 32.0.50 的 lisp/which-key.el 存在，直接 (require 'which-key) 就行，不需要装包。上游仓库 github.com/justbur/emacs-which-key 已经 archived（最后一次提交 2024-06-25）——这不是坏事，说明它已经毕业进 Emacs 了，之后的维护由 Emacs 社区接手。想升级的话 GNU ELPA 上还有 3.x 版本。

;; Emacs 30+ 内置，直接 require
(use-package which-key
  :init
  ;; 变量必须在 which-key 加载前设置
  (setq which-key-idle-delay 0.7          ; 默认 1.0 秒，改快一点
        which-key-show-prefix 'echo        ; 默认就是 'echo
        which-key-max-description-length 40)
  :config
  (which-key-mode 1))

几个值得知道的行为（默认值来自 Emacs 32.0.50 的 which-key.el 源码）：which-key-idle-delay 默认 1.0（秒），which-key-idle-secondary-delay 默认 nil，which-key-max-description-length 默认 27，which-key-show-prefix 默认 'echo——提示直接画在屏幕最底下的回显区，不再另开一个小窗，这是新版最明显的体验变化。

技巧

如果提示还是跟不上你，把 which-key-idle-delay 调到 0.2，并把 which-key-max-description-length 调小（描述太长会挤掉后面的键名）。反过来，如果你觉得烦——它真的很烦，尤其是你已经会了之后——直接 M-x which-key-mode 关掉，或者把 which-key-idle-delay 调到 2.0。

5.3 vertico + corfu + cape：今天的补全组合

Emacs 29 引入了新的补全框架（completions），跟老的 Completion 并行。从 29 开始，「在 minibuffer 里输入 → 弹候选表 → 用方向键选 → RET 确认」这条路径被替换成了新式补全。这三个包就是新式补全上最常用的三层积木：

  1. vertico（MELPA 20260913，GNU ELPA 2.x，仓库 github.com/minad/vertico，约 1890 stars）——排序层。把候选按「最近用过的排前面」重排。它的招牌功能是 orderless matching：你打 nvim 能匹配出 native-comp-…、vertico-mode 之类的候选，因为它不要求字符连续。
  2. corfu（MELPA 20260913，GNU ELPA 2.x，仓库 github.com/minad/corfu）——交互层。它负责弹出候选、让你选中、直接把选中的结果插入缓冲区，还顺便接管文档窗口。
  3. cape（MELPA 20260927，GNU ELPA 2.x，仓库 github.com/minad/cape，约 790 stars）——触发层。它在合适的时机（打字停一下、或者按 C-M-i）自动调用当前主模式该用的补全源。

配合它们通常还有两个：prescient（排序，记住每个候选的历史频率，MELPA 20260906）和 orderless（只提供 orderless 匹配算法，MELPA 20260927，GNU ELPA 1.x）。vertico 内置的排序已经够用，prescient 是锦上添花。

;; 依赖顺序：orderless → vertico → corfu → cape
(use-package vertico
  :after vertico-sort)

(use-package orderless
  :diminish t
  :init
  (setq orderless-matching-style 'orderless))

(use-package corfu
  :diminish t
  :init
  ;; 1. 用 C-M-/ 触发，别抢 TAB（别的模式要 TAB）
  (keymap-set corfu-map "C-M-/" 'corfu-complete)
  (keymap-set corfu-map "TAB" nil)
  ;; 2. 候选先按长度排序，再按缓冲区顺序兜底
  (setq corfu-sort '(length sort-buffer)
        corfu-preview-sort '(length))
  ;; 3. buffer 内补全
  (keymap-set completion-base-map "C-SPC" 'corfu-complete)
  (keymap-set completion-list-mode-map "C-M-o" 'corfu-complete))

(use-package cape
  :diminish t
  :init
  (keymap-set completion-list-mode-map "C-c C-i" 'cape-complete-at-point)
  :hook ((emacs-lisp-mode . cape-auto-complete)
         (python-mode . cape-auto-complete)
         (conf-mode . cape-auto-complete)
         (c-ts-mode . cape-auto-complete)
         (rust-ts-mode . cape-auto-complete)
         (sh-mode . cape-auto-complete)))

易错

最常见的冲突是 TAB。corfu 会把 TAB 抢去当「下一个候选」，但 TAB 在很多模式下是有意义的（缩进、补全、org-cycle）。所以上面的配置里明确写了 (keymap-set corfu-map "TAB" nil) 把 TAB 还回去，改用 C-M-/。另一个常见冲突是 corfu 和 company 一起开——corfu 和 company 是两个互相独立的补全前端，同时开会互相抢按键、弹两套候选列表。Emacs 自带的那一层是 completion-at-point，前端（corfu / company / cape / ivy）只是替换它的弹出界面，所以前端留一个就够了，别装两套。

技巧

如果补全让你觉得卡，先把 cape 关掉。cape-auto-complete 会在你打字时弹候选，配置稍微不当就变成「每敲几下卡一下」。先用 M-x list-timers 看看是不是有 native-comp-jit 的后台编译在抢 CPU，再只在需要的地方挂 cape-complete-at-point（绑在 C-c C-i，手动触发），确认好用再考虑自动化。

5.4 general 与 autop：配置量到了一定规模才需要

Emacs 的配置有一个「规模陷阱」：等你有了 30 个包、300 个自定义变量，init.el 就变成一坨没人看得懂的东西。两组工具专门解决这个：

  • general.el（MELPA 20250612）提供 defgeneral / defgeneral-region / defgroup-general：把「变量定义 + 包加载 + 配置」写在一起。defgeneral 生成的变量会自动出现在 M-x customize 里（前提是包里声明了 :group）。
  • autop.el 提供 defcustom/autop 这种「值写错了就给你一份 customize 链接」的类型安全变量——本作者不建议初学者用，它会让你的 init 变成一种新的 DSL。
(use-package general
  :commands
  (:eval defgroup-general)
  :init
  (defgeneral my-companion-command
    "我的常用命令：时间戳 + git 分支。"
    (interactive)
    (message "%s  on %s"
             (format-time-string "%Y-%m-%d %H:%M:%S")
             (or (vc-git-branch master) "no-vcs")))

  (defgeneral my-show-todo
    "打开我的待办文件。"
    (interactive)
    (find-file "~/org/todo.org"))

  (defgeneral my-project-root
    "当前项目的根目录字符串。"
    (or (when-let ((proj (project-current nil)))
          (car (project-roots proj)))
        default-directory)))

然后调用就变成 M-x my-companion-command。这个模式的价值在于：把「我想要什么」写成一句英语，而不是一堆设置变量然后配一堆钩子。代价是多了一层间接，初学者读 init 会更费劲。

要点

我的建议：先别用。第 13 章讲的 use-package 已经解决了「声明依赖 + 延迟加载 + 配置」这三件事。等到你的 init 超过 500 行、并且开始觉得「这段配置在干什么」说不清楚的时候，再引入 general.el。配置的价值不在于优雅，在于你能一年之后还改得动它。

5.5 keymap-set：29 起推荐的绑定写法

最后一件胶水。Emacs 有两种绑定按键的写法：

;; 老写法（Emacs 28 及以前唯一的选择）
(define-key global-map (kbd "C-c C-v") 'version-control)
(define-key some-mode-map [?\C-c ?a] 'some-command)

;; 新写法（Emacs 29 起推荐）
(keymap-set global-map "C-c C-v" #'version-control)
(keymap-set some-mode-map "C-c a" #'some-command)

NEWS.29 里有一条明确写着「Use keymap-set instead of define-key」（以及对应的 keymap-set-after 替代 define-key-after）。差别有两处：键序列写成字符串（"C-c C-l"）而不是向量（[?\C-c ?\C-l]），可读性好很多，少一层反斜杠噪音。

易错

网上有说法称 keymap-set 遇到已有绑定会拒绝并给你一条消息——这是错的，它照绑不误。我在 Emacs 32.0.50 上实测：先看 (key-binding (kbd "C-x C-f")) 是 find-file，执行 (keymap-set global-map "C-x C-f" #'find-file-read-only) 之后再查，它已经变成 find-file-read-only 了，中间没有任何报错。好处是 define-key 也有同样的「直接覆盖」语义，你现在写的每一条绑定都要自己负责——覆盖别人的包之前先 M-x describe-key 看一眼。另一个区别只是形式：keymap-set 的 KEY 参数必须是字符串（或满足 key-valid-p 的键），不能传向量。

易错

在 Emacs 32.0.50 上写 (require 'keymap-set) 会失败：keymap-set.el 这个文件已经被合并进 lisp/keymap.el 了（(symbol-file 'keymap-set) 指向 keymap.el）。宏本身照常可用，我实测 (keymap-set global-map "C-c C-l" #'find-file) 能正确绑定。所以：不要写那行 require。网上很多配置模板里都有它，照抄会报错。

练习 11　你要把 C-c C-l 绑到 find-file。Emacs 29 之后推荐怎么写？为什么不能照抄老教程里的 (require 'keymap-set)？

写 (keymap-set global-map "C-c C-l" #'find-file)。不能 require：在 Emacs 32.0.50 上 keymap-set.el 这个文件已经不存在了（定义被并进了 keymap.el），(require 'keymap-set) 会报 Cannot open load file。它本身不用加载就能用——我实测这条绑定写进去之后 (key-binding (kbd "C-c C-l")) 确实返回了 find-file。

练习 12　你有三个 Python 项目，各自用不同的 virtualenv。Emacs 不管你从哪个终端启动，永远用同一个解释器。怎么解决？

两个办法。一：装 MELPA 上的 direnv 包（仓库 wbolster/emacs-direnv），每个项目根目录放 .envrc 写上 layout python3，Emacs 切目录时自动应用。二：如果只是「解释器名字不同」，用 exec-path 和 project.el 挂钩也行，但麻烦得多。direnv 是标准解法。

六、Emacs 作为 shell

第 11 章已经讲过怎么把命令结果倒进缓冲区。这里补的是另一个问题：你想在 Emacs 里真的开一个能交互的 shell。Emacs 为这件事准备了六套方案，它们解决的问题完全不同，混着讲最容易让人选错。

6.3 term、ansi-term 与 vterm

term（lisp/term.el，内置）是一个行模式的终端模拟器：整个屏幕就是一条很长的文本行，你用普通的 Emacs 编辑命令改它。这和 comint 很像，区别是 term 不猜提示符格式，它靠一个「终端驱动程序」文件（etc/term/*.el，xterm、screen、tmux、linux、vt100……都有）来知道字符怎么控制光标。行模式的好处是编辑方便，坏处是全屏程序会画得很乱。

易错

ansi-term.el 这个文件在现代 Emacs 里已经没有了。我在 Emacs 32.0.50 上实测：(require 'ansi-term) 报 Cannot open load file "ansi-term"，源码树里也找不到 ansi-term.el。但 M-x ansi-term 仍然能用——因为它被合并进了 term.el，loaddefs.el 里的自动加载声明写的是 (autoload 'ansi-term "term" ...)。我实测 (ansi-term "cat") 能正常跑起来。所以结论是：ansi-term 还在，只是它的「文件」变了；配置里不要写 (require 'ansi-term)。

(defvar my-vterm-shell "/bin/bash")
(defun my-vterm (&optional (new-buffer nil))

  (interactive)
  (vterm new-buffer (format "cd %s; PS1='(emacs) %% ';" default-directory)
           my-vterm-shell "-l"))
要点

2026 年的建议：vterm 是默认答案，term/ansi-term 是备选。理由很直接：term 的行模式在 vim、htop、fzf、tmux 面前基本不可用，而 vterm 全部正常。代价是 vterm 多了一个外部依赖（libvterm），而且输出不能像文本缓冲区那样 C-s 搜索——想搜历史输出还是得靠 tmux（配合 tmux pipe-pane 把输出灌进一个真缓冲区）。

易错

vterm 里几乎所有按键都被终端程序吃掉了：C-c 是 SIGINT，C-d 是 EOF，C-z 是挂起，C-w 可能被 readline 占用。所以 Emacs 的按键必须用 C-c 前缀或者 C-M（Meta）前缀来绑——这就是上面配置里用 C-c C-k、C-c M-t 的原因。另外 (vterm-available-p) 必须在 use-package 里加 :if 守卫，否则 libvterm 没装时 Emacs 启动会报错。

6.4 eshell：Emacs 自己实现的 shell

eshell（lisp/eshell/*.el，内置）的思路最激进：连外部进程都不起。ls 是 Emacs 内部函数做的（em-alias.el），cd、pwd、export、通配符（em-glob.el）全是 Elisp 实现。它最大的卖点是目录感知补全：你打 TAB，它会列出这个命令能补什么（命令参数补全、文件名补全、变量名补全，各走各的表）。

eshell 的绑定分两层：eshell-mode-map（我实测 Emacs 32.0.50 上有 16 条）和 eshell-command-map（14 条，即按下 C-c 之后的那一层，源码在 lisp/eshell/esh-mode.el 的 defvar-keymap 里）。常用的这七条：

eshell 的坑比它的好处多。它的 glob、管道、heredoc 都是近似实现；命令找不到时必须显式加 eshell-command-extension-path；cd 只改 Emacs 自己的 default-directory，不会通知外面；最要命的是 eshell 里没有真 shell 的 source、alias、管道进 grep 的性能。所以我的建议是：把 eshell 当「Emacs 控制面板」而不是「你的主力 shell」。适合它的场景是「在项目目录里快速跑一两条 Emacs 能理解的命令」；如果你已经在终端里用 tmux + zsh + fzf 花了十年时间调好一套环境，Emacs 里的 shell不应该取代它。

;; 让 C-x c 每次都跑上一条编译命令
(global-set-key (kbd "C-x c") 'compile)

;; 记住所用的编译命令，按 C-x c 时给个候选列表
(add-to-list 'compilation-arguments '("-Wall" "-g"))

;; 按主模式挑默认编译命令
(defvar my-compile-defaults
  '((python-ts-mode . "python -m compileall .")
    (c-ts-mode      . "make -j8")
    (rust-ts-mode   . "cargo build")
    (sh-mode        . "bash -n")))

(defun my-compile ()
  "按当前主模式挑一条默认命令编译。"
  (interactive)
  (let ((cmd (or (cdr (assq major-mode my-compile-defaults))
                 (cl-loop for (mode . c) in my-compile-defaults
                          when (derived-mode-p mode) return c))))
    (if cmd (compile cmd) (call-interactively 'compile))))

注意：网上常见的「用 compilation-defaults 按主模式记编译命令」这个说法，我在这台机器上没能证实：(boundp 'compilation-defaults) 返回 nil，在 lisp/progmodes/compile.el 和整棵 lisp/ 目录里 grep compilation-defaults 都是零命中。但这只说明「这台机器的这份 Emacs 里没有」，不等于「Emacs 从来没有这个变量」——不同发行版的打包裁剪方式不一样。所以上面那段是用十几行 Elisp 自己实现的，不依赖它；你自己想用之前，先在 M-x 里求值 (boundp 'compilation-defaults) 确认一下。

可以确认存在的是这两个：compilation-arguments（lisp/progmodes/compile.el 第 191 行的 defvar，全局附加给编译命令的参数，默认 nil）和 compilation-environment（给子进程加的环境变量，默认 nil）。

6.6 怎么选：一张决策表

  1. 装好项目的编译、跑测试、看错误 → M-x compile，再用各主模式 hook 里设 compilation-arguments 来省掉每次敲参数。这是你 90% 的「跑命令」需求。
  2. 需要真 shell + 全屏工具（vim / htop / fzf / tmux） → vterm。
  3. 需要远程 ssh、数据库客户端、GDB、Python REPL，并且想在输出里搜索 → comint（M-x shell、M-x run-shell-command ssh RET host、gdb 等）。
  4. 想给项目开一个干净的、跟着项目目录走的 shell → C-x p e（project-eshell）或 C-x p s（project-shell，这个是真 shell 走 comint）。
  5. 想在 Emacs 里快速敲一两条 Emacs 理解的命令、享受目录感知补全 → eshell，但别指望它取代你的主力 shell。
技巧

一个能同时满足 2 和 3 的方案是 tmux + Emacs。在你真正的终端里开一个 tmux session（里面是你的 zsh 和所有配置），在 Emacs 里用 M-x run-shell-command tmux attach RET 接进去。这样 Emacs 里看到的是真终端，同时你能用 tmux pipe-pane 把任意 pane 的输出复制到一个 Emacs 缓冲区里搜索。这套组合比在 Emacs 里折腾终端模拟器省心得多。

练习 13　你想在 Emacs 里跑一个交互式 bash，还要在里面用 fzf 选文件。应该用哪一个？

用 vterm（M-x vterm）。fzf、vim、htop 这类全屏程序需要真正的终端模拟器，vterm 基于 libvterm，能正常工作。shell（comint）不行，eshell 也不行——它们都是文本/伪终端，fzf 在里面只会画出乱码然后卡住。

练习 14　你改了 Python 代码，想跑一遍看有没有语法错误，希望报错时能一键跳到出错那一行。怎么配置？

M-x compile（可以绑到 C-x c），命令填 python -m compileall .。在编译输出缓冲区里 M-n / M-p 在错误之间跳，RET 跳到源码对应位置，g 重新编译。最省事的做法是在 python-ts-mode-hook 里设 (setq-local compilation-arguments '("-Wall"))，这样每次编译自动带上参数。

三条贯穿全章的原则，最后再说一遍：

  • 先确认是内置还是第三方。本章至少有六个「以为是第三方其实内置」的案例（Eglot、which-key、dired-x、project.el、keymap-set、部分 tree-sitter 模式）。装之前先 M-x locate-library RET 名字 RET 试一下。
  • 键位以 C-h m 为准，以命令名为准。本章实测出来的最大陷阱是：网上教程的键位常常只对某个版本成立——Eglot 根本没有 C-c C-d，Org 这一版的 org-mode-map 里没有 C-c a，Dired 的整目录重命名是大写 R 而不是 r，而 outline 折叠早就不是 hide-entry / C-c M-f 那套了。你手上的 Emacs 版本和你读到的那篇文章不一定匹配。
  • 每加一个包都是一笔长期债。包的维护会停、键位会变、依赖会冲突。默认不加，需要时再加，关掉了 init 还能启动——这是 Emacs 配置健康的底线。
